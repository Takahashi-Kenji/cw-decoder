# CLAUDE.md - cw-decoder 開発ルール

このドキュメントは `cw-decoder` プロジェクト固有の開発ルールです。
共通ルールは上位の `.claude/CLAUDE.md` を参照すること。

## プロジェクト概要

AIモールス信号デコーダ。深層学習(CNN+BiLSTM+CTC)で音声からモールス符号トークン列を抽出し、決定論的変換表で欧文/和文テキストにデコードする。

詳細は `cw-ai-decoder-requirements.md` を参照。

---

## アーキテクチャの最重要原則

### 1. 「音→符号」と「符号→文字」の分離

- NN の語彙は**統合符号トークン集合** (欧文+和文+数字+記号+プロサイン)
- 文字割当 (欧文表/和文表) は決定論的変換表で行う
- NN にモード文脈を保持させない
- 変換表の修正だけで表示仕様を拡張できる構造を維持すること

### 2. 単一ソース管理

- 符号定義は `src/tokens/morse_tokens.py` を**唯一の真正なソース**とする
- 合成器・テスト・学習・推論すべてがこのモジュールを参照する
- 符号を別の場所に二重定義しないこと

### 3. 「?」出力の2分類

- **TABLE_MISS**: 変換表に該当なし (欧文モード中の和文符号等)
- **LOW_CONFIDENCE**: CTC 事後確率が閾値未満
- ログには種別を区別して記録すること (デバッグ用)

---

## 開発フロー

1. プランモード → 実行モード (要件定義書 §6 の Phase に従う)
2. 新規機能は `feature/説明` ブランチで作業
3. 修正は `fix/説明` ブランチ
4. テスト駆動: 実装前にテストを書く
5. コミット単位は論理単位で細かく
6. PR 経由で `main` にマージ

---

## コーディング規約

### Python

- Python 3.11+ の機能を活用 (`Literal`, `match`, `Self` 等)
- 型ヒント必須 (`mypy` 互換)
- `@dataclass(frozen=True)` を不変データに積極利用
- パス操作は `pathlib.Path`

### numpy / 信号処理

- **forループ禁止**: 波形生成は必ず numpy ベクトル化
- サンプル単位の処理は `np.cumsum`, `np.where`, ブロードキャスト等で表現
- 乱数は `np.random.Generator` を渡す (グローバル `np.random` を使わない)
- 性能要件: GPU が合成待ちにならないこと (目標 GPU 使用率 80% 以上)

### 再現性

- すべての乱数生成は `Generator` を引数で受け取る
- `make_fixed_eval_set` 等の固定セット生成 API は決定的でなければならない
- テストでも乱数シードを固定

---

## テスト方針

- `pytest` を使用
- 符号表は e-Gov「無線局運用規則 別表第一号」との照合テストを必ず通すこと
- 変換器の濁点合成は単体テストで網羅
- 合成器は数値検証 (SNR ±1 dB、波形時間 ±5% 等)
- `tests/data/eGov_morse_reference.py` は**実装と独立**して維持する

---

## 文字コード

- 符号表記: `・` (U+30FB 中黒) と `-` (U+002D ハイフン)
- 全角・半角の混在に注意。`morse_tokens.py` のコメントに明記する
- ファイルは UTF-8 (BOM なし)、改行 LF

---

## 注意事項

- 和文符号は実装誤記が起きやすい → 必ず e-Gov 規則と照合
- **`・-・-・・` は段落 (`。`) である。`」` ではない。** 2026-06-11 の定義当初から
  `」` と誤記しており、2026-08-12 に運用者が発見した。段落の記号の字形が `」` に
  似ているための取り違えと思われる。**受信のたび、相手の文末が `」` と表示されていた**
  - **`tests/data/eGov_morse_reference.py` も同じ誤りを持っていたので照合テストは
    全部通っていた。** 実装と参照が同じ間違いをすると独立した検証にならない。
    **参照表を書くときは実装を見ないこと**
  - 本物の括弧は和文表に実在する: 下向き括弧 `「` = `-・--・-`、
    上向き括弧 `」` = `・-・・-・`。**どちらもこの語彙には入れていない。**
    トークン ID は `(符号長, 符号文字列)` の辞書順なので、足すと**それ以降の ID が
    全部ずれて学習済みモデルが無意味になる**。足すのは再学習の機会に合わせること
    (`tests/test_tokens.py` の `TestDanrakuAndBrackets` が歯止め)
  - 送信テキストの中の `」` は段落の別名として通す (`src/tx/encoder.py` の
    `DANRAKU` / `_as_danraku`)。**`split_segments` の段階で書き換えないこと** —
    `find_unsendable` は segment が元テキストの部分文字列であることを前提に
    位置を求め直しており、置換すると `ValueError: substring not found` で落ちる
- ホレ/ラタは「和文開始/終了」の運用記号。符号トークンとしては独立、表示はモードで切替
- 濁点・半濁点は独立トークン、変換器側で前カナと合成
- Phase 1 では実信号は扱わない (Phase 4 で実装)
- ブラウザ版 (`web/`) がある。学習済みモデルを ONNX 化し、ブラウザ上でリアルタイムに
  CW をデコードする。詳細は `web/README.md` を参照
- **`morse_tokens.py` を変更したら `scripts/export_tokens.py` を必ず再実行すること**
  (`web/src/generated/tokens.ts` を再生成する。`tests/test_export_tokens.py` が差分を検出する)
- **モデルを再学習したら `scripts/export_onnx.py` と `scripts/export_golden.py` を
  再実行すること** (ブラウザ版の ONNX モデルと golden fixture を更新する)
- **確定精度に効くのは `commit_lag_s` 単独ではなく `commit_lag_s + hop_s / 2`
  (= 実効右文脈) である。目標値は 2.25 秒**
  (`docs/commit_lag_sweep_result.md` §8。held-out 実録音 21 件の CER 実測で
  実効 2.25 秒が最良だった。**3.0 秒より速く、かつ精度も良い**)
  - 確定境界は `totalConsumed - commit_lag` で、`redecode()` は hop ごとにしか
    呼ばれないため、確定時に使えている右文脈は `[commit_lag, commit_lag + hop)`、
    平均 `commit_lag + hop/2` になる
  - **デスクトップ版もブラウザ版も hop 0.5 / lag 2.0 → 実効 2.25 秒で同一**
    (`src/infer/settings.py` と `web/src/ui/app.ts`)
  - hop の既定は `AppSettings` / `AudioInferenceWorker` / `SlidingWindowDecoder` の
    3 箇所にある。**変えるときは 3 つとも揃えること** (過去に片方だけ取り残して
    「直接生成したときだけ挙動が違う」状態を作っている)
  - **hop を変えるときは必ず `commit_lag_s` も動かして和を保つこと** (hop だけ
    縮めると右文脈が静かに失われる。実際に一度これを踏んでいる)
  - **これ以上縮めるとはっきり悪くなる**: 実効 1.5 秒で +1.8pt、1.0 秒で +5.7pt
  - **同じ文書の §1〜§4 (2026-08-05/06 の掃引) は「2.5 を維持、下げられない」と
    結論しているが、これは覆っている。** 旧掃引は**学習データ**に対して
    「オフライン一括デコードとの一致率」という**代理指標**で測ったものだった。
    一致率は正しさではない (オフライン結果自体が誤っていれば一致は良いことではない)。
    **評価は held-out データに正解ラベルで当てること**
- **確信度閾値を下げて `?` を消してはいけない。** held-out 実録音で閾値 0.5 → 0.0 に
  すると CER が 19.74% → 23.64% と 3.9pt 悪化した。`?` の裏に正解が隠れているのでは
  なく、ほとんど間違った文字が出てくるだけだった
  - `?` を画面から減らしたいときは、**確定テキストは変えずに表示層で**
    最尤文字を薄字にする (`web/src/ui/app.ts` の `renderInto`)。CER は悪化しない
- **辞書補正 (`src/infer/word_correct.py`) は「文字」ではなく「語の切れ目」を主に直す**
  (`docs/word_correct_result.md`)。held-out 欧文で CER 19.25% → 17.15% (-2.09pt)、
  和文は +0.00pt。LLM を使わずマイクロ秒で終わる
  - 寄せ先は**符号 (・-) の距離**で選ぶこと。素の編集距離では D と B が「ただの
    別の文字」になり、CW の誤りの構造 (点 1 個の差) が消える
  - **語彙 `EUROPEAN_LEXICON` はここが唯一の真正ソース。** `src/llm/prompt.py` の
    参考語彙もこれを参照する。書き写すと必ず食い違う
  - **歯止めを外してはいけない。** 数字を含む語 (コールサイン/RST)・プロサインは
    触らない。2 位との差 (margin) が無ければ寄せない。実測で `?UR` の最近傍は
    誤りの `CUL` で、margin が無ければ誤答を自信ありげに出していた
  - **`?` は「読めなかった」印であると同時に符号表にある実在の文字 (・・--・・)**。
    `QSL?` の `?` を消すと 0.42pt 悪化する
