# cw-decoder 概要と原理

このドキュメントは cw-decoder が**何をするものか**と**どういう仕組みで動くか**を説明します。
インストール手順は [INSTALL.md](./INSTALL.md)、画面の使い方は [USAGE.md](./USAGE.md) を参照してください。

---

## 1. これは何か

アマチュア無線の **CW（モールス信号）を耳で追う代わりに、画面に文字で出す**ソフトウェアです。
受信機の音声出力を PC に入れると、リアルタイムで欧文（英数字）・和文（カタカナ）に変換して表示します。

主に HF 帯（7 MHz 帯など）の実運用を想定しています。実際の交信では次のような条件が重なります。

- **手送り電鍵の揺らぎ** — 人が打つ符号は機械のように正確ではない
- **QSB（フェージング）** — 電離層の状態で信号が周期的に強弱する
- **QRM（混信）** — 近い周波数に別の局がいる
- **QRN（空電）** — 雷などのインパルスノイズ

従来のデコーダはこれらに弱い傾向がありました。cw-decoder は深層学習で符号を読み取ることで、
崩れた信号に対する耐性を上げることを狙っています。

### できること

- 欧文・和文のリアルタイムデコード（モード自動切替あり）
- 録音した WAV ファイルのオフラインデコード
- 受信音の録音とスペクトログラム表示
- 受信機を繋いだ PC と処理する PC が別でも動作（LAN 経由の音声転送）
- LLM による清書・翻訳（任意。API キーが必要）

### できないこと・向かないこと

- **送信はしません**。受信専用です
- **極端に弱い信号は読めません**。実効 SNR がおよそ 0 dB を下回ると急激に精度が落ちます（後述）
- **複数局の同時デコードはできません**。フィルタで 1 局に絞る前提です
- 耳で取れない信号を読めるわけではありません。**人間の補助**であって置き換えではありません

## 2. 原理

### 2.1 なぜ機械学習なのか

従来のルールベース方式は「短点と長点をタイミングの閾値で判定する」という考え方です。
理屈は単純ですが、実際の運用では次の理由で崩れます。

- 手送りの符号長は一定でない。同じ人でも文中で変わる
- ノイズで符号の切れ目が埋もれる、あるいは無い所に切れ目が現れる
- 速度（WPM）が交信中に変わることがある

閾値を調整して個別の条件に合わせることはできますが、条件が変わるたびに調整が要ります。
機械学習は「**崩れ方そのものを大量に見せて覚えさせる**」アプローチで、この調整を学習に肩代わりさせます。

### 2.2 「音 → 符号 → 文字」の三層分離

このプロジェクトで最も重要な設計判断です。

```
音声入力
  ↓ ① 前処理（バンドパスフィルタ・メルスペクトログラム）
  ↓ ② ニューラルネット（CNN + BiLSTM + CTC）
符号トークン列   ← 例: [・-][-・・・][-・-・]
  ↓ ③ 変換表（欧文表 / 和文表）
表示テキスト     ← 欧文なら "ABC"、和文なら "イロハ"
```

ニューラルネットの仕事を「**音から符号の並びを取り出すこと**」だけに限定し、
符号を文字に割り当てる作業は決定論的な表（辞書引き）で行います。

なぜ分けるのか。**欧文と和文は同じ符号が別の文字を意味する**からです。

| 符号 | 欧文 | 和文 |
|---|---|---|
| `・-` | A | イ |
| `-・・・` | B | ハ |
| `-・-・` | C | ニ |

音として区別できないものを、ニューラルネットに区別させようとすると無理が生じます。
そこで音響レベルでは曖昧さを残さず、文字の割り当ては後段に任せます。この分離には実際に効果がありました。

- 和文モードでの数字対応が、**モデルの再学習なしで**実現できた（変換表に足すだけ）
- ニューラルネットの誤りと変換ロジックの誤りを切り分けてデバッグできる
- チャンク単位のストリーミング推論で、モデルが「今は和文モード」といった文脈を保持する必要がない

符号の定義は `src/tokens/morse_tokens.py` の 1 箇所だけに置き、
合成データ生成・学習・推論・テストのすべてがそこを参照します。
定義が二重に存在すると必ず食い違うためです。この表は
総務省 e-Gov の「無線局運用規則 別表第一号」と**実装から独立に転記した参照辞書**で照合しています。

### 2.3 モデルの構造

```
入力: メルスペクトログラム (64 周波数ビン × 時間)
  ↓
CNN 3 層          — 周波数方向を圧縮し、時間方向は保つ
  ↓
BiLSTM 2 層       — 前後の文脈を見る（双方向、隠れ層 256）
  ↓
全結合層          — 73 種類の出力に変換
  ↓
CTC               — 符号トークン列を取り出す
```

パラメータ数は約 427 万（fp32 で 17 MB）。学習済みモデルを同梱しているため、
利用者が学習を回す必要はありません。

**73 の内訳**: 全モード共通の符号 71 種 + CTC 用の空白 1 + 語間スペース 1。
同じ符号は 1 トークンにまとめてあります（`・-` は「欧文 A かつ和文 イ」ではなく、単に `・-` というトークン）。

### 2.4 CTC — 「いつ」を教えなくてよくする仕組み

学習データを作るとき、本来なら「0.31 秒から 0.45 秒までが A」というように
**時刻の対応**を全部書く必要があります。これは現実的ではありません。

CTC（Connectionist Temporal Classification）は、
**「音声全体」と「正解の符号列」だけを与えれば、時刻の対応は自動で学習する**手法です。
音声認識で広く使われています。

仕組みとしては、各時刻で「何も出力しない」を意味する空白トークンを許し、
同じトークンの連続を 1 つにまとめることで、長さの違う音声と符号列を対応づけます。

```
モデルの出力: _ _ ・- ・- _ -・・・ _ _ -・-・ _
             ↓ 連続をまとめ、空白を除く
結果:        ・-  -・・・  -・-・
```

### 2.5 学習データはどう作るか

CW のラベル付き音声は世の中にほとんど存在しません。そこで**2 段構え**にしています。

**① 合成データで基礎を作る**

キーイング波形をプログラムで生成し、そこに実際の劣化要因を加えます。
テキストからいくらでも作れるので、ラベル付けの作業がゼロで済みます。

| 要素 | 範囲 |
|---|---|
| 速度 | 8〜50 WPM |
| ウェイト比（長点:短点） | 2.5:1 〜 4:1 |
| 要素長のばらつき | 短点長の 5〜25% |
| トーン周波数 | 400〜900 Hz |
| 立ち上がり/立ち下がり | レイズドコサイン 3〜10 ms |
| 白色雑音 | SNR −10〜+20 dB |
| QSB | 周期的な振幅変動 |
| QRM | 別の CW 局を重ねる（0〜2 局） |
| QRN | ポアソン分布のインパルス雑音 |

波形生成は numpy でベクトル化しています（for ループを使わない）。
GPU が合成待ちにならないようにするためです。

**② 実信号で仕上げる（ファインチューニング）**

合成データだけでは、実際の受信音との間に差が残ります。これを埋めるため、
**既知の原稿を自分で打鍵して録音**したデータで追加学習します。原稿がそのままラベルになるので、
書き起こし作業が不要です。

原稿は 6 要素符号（`?` `,` `-` `@` など、認識が特に難しい符号）が
設計した回数だけ出現するように手書きで作ってあります。乱数で文を組み立てると、
低頻度の符号が十分に出ないためです。

### 2.6 前処理 — バンドパスフィルタが効く

受信音はそのままモデルに入れません。

```
受信機の音声 → バンドパスフィルタ（中心 600 Hz / 帯域 400 Hz）
            → スキッシュ（無音判定）
            → メルスペクトログラム → モデル
```

**バンドパスフィルタは必須です。** 通さないと認識が崩壊します。実測では、
同じ録音 90 件に対して次の差が出ました。

| 前処理 | 誤り率（TER） |
|---|---|
| フィルタなし | **97.03%**（ほぼ全滅） |
| バンドパスフィルタあり | 14.44% |
| ＋ 前後に無音を追加 | **10.60%** |

CW のトーンは 500 Hz 前後の細い帯域にあり、それ以外の帯域はすべてノイズです。
帯域外を落とさずに特徴量へ入れると、モデルが見るべき情報が埋もれます。

「前後に無音を追加」が効くのは、録音の冒頭で音が唐突に始まると、
モデルがその立ち上がりを符号と誤読して先頭にゴミを出すためです。

### 2.7 ストリーミング — 遅延と精度の両立

リアルタイムでデコードするには、音声を細かく区切ってモデルに入れる必要があります。
ところが単純に区切ると、**区切り目にまたがる符号が壊れます**。

そこで「スライディングウィンドウ + 確定コミット」方式を使っています。

```
時間 →
[━━━━━━━━ 窓 30 秒 ━━━━━━━━]
        [━━━━━━━━ 窓（1 秒後） ━━━━━━━━]
                [━━━━━━━━ 窓（2 秒後） ━━━━━━━━]

  確定済み（黒で表示）    | 暫定（グレーで表示）
  ─────────────────────→ |
                    2.5 秒前までを確定する
```

1 秒ごとに直近 30 秒を丸ごとデコードし直し、
**2.5 秒より前の部分だけを「確定」として黒で表示**、それ以降は暫定としてグレーで表示します。
後から文脈が増えると読みが変わることがあるため、直近は確定させません。

この方式により、窓に収まる長さのファイルでは**オフラインデコードと 100% 一致**します。

音声のサンプリングレート変換には `soxr` のストリーミングリサンプラを使っています。
ブロックごとに独立して変換すると境界に歪みが生じ、短点・長点が壊れるためです
（開発中、これが原因で 37 トークンが 1 トークンに潰れる不具合が実際に起きました）。

### 2.8 自動モード切替

和文の運用では、和文の開始に「ホレ」（`-・・---`）、終了に「ラタ」（`・・・-・`）を送る習慣があります。
自動モードはこれを検出して、変換表を欧文用と和文用で切り替えます。

符号としては独立したトークンで、表示上のモードとは分離されています。

### 2.9 「?」には 2 種類ある

読めなかった箇所は `?` で表示されますが、内部では原因を区別して記録しています。

| 種別 | 意味 |
|---|---|
| **TABLE_MISS** | 変換表に該当がない（例: 欧文モード中に和文専用の符号を受信した） |
| **LOW_CONFIDENCE** | モデルの確信度が閾値に届かなかった |

前者は「モードの選択が違う」、後者は「信号が弱い・ノイズが多い」という別の対処につながります。
確信度の閾値は画面のスライダで調整できます。

> **確信度の閾値を下げて `?` を消してはいけません。** held-out 実録音で 0.5 → 0.0 に
> すると CER が 19.74% → 23.64% と 3.9pt 悪化しました。`?` の裏に正解が隠れているのではなく、
> ほとんど間違った文字が出てくるだけでした。

### 2.10 デコードの後に置く 2 段の直し

NN の出力そのものは触らず、後段で 2 つの直しを重ねます。**どちらも決定論的な層と
確率的な層に分かれており、役割が違います。**

| 段 | 何をするか | 速さ | 検証 |
|---|---|---|---|
| **辞書補正** | CW 定型語彙で語を切り直し・寄せする | マイクロ秒 | CER で測れる |
| **LLM 清書** | 文脈からの復元、和文の漢字かな交じり化 | 秒 | 和文は CER で測れない |

**辞書補正の寄与は「語の切れ目」が主です。** WORD_BREAK トークンの再現率が 57〜69% しか
ないため語が繋がって出ますが、語彙語の並びに厳密一致で分割できるときだけ切ることで
CER 19.25% → 17.15%（−2.09pt）になりました。

文字の寄せ先は**符号（・-）の距離**で選びます。CW の誤りは D(-・・) ↔ B(-・・・) のように
点 1 個の差で起きるので、符号空間で測ると正解が最近傍に来ます。文字空間では
D と B は「ただの別の文字」で、距離に情報がありません。

**欧文では LLM 清書は CER を悪化させます**（17.15% → 18.27%、+1.12pt）。辞書補正が既に
機械的な直しを済ませており、LLM は誤りを足す側に回ります。欧文で清書を使うかは
読みやすさとの取引であって、精度のためではありません。

和文は事情が違います。電文がカタカナなのは和文モールスの仕様上どうにもならず、
**漢字かな交じりへの変換そのものが目的**なので、LLM でしかできません。

## 3. 実際の性能

| 指標 | 値 |
|---|---|
| 合成評価データ トークン誤り率 | 0.00% |
| 合成評価データ 文字誤り率 | 2.48% |
| 実打鍵録音 20 件 トークン誤り率 | 23.27% |
| 合成＋実バンドノイズ 400 件 | 45.16% |

実運用の体感では、条件が良ければほぼそのまま読めます。

**信号強度に対する崖があります。** 実効 SNR（バンドパスフィルタ通過後の信号対雑音比）で見ると、

| 実効 SNR | トークン誤り率 |
|---|---|
| +10 dB | 1.3% |
| +5 dB | 6.3% |
| 0 dB | 77.9% |
| −5 dB | 90.3% |

**+5 dB と 0 dB の間で急激に悪化します。** 耳で「かろうじて取れる」程度の信号は、
現状のモデルでは読めないと考えてください。

苦手な符号もはっきりしています。`?` `,` `-` `@` といった**6 要素の長い符号は認識率がほぼ 0%** です。
出現頻度が低く、学習データに十分含まれていなかったことが原因と考えられます。

### 処理速度 — GPU は要らないどころか、CPU の方が速い

ライブデコードの条件は「**30 秒の窓を 0.5 秒以内にデコードし直せること**」です
（hop 0.5 秒ごとに窓を再デコードするため）。

2026-08-08 の実測（`models/full/best_infer.pt`、Intel Core i7-14700F + CUDA）。

| デバイス | 30 秒の窓のデコード | 最悪 | hop 0.5 秒に対する余裕 |
|---|---:|---:|---:|
| CPU 2 スレッド | 164 ms | 192 ms | 2.6 倍 |
| **CPU 4 スレッド** | **112 ms** | **134 ms** | **3.7 倍** |
| CPU 8 スレッド | 149 ms | 155 ms | 3.2 倍 |
| CUDA | 139 ms | 175 ms | 2.9 倍 |

**CPU 4 スレッドが CUDA より速い。** モデルが 427 万パラメータと小さく、
GPU はレイヤごとの起動費用（特に BiLSTM）の方が勝ってしまうためです。

そこで**既定を CPU にし、GPU はローカル LLM（清書）に空けています**。
明け渡すのに代償はありません。

- **GPU が必要なのは学習だけ**です。学習済みモデルを同梱しているため、利用者が学習を回すことはありません
- スレッドは 4 が最速で、増やすと同期の費用で遅くなります。
  実際には画面描画のほうが負荷が高い場合があります
- LAN 構成の送信側 PC はさらに軽く、深層学習のライブラリを読み込みません
  （numpy / sounddevice / soxr / scipy のみ）

> 測定環境: Intel Core i7-14700F、Windows 11、PyTorch CPU 実行。
> 絶対値は CPU により変わりますが、**1 コアあたりの性能で決まる**ため、
> 古い PC でも実時間には十分間に合う見込みです。

## 4. 構成

### PC 1 台の構成

```
受信機 ── 音声ケーブル ── PC（cw-decoder）
```

受信機のヘッドホン出力やライン出力を PC のライン入力に繋ぎます。

### PC 2 台の構成（LAN 経由）

受信機の近くに置く PC と、処理をする PC（GPU 搭載機など）が別でも動きます。

```
受信機 ── PC-A（送信スクリプト）
              │ LAN（16 kHz モノラル非圧縮 PCM / TCP / 約 32 kB/s）
              ↓
          PC-B（cw-decoder 本体）
```

PC-A で `scripts/audio_send.py` を動かし、PC-B で `--net-source` を指定して起動します。
PC-A 側は深層学習のライブラリを必要としません（numpy などの軽い依存のみ）。

**リモートデスクトップの音声転送は使えません。** 音声が狭帯域コーデックで圧縮され、
エネルギーの 99% が 1000 Hz 以下になります。そのため非圧縮のまま素通しする経路を用意しています。

## 5. 限界と既知の問題

正直に書いておきます。

- **弱信号は読めません**（§3 の崖）
- **6 要素符号（`?` `,` `-` `@`）はほぼ読めません**
- **語間スペースの過剰検出**が誤りの主要因の一つです。単語の切れ目でない所にスペースが入ります
- **LAN 経由で接続が切れても画面には何も出ません**。デコードが止まったまま表示が固まります
- 複数局が同時に聞こえる状況では、フィルタで 1 局に絞る必要があります

## 6. 開発から得た教訓

同種のものを作る方の参考になるかもしれない事柄です。

**評価データのラベルは、実際の音と一致していなければ意味がありません。**
このプロジェクトでは、評価用録音のラベルに「原稿には書いたが実際には打鍵しなかった符号」が
19 個混ざっていました。全体の 4% です。その結果、
「このモデルは特定の符号が全く読めない」という分析結果が出ていましたが、
実際には**音に存在しないものを読めないと数えていた**だけでした。

**合成データで良くなっても、実信号で良くなるとは限りません。**
合成データ上の指標を改善する実験を複数回行いましたが、いずれも実録音での性能は悪化しました。
両方の指標が同時に改善したのは、実録音でファインチューニングしたときが初めてです。

**実装しやすい打ち手を優先すると、当たらない手ばかり試すことになります。**
既存のパイプラインに引数を足すだけで試せる実験は手軽ですが、
効果が大きいと分かっていた「実信号での学習」は、データ収集が必要という理由で後回しになり続けました。

## 8. ライセンスと免責

このソフトウェアはアマチュア無線の受信補助を目的としています。
デコード結果の正確性は保証されません。**交信内容の確認は必ず自身の耳で行ってください。**
コンテストやアワードの申請など、正確性が要求される用途での使用は想定していません。
