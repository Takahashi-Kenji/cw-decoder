# 周波数と認識率の関係 実測結果

実施日: 2026-08-06
チェックポイント: `models/full/best_infer.pt`
デバイス: CUDA (RTX 5060 Ti)

**結論を先に書く。周波数まわりに伸びしろは無い。BPF の中心周波数は現行の 600 Hz が
最良で、受信ピッチに合わせようとすると悪化する。**

---

## 1. なぜ測ったか

ブラウザ版の実信号運用で誤認が 10% 程度という報告があり、その「?」のほとんどが
LOW_CONFIDENCE だった。運用者の受信ピッチが 527 Hz である一方、BPF の中心は 600 Hz
(通過 400〜800 Hz) だったため、次の仮説を立てた。

> BPF がトーンから外れているため信号を約 5 dB 落とし、一方で混信の多い 550〜750 Hz を
> 素通しさせている。つまり BPF が SNR を改善するどころか悪化させている。

**この仮説は実測で否定された。** 以下がその記録である。

---

## 2. 実験A: BPF の中心周波数 (実録音)

対象: `data/keying_scripts` の手打ち録音 20 件 + `data/keyed_extra` 1 件 = **21 件**。
録音のトーン周波数は FFT ピークで実測して **中央値 495 Hz、範囲 494〜527 Hz**。

フィルタはデスクトップ版 `src/app/workers.py` の `_StreamingBPF` と同じ特性
(4 次バターワース bandpass、`scipy.signal.butter(4, ..., btype="bandpass")`)。
デコードは `InferenceEngine.decode_chunk` + `TokenConverter(confidence_threshold=0.5)`、
CER は正解ラベルとの文字誤り率 (スペースを除去して比較)。

| 条件 | CER | BPF なし比 |
|---|---|---|
| BPF なし | 19.74% | — |
| 中心 450 Hz / 帯域 400 | 22.34% | +2.60pt |
| 中心 500 Hz / 帯域 400 | 20.26% | +0.52pt |
| 中心 550 Hz / 帯域 400 | 17.92% | −1.82pt |
| **中心 600 Hz / 帯域 400 (現行設定)** | **17.14%** | **−2.60pt** |
| 中心 650 Hz / 帯域 400 | 20.00% | +0.26pt |
| 中心 700 Hz / 帯域 400 | 21.30% | +1.56pt |
| 中心 500 Hz / 帯域 200 | 17.92% | −1.82pt |
| 中心 527 Hz / 帯域 200 | 20.26% | +0.52pt |
| 中心 550 Hz / 帯域 200 | 21.04% | +1.30pt |

### 読み取れること

- **現行の 600 Hz が全条件で最良。** トーンは 495〜527 Hz にあるのに、そこへ中心を
  合わせる (500 / 527 Hz) と**かえって悪化する**
- **BPF を外すと 2.60pt 悪化する。** BPF 自体は効いている
- 帯域を 400 → 200 Hz に絞っても改善しない

仮説は逆だった。**BPF は触らないこと。**「トーンに合わせるべきだ」という直感は
このデータで否定されている。

### 限界

21 ファイル、条件間の差は最大 5pt 程度。統計的な有意性の検定は行っていない。
「600 Hz が最良」は確からしいが、「550 Hz との 0.78pt 差」を根拠に何かを決めるのは
やりすぎである。言えるのは **「合わせに行く方向は間違い」** までである。

---

## 3. 実験B: トーン周波数そのもの (合成音、BPF なし)

モデル自体に周波数の得手不得手があるかを見る。合成音 (欧文 5 種 × SNR 10/5/0 dB =
15 サンプル/点)、WPM 23、ジッタ σ 0.10、BPF なし。**学習分布のトーン範囲は 400〜900 Hz。**

| トーン | CER | | トーン | CER |
|---|---|---|---|---|
| 300 Hz | 124.6% | | 600 Hz | 52.2% |
| 350 Hz | 72.5% | | 700 Hz | 41.6% |
| 400 Hz | 55.1% | | 800 Hz | 63.8% |
| 450 Hz | 61.8% | | 900 Hz | 36.2% |
| 500 Hz | 47.8% | | 1000 Hz | 100.5% |
| 550 Hz | 41.6% | | 1100 Hz | 98.1% |

### 読み取れること

- **学習分布 (400〜900 Hz) の中では周波数の得手不得手は見当たらない。**
  36〜64% とばらついているが、1 点あたり 15 サンプルしかないのでこの程度の差は
  ノイズの範囲。**範囲内の順位を根拠に何かを決めてはいけない**
- **範囲外に出た瞬間に崩壊する** (300 Hz で 124%、1000 Hz で 100%)。
  学習範囲は事実上ハードな境界である
- 運用者の 527 Hz は範囲の中に十分入っている。**周波数は問題の原因ではない**

CER の絶対値が高いのは、SNR 0〜10 dB の短文を `confidence_threshold=0.5` で
デコードしているため (`?` はすべて誤りに数えられる)。`eval_model.py` の数値とは
比較できない。条件間の比較にのみ意味がある。

---

## 4. 今後への申し送り

- **BPF の中心周波数を受信ピッチに合わせる変更はしないこと。** 実測で悪化する
- ブラウザ版 (`web/src/ui/app.ts`) の BPF も中心 600 Hz / 帯域 400 Hz のままでよい
- トーン周波数が学習範囲 (400〜900 Hz) の外に出る運用が想定されるなら、
  そのときは学習分布の拡張が必要になる。範囲内での微調整には意味が無い

再現用スクリプトはこの調査のために書いた使い捨てのもので、リポジトリには入れていない。
再測定が必要なら `scripts/analyze_keying.py` でトーンを実測し、
`src/app/workers.py` の `_StreamingBPF` と同じ `butter(4, [lo, hi], btype="bandpass")`
を掛けてから `InferenceEngine.decode_chunk` に渡せば再現できる。
