## 1. 現行モデル

| 項目 | 値 |
|---|---|
| 重み | `models/full/best_infer.pt` |
| 由来 | `models/full/best.pt` (フル学習 102,000 step) + 実信号 FT 1,000 step |
| 採用日 | 2026-08-03 (以後 **未更新**) |
| アーキテクチャ | CNN 3 層 + BiLSTM 2 層 + Linear、CTC |
| パラメータ数 | 4.27M (fp32 で約 17 MB) |
| 語彙 | 統合符号トークン 72 個 (blank 含む) |
| ブラウザ版 | 同じ重みを ONNX 化 (`web/`、ORT Web の WASM 実行) |

### 1.1 ネットワーク (`src/train/model.py`)

```
入力: 対数メルスペクトログラム (B, 64, T)
  ↓ Conv2d ×3  ch (32, 32, 64)、周波数方向のみ stride (2, 2, 1)
  ↓ BiLSTM 2 層、hidden 256、dropout 0.1
  ↓ Linear → 72 クラス
出力: (B, T, 72) → CTC
```

**時間次元 T は入力から出力まで保たれる** (CNN は周波数方向しか縮約しない)。
時間分解能は前処理のメル hop (10 ms) にそのまま等しい。

### 1.2 前処理 (`src/train/preprocessing.py`)

| 項目 | 値 |
|---|---|
| サンプルレート | 8 kHz |
| メルビン数 | 64 (50 Hz 〜 4 kHz) |
| 窓長 | 25 ms (200 サンプル) |
| ホップ | **10 ms** ← モデルの時間分解能はここで決まる |
| n_fft | 256 |
| 正規化 | あり (top_db 80) |

### 1.3 設計上の前提

- NN が出すのは**統合符号トークン列だけ**で、欧文表・和文表への割当は決定論的変換表
  (`src/tokens/morse_tokens.py`) が行う。表示仕様の訂正は**再学習なしで直せる**
  (2026-08-12 の段落 `・-・-・・` = `。` の訂正がこれ)。
- 逆に**語彙にトークンを足すと ID がずれて学習済みモデルが無意味になる**。
  トークン追加は再学習と同時にしかできない (§8)。

## 2. 学習条件

### 2.1 共通のハイパーパラメータ (`src/train/loop.py`)

| 項目 | 値 |
|---|---|
| 損失 | `torch.nn.CTCLoss` (blank=0, zero_infinity=True) |
| 最適化 | AdamW (lr 3e-4、weight_decay 1e-4) |
| AMP | 有効 (float16) |
| 勾配クリップ | norm ≤ 5.0 |
| ハードウェア | RTX 5060 Ti 16GB (Blackwell sm_120) |
| 速度 | 約 2.8〜3.0 sps (batch 8, num_workers 2 が最速) |

### 2.2 合成データの分布 (`src/synth/dataset.py` `DefaultConfigSampler`)

**現行モデルが見た分布** (`hand_keying=False` の従来分岐):

| パラメータ | 範囲 |
|---|---|
| WPM | **8 〜 50** (Phase 2 は 10〜40、Phase 2.5 で拡張) |
| トーン周波数 | 400 〜 900 Hz、ドリフト ±50 Hz/s |
| 立ち上がり/立ち下がり | 3 〜 10 ms |
| 長短点比 (dash/dot) | 2.5 〜 4.0 |
| 要素ジッタ σ | 0.05 〜 0.25 dot (全要素共通) |
| 要素間 / 文字間 / 語間 | 1.0 / 3.0 / 7.0 dot 固定 + σ |
| SNR | −10 〜 +20 dB (nominal) |
| QSB | 50% の確率で深さ 0〜0.8、周期 1〜8 秒 |
| QRM | 0 〜 2 局 |
| QRN | 30% の確率で 0〜10 回/秒 |
| 受信フィルタ | 中心 = トーン、帯域 250 〜 500 Hz |
| モード比 | 欧文 : 和文 = 0.5 : 0.5 |

**手打ち分布 (`hand_keying=True`) は実装済みだが既定オフ。**
2026-08-07 のフル学習で実打鍵 TER が 2 倍以上悪化したため、既定を `False` に戻し
CLI をオプトイン (`--hand-keying`) に反転した (§4 の (F))。

### 2.3 フル学習のコマンド (土台、2026-06-12)

```bash
python scripts/train.py \
  --steps 102000 --batch-size 8 --num-workers 2 \
  --ckpt-dir models/full --device cuda --seed 42
```

- 102,000 step × batch 8 = 延べ約 816,000 サンプル、約 9 時間
- データは**オンザフライ合成 100%** (実信号なし)

> **注意**: 当時の正確なコマンドは記録されていない (設計書に「102,000 step
> (フル + 補充)」とあるだけ)。上記は再現に使っている推定コマンドで、
> 設定ドリフトの疑いが残る。**次にフル学習を回すときはコマンドを結果文書に必ず残すこと。**

### 2.4 実信号ファインチューニングのコマンド (2026-08-03、採用)

```bash
python scripts/finetune.py \
  --data-dir data/real/train --resume models/full/best.pt \
  --ckpt-dir models/ft_1k --steps 1000 --lr 5e-5 --batch-size 16 \
  --mix-synth --real-ratio 0.5 --tone-center 490 --tone-span 60 \
  --num-workers 0
```

| 項目 | 値 |
|---|---|
| データ | 打鍵録音 90 件 (24.8 分)、`data/real/train` |
| ステップ | 1,000 (約 9 分) |
| lr | 5e-5 (フル学習の 1/6) |
| 合成混合 | あり (実データ比率 0.5) |
| トーン | 490 ± 60 Hz (運用者の受信ピッチ近傍) |
| 実ノイズ混合 | なし |

前処理は必須: **BPF 600/400 Hz + 前後 0.4 秒の無音追加**
(未処理だと TER 97% → BPF で 14.4% → 無音追加で 10.6%)。

> **synth_val の baseline が 2 種類あるのは評価条件が違うため。**
> A は `models/eval/b1_baseline.json` (37.21%)、B〜G は `models/eval/base_valnoise.json`
> (48.06%) を基準にしている。**synth_val の値は同じ評価バッチ内でしか比較できない。**

### 4.1 keyed_val の baseline が 2 つある理由 (ラベル汚染、2026-08-03)

keyed_val 20 件のラベルに、**実際には打鍵されていないトークンが 19 個**含まれていた
(`{HORE}` 7・`{RATA}` 7・`{SK}` 5)。原稿には書かれていたがオートキーヤーが送出して
いなかった。ref_tokens 447 の 4% にあたる。

- ラベル修正により baseline は **23.35% → 25.95%** に変わった
  (幻覚ホレが挿入誤りとして正しく計上されるため、悪化するのが正しい)
- **実験 A〜D の 23.35% はすべて汚染された値**である。同じ汚染で測っているため
  相対比較は生きているが、絶対値は E 以降と直接比べられない
- `[ラタ]` recall 0% は「音に無いものを数えていた」だけ。`[ホレ]` recall 85.7% も
  「和文冒頭で無条件にホレを吐く癖」とラベルがたまたま一致していただけだった
- 一方 `?` `,` `-` `@` の recall 0% は**本物** (打鍵済みの新データ 90 件でも全滅)

### 4.2 各実験の要点

**(A) B1 実効 SNR 拡張** — 低 SNR 側は劇的に良くなった (synth 0 dB 54.6% → 29.5%) が、
高 SNR 域は微悪化 (+5 dB 4.9% → 9.7%) し、実打鍵は +19.7pt 悪化した。
WORD_BREAK recall が 80% → 41% に落ちている。
**「synth だけ見ると成功に見えるが実録音は悪化する」を初めて暴いた実験。**

**(B〜D) 実ノイズ混合 FT** — step を増やすほど keyed_val が単調に悪化した
(24.4 → 25.3 → 26.1%)。AWGN を実ノイズに替えても実打鍵には転移しなかった。

**(E) 実信号 FT** — **プロジェクトで初めて実信号と合成の両指標が同じ向きに改善した施策。**
synth 実効 0 dB も 85.43% → 77.88% (−7.55pt) と改善している。
2,000 step 以降で悪化するのはデータ量が原因 (90 件を 355 エポック相当なめる)。

**(F) 手打ち分布 FT** — 当初は「手打ち分布が悪い」と結論しかけたが、
**対照群 (`--no-hand-keying` だけを変えた条件) を足したら同じだけ悪化した。**
悪かったのは分布ではなく **FT レシピ** (すでに FT 済みの `ft_1k` からさらに同じ 90 件で
1,000 step 追加 = 過学習) だった。ただし synth_val は対照群が横ばい・手打ちアームだけ
悪化したので、synth 側の不合格は交絡なしに確定している。

**(G) 手打ち分布フル学習** — (F) で FT の露出が土台の 0.15% しかないと分かったので、
**露出 100%** で測り直した。結果は実打鍵 TER が 2 倍以上 (25.95% → 52.35%)。
**露出 100% でも悪化したので言い訳の余地がない。** 既定を従来分布へ戻した。

## 5. 再学習なしで得た改善 (推論側)

学習と同じくらい、ここのパラメータが実効の認識率を決めている。

| 日付 | 施策 | 効果 | 採否 |
|---|---|---|---|
| 2026-07-31 | WORD_BREAK 閾値掃引 | keyed −4.03pt だが synth +2.75pt 悪化 | ✗ |
| 2026-08-05 | 周波数まわりの掃引 | 伸びしろなし | ✗ |
| 2026-08-06 | **commit_lag 再測定 (held-out)** | 実効右文脈 **2.25 秒**が最良。3.0 秒より速く精度も良い | ✅ |
| 2026-08-12 | **2 段階確定** | held-out TER 27.4% → **25.1%** | ✅ |
| 2026-08-12 | **辞書補正 (欧文)** | held-out 欧文 CER 19.25% → **17.15%** (−2.09pt) | ✅ |
| 2026-08-14 | **辞書補正 (和文)** | 符号列距離ベース、語彙 405 語。実受信で安全な直しのみ | ✅ |
| 2026-08-14 | 読めない文字の確定猶予 1.5 秒 | TER −2.01pt (和文 −3.84pt) | ✅ |

現在の推論設定 (認識率に効くもの):

| 項目 | 値 | 根拠 |
|---|---|---|
| デコードデバイス | **CPU 4 スレッド** | CPU 112 ms < CUDA 139 ms (モデルが小さく GPU 起動費用が勝つ) |
| hop / commit_lag | 0.5 秒 / 2.0 秒 | 実効右文脈 = lag + hop/2 = **2.25 秒** |
| 左文脈 | 5.0 秒 | 確定済みは再計算しない (RTF 0.07) |
| 2 段階確定 | 有効 (デスクトップ版のみ) | ターン終了時に全文脈で再デコード |
| 確信度閾値 | 0.5 | 0.0 に下げると CER 19.74% → 23.64% と**悪化** |
| 改行ギャップ | 3.0 秒 | ターンの切れ目 |

### 6.4 人間の耳という上限 (2026-08-14)

実受信の和文 1 件について、運用者が耳で読んだ結果と比較できた。

| 比較 | CER |
|---|---:|
| モデル → 推測原文 | 34.92% |
| **運用者の耳 → 推測原文** | **28.57%** |
| モデル ↔ 運用者の耳 | 25.68% |

**熟練者が耳で読んでも 28.57% 間違えている。** 差は 6.35pt しかなく、
両者の差 (25.68%) はそれぞれの原文との差より小さい =
**モデルと人間は同じ箇所を同じように読み違えている**。
人間が実用的に読めているのは**文脈から語を推測して直しているから**である。

したがって足りないのは**要素の読み取り精度ではなく語の推測**であり、
和文の文脈補正が最優先になる。

## 7. この履歴から読み取れること

1. **合成側をいじると実信号が落ち、実信号側を上げると合成が落ちる**という逆相関が
   3 回繰り返し観測された (A, B〜D, G)。
2. **唯一の例外が実信号 FT (E)** で、これだけが両方を改善した。
   → **ラベル付き実録音を増やすことが最も確度の高い投資**。
3. 合成分布を広げる方向 (低 SNR 拡張・手打ちジッタ拡張) は**すべて失敗している**。
   分布を広げると実信号に転移しない手掛かりを覚える。
4. その理由が 2026-08-14 に判明した。**測れる統計量 (速度・長短比・間隔・ジッタ・SNR) を
   実測どおりに合成しても TER 3%、同じ統計量を持つ実録音は TER 30%。**
   合成器は実信号の難所を含んでいない。**合成分布をこれ以上いじっても改善しない。**
5. デコード側 (確定戦略・辞書補正) の改善は**低コストで確実に効く**。
   2 段階確定と辞書補正で合わせて 4pt 以上を再学習なしに得た。
6. 律速はラベル付き実録音の量である。学習に使えるのは 90 件 24.8 分、held-out は 21 件
   (和文は 208 トークン) しかない。しかも **90 件はすべて自局の打鍵**で、
   打鍵者の多様性が学習分布に入っていない。

## 9. 実験の原則 (踏んだ穴から)

1. **対照群を置く。** 「手打ち分布が悪い」と結論しかけたが、対照群も同じだけ悪化した。
   悪かったのは分布ではなく FT レシピだった
2. **評価は held-out に正解ラベルで当てる。** 代理指標 (オフライン一括デコードとの
   一致率) で測った掃引は結論が逆だった。一致率は正しさではない
3. **測る対象そのものの正しさを先に確認する。** ラベル汚染 19 トークンで
   baseline を 2.6pt 誤っていた。**原稿はラベルではない**
4. **参照表を書くときは実装を見ない。** 段落の誤記は参照表も同じ間違いをしていたので
   照合テストが 2 か月素通りした
5. **掃引の形が変なときは実装のバグを疑う。** 「余白を増やすほど悪くなる」という
   逆向きの結果が、実際には書き直しを諦める分岐のバグだった
6. **仮説は合成で再現して確かめてから対策する。** 合成器は仮説を数分で否定できる道具。
   学習を回す前に必ず通すこと
7. **「異常」と決める前に平常値を測る。** 問題の録音の誤り率は held-out 和文の
   31.73% とほぼ同じで、異常な録音ではなかった
8. **人間の耳と比べる。** 上限を知らずに改善目標を立てると、達成不可能な数字を追って
   データや分布をいじり続けることになる
9. **`?` を消しても精度は上がらない。** 確信度閾値を下げると CER は悪化する。
   減らしたいなら表示層でやる
10. **`--num-workers 0` (FT 時)。** Windows で Ctrl+C すると worker が孤児化して
    RAM を握り続ける
11. **`--steps` は絶対値。** resume すると step が復元されるので `base + N` を渡す
