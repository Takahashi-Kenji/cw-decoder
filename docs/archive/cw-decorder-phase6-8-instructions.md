## 1. 解決すべき課題と対応の全体像

| design.md の課題 | 根本原因 | 対応 Phase |
|---|---|---|
| §5.4/5.5 ストリーミング精度がオフラインに劣る | チャンク切断による文脈損失。「切って捨てる」方式が原因 | **Phase 6**: スライディングウィンドウ再デコード + prefix commit |
| §5.2 実音声 TER 約30%、系統誤り (末尾dot消失・先頭欠落) | 合成データと実音声のギャップ (ノイズテクスチャ、AGC挙動、打鍵癖、フィルタ経路不一致) | **Phase 7**: 合成器刷新 + 特徴量正規化 + ゼロから再学習 |
| §5.7 WORD_BREAK 過剰検出 | 学習データの語間が 7 dot 固定 | **Phase 7**: 語間分布拡大 |
| §5.8 AGC ランプアップ不安定 / §5.10 BPF×AGC 相互作用 | 時間領域 AGC がデコード経路に存在すること自体 | **Phase 7**: AGC をデコード経路から排除、スペクトログラム正規化に置換 |
| §5.3 短符号 (E/T等) 不安定 | 帯域内ノイズ片と dot の競合 | **Phase 7** (実ノイズ学習) + **Phase 8** (FT) で改善 |
| §5.2 残存する系統誤り | 送信局個別の打鍵癖・実伝搬 | **Phase 8**: 実信号ファインチューニング |
| §5.6 設定の永続化 | settings.json のマイグレーション欠如 | **Phase 6** に同梱 (小規模) |

### 設計上の重要な確認事項 (議論済み・変更しないこと)

1. **三層分離 (音→符号→文字) は維持**する。
2. **ナロー BPF は正義** — SNR を直接改善するため、廃止・緩和しない。問題は「学習時と推論時のフィルタ経路の不一致」であり、Phase 7 でコード共有により解消する。
3. **再学習はゼロから** (warm start しない)。入力特徴量の正規化変更により入力分布が根本的に変わるため。Phase 8 の実信号 FT のみ追加学習とする。

## 2. Phase 6: ストリーミング推論の再設計 (モデル無改修)

### 2.1 背景と方針

実測値 (design.md §8.2) より、6 秒チャンクの推論は GPU 50ms / CPU 200ms 程度。**30 秒バッファの全体デコードを毎秒実行しても実時間係数 0.1 以下**であり、「ストリーミング (低精度) vs 全体デコード (高精度)」の二者択一は不要。オフラインデコードを繰り返し実行し、文脈が確定した部分だけを表示確定する方式に置き換える。

これにより design.md §5.4/§5.5 の文脈損失問題は構造的に消滅する (各トークンは必ず前後数秒の文脈を持った状態でデコードされた結果のみが確定するため)。

### 2.2 アルゴリズム仕様: スライディングウィンドウ再デコード + prefix commit

```
定数 (settings.json で調整可能、括弧内デフォルト):
  WINDOW_S      = 解析窓長            (30.0 秒)
  HOP_S         = 再デコード周期       (1.0 秒)
  COMMIT_LAG_S  = 確定遅延            (2.5 秒)
  HEAD_GUARD_S  = 窓先頭の不採用区間   (1.0 秒)

状態:
  ring_buffer   : 直近 WINDOW_S 秒の音声 (BPF 通過後 8kHz)
  committed     : 確定済みトークン列 (各要素: token_id, 確信度, 絶対時刻)
  last_commit_t : 確定済み末尾の絶対時刻

HOP_S ごとに実行:
  1. audio = ring_buffer 全体
  2. result = engine.decode_chunk(audio)   # FrameToken 列 (フレーム位置付き) — 既存実装を流用
  3. 各 FrameToken のフレーム位置を絶対時刻に変換
  4. 採用区間の決定:
       t_head = 窓先頭時刻 + HEAD_GUARD_S          # 窓先頭は左文脈がないため不採用
       t_commit_limit = 現在時刻 - COMMIT_LAG_S     # 末尾 COMMIT_LAG_S は文脈不足のため未確定
  5. result のうち [max(t_head, last_commit_t), t_commit_limit) の区間のトークンを「確定候補」とする
  6. 確定候補と committed 末尾を突き合わせ (絶対時刻 ± 許容幅でマッチング)、
     新規分のみ committed に追加 → UI に「確定」として emit
  7. result のうち t_commit_limit 以降のトークンは「暫定」として UI に emit
     (UI はグレー表示し、次回 HOP で置き換える)
```

実装上の注意:

- `StreamingDecoder` の既存オーバーラップマージは本方式に置き換える。旧ロジックは削除してよいが、テストは新仕様に書き換えて同数以上を維持すること。
- ring_buffer が WINDOW_S 未満 (起動直後) の間は、ある分だけでデコードする。HEAD_GUARD_S は録音開始時刻より前には適用しない (起動直後の信号を捨てない — design.md §4.4 の「先頭無音待ち廃止」の教訓を踏襲)。
- トークンマッチング (手順 6) は絶対時刻ベースとし、許容幅はデフォルト ±0.3 秒。同時刻に異なるトークンが来た場合は新しいデコード結果を優先しない — **確定済みは不変** (immutable)。これが「表示がちらつかない」ことの保証になる。
- 無音区間 (スキッシュ閾値ベース、既存実装) が WINDOW_S の大半を占める場合は再デコードをスキップして CPU を節約する。
- WORD_BREAK トークンの表示は確定区間でのみ反映する。
- 既存の「手動全体デコード」「自動チャンク」モードは検証用に残すが、UI のデフォルトは本方式 (名称例:「ライブ (連続)」) とする。

### 2.3 UI 変更

- デコードテキスト表示を「確定 (黒)」+「暫定 (グレー)」の 2 領域構成にする。暫定部分は HOP ごとに置換される。
- ステータスバーに `window=Xs hop=Ys lag=Zs decode=Nms` の診断情報を追加。

### 2.4 同梱する小規模修正: settings.json マイグレーション

- `AppSettings` に `settings_version: int` フィールドを追加 (現行を version 1 とし、本改修で 2)。
- 読込時: 保存値に存在しないフィールドはコードのデフォルトで補完し、`settings_version` が古い場合は既知の旧デフォルト値 (例: `chunk_duration_s == 1.5`) を新デフォルトに置換するマイグレーション表を適用。適用結果はログに出力。
- マイグレーションの単体テストを追加 (旧 version の JSON → 新フィールド補完を検証)。

### 2.5 Phase 6 受け入れ基準

| 項目 | 基準 |
|---|---|
| 精度 | 80 秒実録音 QSO (`data/real/` の既存 4 件) で、確定トークン列がオフライン全体デコード結果と **95% 以上一致** |
| 遅延 | トークンの音声上の終了時刻から確定表示まで **HOP_S + COMMIT_LAG_S + 推論時間以内** (デフォルト設定で約 3.5〜4 秒)。設定で 2 秒台まで詰められること |
| 負荷 | CPU 推論で実時間係数 0.2 以下 (30 秒窓・1 秒 hop) |
| 安定性 | 確定済みテキストが後から変化しないこと (テストで保証) |
| 回帰 | 既存テストすべてパス + 新規テスト (prefix commit のマッチング、窓端処理、マイグレーション) |

## 3. Phase 7: 合成器刷新 + 特徴量正規化 + ゼロから再学習

### 3.1 背景と方針

実音声の系統誤り (D↔B、9→O の末尾 dot 消失、N→E・I→E の先頭欠落) は、合成データと実音声の**包絡線・ノイズテクスチャの不一致**の指紋である。対策は (a) 実ノイズの導入、(b) 学習/推論の信号経路統一、(c) AGC のデコード経路からの排除、(d) 打鍵・語間分布の写実化。これらは入力分布を変えるため、**既存モデルへの追加学習ではなくゼロから再学習**する (一晩で完了する規模)。

### 3.2 WP7-1: 実バンドノイズ重畳 (最重要)

**目的**: AWGN を実 7MHz バンドノイズに置き換え/混合し、空電・ハム・受信機ノイズフロアの実テクスチャを学習させる。

実装:

- `data/noise/` ディレクトリを新設し、ユーザーが録音した無信号バンドノイズ WAV (8kHz、長時間) を配置する規約とする。
- `src/synth/noise.py` に `RealNoiseBank` を追加:
  - 起動時に `data/noise/*.wav` をインデックス化 (メモリに全ロードしない。memmap またはランダムシーク読出し)
  - サンプル生成時にランダム位置から必要長を切り出し、ランダムゲインで合成 CW に重畳。目標 SNR は既存と同じ -10〜+20 dB の指定方法を踏襲 (ノイズ実効値を測定してスケーリング)
- 混合比率を設定可能にする: `real_noise_prob` (デフォルト 0.7 — 70% のサンプルは実ノイズ、30% は従来の AWGN+QRN 合成ノイズ。実ノイズが無い環境でも学習が回るよう、`data/noise/` が空なら自動で従来方式 100% にフォールバックし警告を出す)
- 実ノイズ使用時も QRM (混信 CW) の重畳は従来通り行う。

**ユーザー側の作業 (Claude Code の作業ではない、README に明記すること)**: 実運用と同じ受信機設定 (ナローフィルタ・AGC 設定込み) で無信号周波数を数時間録音し `data/noise/` に置く。複数の時間帯・コンディションで録ると分布が広がり望ましい。

### 3.3 WP7-2: フィルタ経路の学習/推論統一

**目的**: 推論アプリの BPF と合成器の BPF が別実装・別パラメータ分布である不一致を解消する。

実装:

- BPF 実装を `src/dsp/bandpass.py` (新設) に一本化し、`src/infer/audio.py` と `src/synth/noise.py` の両方がこれを import する。実装は現行の推論側 (バターワース 4 次 SOS、ステートフル) を正とする。
- 合成器の最終段 (ノイズ重畳後) に、このフィルタを推論時と同じ設定分布で適用する: 中心 600 Hz を中心に ±100 Hz、帯域 200〜500 Hz をランダム。完全固定にしないこと (運用時の設定変更への頑健性のため)。
- 注意: WP7-1 の実ノイズは受信機フィルタを既に通った音である。実ノイズ使用サンプルではアプリ側 BPF 相当の 1 段のみ追加適用し、二重に狭めすぎない (合成 CW トーン側にも同一フィルタを通してから重畳する)。

### 3.4 WP7-3: AGC のデコード経路からの排除 + 特徴量正規化

**目的**: design.md §5.8 (AGC ランプアップ) と §5.10 (BPF×AGC 相互作用) を構造的に消す。

実装:

- **推論側**: デコードに渡す音声経路から時間領域 AGC を外す。AGC はレベルメータ表示・録音用途にのみ残す (UI の AGC トグルの意味を「表示用」に変更)。
- **特徴量**: メルスペクトログラム算出を log-mel に統一し、**ウィンドウ (デコード単位) ごとの平均・分散正規化**を学習・推論共通の前処理として実装する。実装は `src/dsp/features.py` (新設) に一本化し、学習 (`src/train/`) と推論 (`src/infer/engine.py`) の両方がこれを使う。
- **学習側**: 合成サンプルにランダムゲイン拡張を追加 (ピークレベル -30〜0 dBFS を一様分布)。レベル不変性をモデル自体に学習させる。
- ストリーミング推論 (Phase 6 の 30 秒窓) では窓全体で正規化する。窓内に強信号と無音が混在しても破綻しないことをテストで確認すること (無音のみの窓で分散ゼロ割りを起こさないよう ε を入れる)。

### 3.5 WP7-4: キーイング・語間分布の写実化

実装 (`src/synth/keying.py`, `src/synth/text_generator.py`):

1. **語間ギャップ分布の拡大**: 7 dot 固定 → **4〜15 dot の分布** (対数正規またはガンマ分布、中央値 7)。§5.7 WORD_BREAK 過剰検出の根本対策。
2. **文字間ギャップ**も 3 dot 固定なら 2〜6 dot の分布に拡大。
3. **非対称打鍵癖モデル**: 送信者単位のパラメータとして「dot 短め/長め」「符号末尾の要素が弱く・短くなる」「文字間が詰まる」係数を導入し、1 サンプル内で一貫した癖として適用 (要素ごとの独立ジッタとは別系統)。
4. **AGC 圧縮模擬** (任意・効果検証付き): 合成信号に簡易 AGC (アタック 10〜50ms、リリース 0.5〜2s) を通すサンプルを一定割合 (30%) 混ぜる。符号列先頭の振幅が相対的に潰れる実受信機挙動を再現する。

### 3.6 WP7-5: ゼロから再学習と検収

手順:

1. 新合成器で固定評価セットを再生成 (`data/eval/v2/`)。**旧評価セット (`data/eval/` 既存) は残す**。
2. ゼロから学習 (構成は現行と同一: CNN3 + BiLSTM2 + CTC、AMP、約 100k step)。チェックポイントに**メタデータを埋め込む**: 合成器バージョン、特徴量設定 (正規化方式・mel パラメータ)、git commit hash、語彙バージョン。`torch.save` の dict に `meta` キーを追加し、推論側はロード時にメタデータと自身の特徴量設定の一致を検証、不一致なら警告。
3. 保存先: `models/v2/best.pt`。`models/full/best.pt` (旧) は不変。

検収 (受け入れ基準):

| 項目 | 基準 |
|---|---|
| 合成評価 (新セット v2) | TER 1% 以下 / SNR 0dB 以上、TER 15% 以下 / SNR -5dB (要件定義 §5 を新評価セットに適用) |
| 旧評価セットでの確認 | 旧セットでも TER 5% 以下 (大幅劣化していないこと) |
| **実音声リグレッション** | `data/real/` 既存 4 件のオフラインデコードで、旧モデル比でトークン一致率が改善していること。新旧並記の比較レポートを `docs/v2_regression.md` に出力するスクリプト (`scripts/compare_models.py`) を作成 |
| WORD_BREAK | 実音声 4 件で WORD_BREAK 過剰検出数が旧モデル比で減少 |
| 学習時間 | RTX 5060 Ti で 10 時間以内 |

### 3.7 Phase 7 実装順序

WP7-2 (フィルタ統一) → WP7-3 (特徴量) → WP7-4 (キーイング) → WP7-1 (実ノイズ、録音データ到着待ちと並行可) → WP7-5 (再学習)。WP7-1 の録音が揃わない場合でも、WP7-2〜4 のみで一度再学習して効果を確認してよい (実ノイズは後から追加して再々学習)。

## 4. Phase 8: 実信号ファインチューニング (Phase 4 基盤の本格運用)

### 4.1 背景と方針

Phase 7 の新ベースモデルに対し、実録音による追加学習で送信局固有の癖・実伝搬への最終適応を行う。**少量データのため過学習防止策を必須とする**。既存の Phase 4 基盤 (`src/finetune/`) を以下の仕様で強化して使う。

### 4.2 仕様

- **データ**: `data/real/*.wav + .txt`。目標 20〜30 件 (current 4 件では本格 FT を実施しない。10 件未満の場合スクリプトは警告を出す)。
- **混合**: `MixedRealSynthDataset` で実データ比率 10〜30% (デフォルト 20%)、残りは新合成器のオンザフライ合成。
- **学習率**: ベース学習の 1/10 (3e-5)。
- **凍結**: CNN 層は凍結し、BiLSTM + Linear のみ更新 (`--freeze-cnn` をデフォルト ON)。
- **忘却監視**: FT 中も合成評価セット v2 で定期評価し、TER が 2 倍以上悪化したら早期停止。
- **保存**: `models/ft/` 配下にベースモデルのメタデータを引き継いで保存。

### 4.3 受け入れ基準

- 実音声評価 (FT に使っていないホールドアウト録音 ≥ 3 件) でトークン一致率がベースモデル比で改善。
- 合成評価セット v2 の TER 劣化が 2 倍以内 (破滅的忘却なし)。

## 5. スコープ外 (本改修では実施しない)

以下は本改修の効果測定後に別途判断する。実装しないこと:

- beam search + 言語モデル (コールサイン辞書・文字 n-gram) によるリスコアリング
- ホレ/ラタによる欧文/和文自動切替
- 単方向 LSTM / ストリーミング特化アーキテクチャへの変更 (Phase 6 の prefix commit で不要になる見込みのため)
- ONNX エクスポート、PyInstaller 配布、Raspberry Pi 移植

## 6. 全体スケジュールと依存関係

```
Phase 6 (推論再設計 + settings移行)     : モデル無改修。最初に実施、即日効果
   │  ← Phase 6 完了後、新方式で実録音の収集を継続 (Phase 8 のデータが貯まる)
   ▼
Phase 7 (合成器刷新 + 正規化 + 再学習)  : WP7-2/3/4 実装 → 再学習(一晩) → 検収
   │     ※ WP7-1 実ノイズはユーザー録音の到着次第で組込み、必要なら再々学習
   ▼
Phase 8 (実信号 FT)                    : 実録音 20 件以上が貯まった時点で実施
```

注意: Phase 7 完了後、Phase 6 のストリーミングは新モデル (`models/v2/best.pt`) に切り替えて再検証すること。特徴量正規化の変更により `InferenceEngine` の前処理も `src/dsp/features.py` 経由に変わっている必要がある (WP7-3 で対応済みのはず — チェックリストに含めること)。
