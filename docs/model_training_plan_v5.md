# モデル学習計画 v5

作成日: 2026-08-27
前提: [モデルと学習結果のまとめ](./models_and_results.md) — この文書の全数値はそこから引く。
前計画 [v4](./model_training_plan_v4.md) は P4 (フル再学習) が 2 回とも失敗して終わった。

---

## 出発点 — 実測が示した 3 つの事実

**1. 短い FT は 3 回とも成功し、実データを土台から混ぜるフル学習は 2 回とも失敗した。**

| 手法 | 結果 |
|---|---|
| FT 1,000 step (25 分) | baseline / wabun / ft_v5_wide — すべて成功 |
| フル学習 102,000 step (13 時間) | full_v4a 44.42% / full_v5 34.12% — 合成のみの旧土台 23.18% にすら負けた |

**2. 中立な評価集合は存在しない。** 4 つの集合は動作点が違い、どれもどれかのモデルの地元である。
運用者の実受信で最良だった `wabun` を、held-out は「baseline より悪い」と評価した。

**3. 運用者の実受信での判断が、どの数値より正確だった。**

v4 は「和文 15%」という単一の目標に向けてフル学習を積む計画だった。
**v5 はそれをやめる。** 目標を「複数の動作点それぞれで強いモデルを、短い FT で作り、
切り替えて使う」に置き換える。運用者が示した方向 (2026-08-27) である。

---

## 目標

**動作点ごとに最適なモデルを持ち、受信音に応じて選ぶ。**

| 動作点 | 代表する集合 | 現状の最良 | 目標 |
|---|---|---|---|
| **弱信号・実交信** | L4 8/24 (5W, 11.7 dB) | wabun 0.53% | 維持しつつ裾野を広げる |
| 強信号・機械打鍵 | L4 8/25 (50W, 22.5 dB) | full_v5 0.06% | 十分。手を付けない |
| 自局の打鍵環境 | held-out (28.8 WPM, 文字間 4.38) | ft_v5_wide 17.38% | 和文 15% |
| **未知の相手局** | (集合が無い) | — | **評価集合を作ることが先** |

数値目標は動作点ごとに置く。「全体で何 %」は置かない (集合が中立でないので意味を持たない)。

---

## 掟 (v4 から引き継ぎ、実測で裏付いたもの)

1. **1 本の run で変えるのは 1 点だけ。** full_v4a → full_v5 で 2 点同時に変えて帰属を失った
2. **起点と全コマンドを `meta.json` に残す。** 系統は記録で追う。**重みの距離で判断しない**
   (FT は 1,000 step で大きく動くので、近さは起点を示さない。実際に誤った)
3. **val は学習データと違う源から取る。** 同じセッションの val は 26 倍外した
4. **判定は複数の集合で行い、最後は運用者の実受信で決める**
5. **フル学習は原則やらない。** やるなら「なぜ FT では届かないか」を先に示す

## P2 — `wabun` の裾野を広げる (1 日・FT 3 本) 【本命】

**`wabun` のレシピは実受信で証明済み。** そこに 2026-08-27 に見つけた 2 つの穴
(合成の文字間が 3.0 固定 / 先頭無音が 0.3 秒まで) を塞ぐ。

### 起点と共通条件 (wabun と完全に同一)

```
finetune.py --resume models/full/best.pt --data-dir data/ft/combined_ja \
  --steps 1000 --lr 5e-5 --batch-size 16 --mix-synth --real-ratio 0.5 \
  --tone-center 500 --tone-span 60 --num-workers 0 --seed 42
```

### 3 本 (各 25 分。変えるのは 1 点ずつ)

| run | wabun からの差分 | 仮説 |
|---|---|---|
| **P2-a** | `--char-space 2.6 5.0` | 文字間の裾野が広がり held-out が改善、L4 は維持 |
| **P2-b** | `--pre-silence 0.0 2.5` | 先頭幻覚 (baseline で 24 個) が消える |
| **P2-c** | a + b + `--intra-space 1.0 1.5` | 両方の効果が足し合わさる |

### 判定 (3 集合すべてで見る)

| 集合 | 合格 |
|---|---|
| L4 8/24 凍結 45 件 | **wabun の 0.53% から +1pt 以内** (弱信号の強さを失わない) |
| held-out | wabun の 21.24% より改善 |
| 先頭誤り | baseline の 24 個から半減 |

**3 集合の 1 つでも大きく崩れたら不採用。** 動作点を移しただけのモデルは要らない。

合格したものは **ONNX 化して運用者の実受信で `wabun` と比べてもらう**。
**最終判定は実受信である。**

### `data/ft/combined_ja` について

旧録音 90 件を含む (2026-08-27 の「旧録音は使わない」方針と食い違う)。
**wabun が成功した最大の要因がこの 90 件である証拠が出た** (外した full_v4a/v5 は
2 本とも失敗) ので、P2 では含めたまま回す。**外すかどうかは P2 の結果を見て運用者が決める。**

## P3 — 動作点の自動判別 (1 日・学習なし) 【完了 2026-08-27】

> **結果**: `src/infer/operating_point.py` + `scripts/measure_operating_points.py`。
> モデル選択に効く 2 軸 (文字間・コントラスト) で 3 動作点を
> **98.8%** で振り分けられた (弱・狭 99.5% / 強・狭 98.3% / 強・広 95.0%)。合格。
>
> **目標を「どの集合か」から「どの動作点か」に改めた。** L4 は意図的に 15〜30 WPM を
> 混ぜているので WPM で集合は当てられない。旧録音と L4 5W は同じ動作点
> (文字間 ~3.3・9 dB) で、分ける必要がない (wabun が両方で学習して成功した)。
>
> 測定器は 3 回作り直した (`git log` の P3 コミット参照)。**閾値の高さはそのまま
> 間隔の測定を歪める** — 弱信号用の低い閾値を全部に掛けると held-out の文字間が
> 4.41 → 3.05 に潰れた。コントラスト 12 dB で経路を分けるのが落ち着き先。

運用者の構想「モデルを切り替えて最適なものを選ぶ」の前提。
**受信音から動作点を測れなければ、手で切り替えるしかない。**

| # | やること |
|---|---|
| 1 | `src/infer/wpm.py` の包絡線解析で **WPM・文字間 (dot 比)・コントラスト (dB)** を出す関数を作る (解析コードは `scripts/analyze_keying.py` にある) |
| 2 | 4 集合 (計 1,400 件) に掛けて、**集合ごとに分離できるか**を測る。分離できなければ P4 は成立しない |
| 3 | 分離できたら、閾値をアプリの設定に置く (自動切替は P4 で) |

判定: 4 集合を **90% 以上正しく振り分けられる**こと。

## P4 — モデルの切り替え運用 (2 日) 【1〜3 実装完了 2026-08-28, `968e6a4` `63afe53` `138f26f`】

> 1: 「読込…」の隣にコンボボックス。登録モデル (`DEFAULT_MODEL_FOR_CLASS` のうち実在
> するもの) を「wabun — 弱信号・狭い間隔」の形で並べ、同じ経路で差し替える。
> 2: ステータスバーに「文字間 3.3 / 9 dB → 弱信号・狭い間隔 (wabun)」。境界に近ければ ?。
> 3: `logs/model_choice.jsonl` に選択と推奨を記録。`choice_log.agreement()` で一致率。
> **残るのは運用者が実交信で使って記録を溜めること。** 自動切替はその後。

P2 で「弱信号に強いモデル」、既存で「自局環境に強いモデル」(ft_v5_wide) がある前提。

| # | やること |
|---|---|
| 1 | アプリに **モデルの一覧と手動切替** (今は「モデルの選択」ダイアログで 1 つずつ) |
| 2 | P3 の判別器で **推奨モデルを表示** (自動切替はしない。運用者が選ぶ) |
| 3 | 実交信で運用者が使い、**どの動作点でどのモデルを選んだか**を記録する |

自動切替は、3 の記録が溜まって「判別器の推奨と運用者の選択が一致する」と分かってから。

## やらないこと

| やらない | 理由 (実測) |
|---|---|
| 実データを土台から混ぜるフル学習 | 2 回とも失敗。合成のみの旧土台にすら負けた |
| held-out 単独での採否判定 | wabun を「baseline より悪い」と評価した。実受信では最良 |
| 学習中の val を当てにすること | 26 倍外した |
| 助走のオーグメンテーション | 8/24 の欠陥救済以外では悪化する |
| 語彙の拡張 (「」) | 全モデルの作り直しになる。切替運用が固まってから |

## 順序と所要

```
P1 評価の土台    1 日    学習なし
P2 wabun の裾野  1 日    FT 3 本 (計 75 分) + 実受信での確認
P3 動作点の判別  1 日    学習なし
P4 切替運用      2 日    アプリ改修 + 実交信での記録
P5 収集の改修    (運用者の判断待ち)
```

**P1 と P3 は GPU を使わないので、P2 の FT と並行できる。**
最初の 2 日で「wabun より良い弱信号モデル」と「動作点の判別」が揃う見込み。
