# WORD_BREAK の下駄 (wordBreakBias)

作成日: 2026-08-07
対象: ブラウザ版 (`web/src/decode/ctc.ts` の `ctcGreedyDecodeWithFrames`)
既定値: **0 (従来どおり。何もしない)**

---

## 何のためのものか

実運用で「文字は取れているのに語がくっついて読めない」という報告があった。

```
TNX1STQSOHPECUAGN GBGL+JA9UKKDEJN3CEL73TUEE BK OK TNX1STQSO
```

原因はモデルの `WORD_BREAK` トークンの recall が **57〜69%** しかないこと。
語間の 3〜4 割が構造的に落ちる。全トークン中で最大の誤り源でもある。

`wordBreakBias` は CTC の貪欲デコードで **WORD_BREAK のロジットにだけ足す下駄**。
正にすると語間が出やすくなる。`?wb=<数値>` で指定する。

## 先に潰した代案 (どれも悪化した)

held-out 実録音 21 件、**スペースを含めた CER**:

| 語間の出どころ | CER | 差 |
|---|---|---|
| **モデルの WORD_BREAK (現行)** | **29.87%** | — |
| フレームギャップ (`convert_timed`) | 34.63% | +4.76pt |
| 音声エンベロープ (`detect_word_breaks_from_audio`) | 38.53% | +8.66pt |

音声由来のものは `559` を `5 5 9` に割るなど余計なスペースを撒く。

**トークンの時刻差は語間の判定に使えない。** CTC の貪欲デコードが返す
`frame_start`/`frame_end` はピーク位置でほぼ幅ゼロ (0〜20 ms) であり、符号の実際の
長さを持たない。したがって測れるのは「ピーク間距離」で、文字自身の長さを含む。
語間 (7 dot ≒ 0.4 秒) は文字の長さに埋もれる (実測で全文字間にスペースが入った)。
改行 (3 秒) には使えるが語間には使えない。

## 下駄の実測 (held-out 実録音 21 件)

| bias | 文字だけの CER | スペース込み CER | スペース数 (正解 77) |
|---|---|---|---|
| -1.0 | 19.74% | 29.00% | 97 |
| **0.0 (既定)** | **19.74%** | **29.87%** | 101 |
| 1.0 | 19.48% | 30.74% | 106 |
| 2.0 | 18.70% | 31.39% | 114 |
| 3.0 | 12.99% | 27.71% | 121 |
| 4.0 | 9.35% | 24.24% | 121 |

**効き方は当初の想定と違った。** 「WORD_BREAK は文字と別トークンだから文字は変わらない」
と考えていたが、実際には**モデルが余計に出すプロサインが押さえられる**経路で文字の
CER が動く。

```
正解  : QRT TNX QSO 73
wb=0  : CQRT TNX QSO 73 [SK]   ← 末尾に余計な [SK]
wb=3  : CQRT TNX QSO 73        ← 消えた
```

`[SK]` は表示上 4 文字なので、これが消えると CER が大きく動く。
(keyed_val のラベルは「実際に打鍵していないプロサインを除去」してあるので、
モデルが出す `[SK]` は本当に偽の挿入である)

## なぜ既定を 0 のままにしたか

**手元の held-out 録音と実運用で、スペースの過不足が逆を向いている。**

- 手元の録音: スペースが**出すぎ** (101 個 / 正解 77 個)
- 実運用の報告: スペースが**足りない**

手元の録音は短い定型文で語間がはっきりしているのに対し、実際の交信は速くて語間が
詰まっているためと思われる。**この数値から既定値を決めるのは危険**なので、
調整口だけ設けて既定は 0 (従来どおり) にしてある。

## 使い方

```
http://localhost:5173/?wb=3      ← 語間を出やすくする
http://localhost:5173/?wb=-1     ← 語間を抑える
http://localhost:5173/           ← 既定 (0、従来どおり)
```

画面下の診断行に `wb 3` と出るので、どの値で出た結果かを取り違えない。

**実信号で試して決めること。** 良い値が分かったら `resolveWordBreakBias()` の
既定値を変えるか、この文書に記録を残すこと。

# 付録: ノイズをデコードする問題とスキッシュ

作成日: 2026-08-07

## 現象

信号が無い状態でも符号が出続ける。実測 (30 秒の入力):

| 入力 | レベル | 出たトークン | 確信度の中央値 | 閾値 0.5 超 |
|---|---|---|---|---|
| 完全な無音 (ゼロ) | — | **0** | — | 0 |
| 極小ノイズ | −80 dBFS | **38** | 0.68 | 35 |
| 白色ノイズ | −40 dBFS | 35 | 0.60 | 27 |
| 白色ノイズ | −20 dBFS | 25 | 0.72 | 20 |
| **帯域ノイズ (BPF 後)** | −30 dBFS | **2** | 0.34 | **0** |

出力は `[SN]` `[SK]` といったプロサインが大半。

## 分かったこと

**確信度では防げない。** ノイズ由来のトークンの確信度は 0.6〜0.72 と高く、
閾値 0.5 を超える。「自信が無いから ?」にはならない。

**音量はほぼ無関係。** −80 dBFS のノイズでも 38 個出る。メル特徴抽出が
サンプル内で z-score 正規化する (`MelConfig.normalize`) ため**音量の情報が
捨てられ**、小さいノイズが増幅されて信号のように見える。
AGC を削除した理由 (正規化があるので冗長) と同じ仕組みが裏目に出た形。

**BPF は非常によく効く。** 同じ −20 dBFS でも BPF 後は 25 個 → 2 個、
確信度 0.34 で閾値以下。**BPF を常時 ON にする運用は正しい。**

## 対処: スキッシュ (`?squelch=<dBFS>`)

デコーダの手前でレベルを見て、下回る間は**無音を流し込む**
(ブロックを捨てない。捨てると時間軸が止まり確定タイミングと改行判定が壊れる)。

効果 (ノイズ 15 秒 → 信号 → ノイズ 15 秒、ノイズ −34 dBFS / 信号 −6 dBFS):

```
正解          : CQ DE JA1ABC K
スキッシュ無し : [SK] / [SN][SN][SK][SN][SN]BNOK / EJA1ABCKK / 3[SN][SN][SN]
?squelch=-25  : DEJA1ABCK
```

**既定は −25 dBFS** (2026-08-07、運用者が実信号で確認した値)。実運用でスペースが
出なかった原因も、精度が上がらなかった原因も、どちらもノイズのデコードだった。

判定は **BPF 通過後**のレベルで行う。生の入力レベルは無信号時 −28 dBFS、信号時
−40〜−10 dBFS と**範囲が重なっていて分離できない**。ノイズの大半は帯域外なので
BPF 後なら差が開く。画面のレベル表示に `(BPF後 -45.2)` と併記してあるので、
それを見て閾値を決める。

**ノイズは状況で変わるので、値は運用中に変えられるようにしてある。**

| | 操作 | 保存先 |
|---|---|---|
| デスクトップ | レベルメータ横の縦スライダ (−60〜0 dB) | 設定ファイル |
| ブラウザ | 操作列の「スキッシュ」スライダ (−60〜0 dB、−60 で「切」) | localStorage |

ブラウザ版は初期値だけ `?squelch=<dBFS>` でも指定できる (指定が無ければ前回の
スライダ値、それも無ければ −25)。

**下げすぎるとノイズを拾い、上げすぎると弱い信号が丸ごと落ちる。** 弱い局を
追うときは下げること。

**注意: WAV 入力経路には BPF がかからない**ので、そこで測るレベルは生のレベルである。
録音ファイルで決めた閾値をライブにそのまま移すときは注意すること。
