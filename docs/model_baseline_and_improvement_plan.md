## 1. 現在運用しているモデル

| 項目 | 値 |
|---|---|
| 重み | `models/full/best_infer.pt` |
| 由来 | `models/full/best.pt` (フル学習 102,000 step) + 実信号 FT 1,000 step |
| 採用日 | 2026-08-03 |
| アーキテクチャ | CNN 3 層 + BiLSTM 2 層 + Linear、CTC |
| パラメータ数 | 4.27M (fp32 で約 17 MB) |
| 語彙 | 統合符号トークン 72 個 (blank 含む) |
| ブラウザ版 | 同じ重みを ONNX 化 (`web/`、ORT Web の WASM 実行) |

### 1.1 アーキテクチャの詳細 (`src/train/model.py`)

```
入力: 対数メルスペクトログラム (B, 64, T)
  ↓ Conv2d ×3  ch (32, 32, 64)、周波数方向のみ stride (2, 2, 1)
  ↓ BiLSTM 2 層、hidden 256、dropout 0.1
  ↓ Linear → 72 クラス
出力: (B, T, 72) → CTC
```

**時間次元 T は入力から出力まで保たれる** (CNN は周波数方向しか縮約しない)。
CTC の時間アラインメントを維持するための設計で、時間分解能はそのまま
前処理のメル hop に等しい。

### 1.2 前処理 (`src/train/preprocessing.py`)

| 項目 | 値 |
|---|---|
| サンプルレート | 8 kHz |
| メルビン数 | 64 (50 Hz 〜 4 kHz) |
| 窓長 | 25 ms (200 サンプル) |
| ホップ | **10 ms** ← モデルの時間分解能はここで決まる |
| n_fft | 256 |
| 正規化 | あり (top_db 80) |

**この 10 ms / 25 ms が速い信号の上限を決めている。** §6.2 で詳述する。

### 1.3 「音→符号」と「符号→文字」の分離

NN が出すのは統合符号トークン列だけで、欧文表・和文表への割当は決定論的変換表
(`src/tokens/morse_tokens.py`) が行う。この設計のおかげで、表示仕様の修正
(例: 2026-08-12 の段落 `・-・-・・` = `。` の訂正) は**再学習なしで直せる**。
逆に、**語彙にトークンを足すと ID がずれて学習済みモデルが無意味になる**ので、
トークン追加は再学習と同時にしか行えない (§7.7)。

## 3. 推論側の設定 (認識率に効くもの)

学習と同じくらい、ここのパラメータが実効の認識率を決めている。

| 項目 | 値 | 根拠 |
|---|---|---|
| デコードデバイス | **CPU 4 スレッド** | CPU 112 ms < CUDA 139 ms。モデルが小さく GPU 起動費用が勝つ |
| hop | 0.5 秒 | — |
| commit_lag | 2.0 秒 | 実効右文脈 = lag + hop/2 = **2.25 秒**が最良 |
| 左文脈 | 5.0 秒 | 確定済みは再計算しない (RTF 0.07) |
| 2 段階確定 | 有効 (デスクトップ版のみ) | ターン終了時に全文脈で再デコード。TER 27.4 → 25.1% |
| 確信度閾値 | 0.5 | 0.0 に下げると CER 19.74 → 23.64% と悪化 |
| 辞書補正 | 有効 | held-out 欧文 CER 19.25 → 17.15% |
| 改行ギャップ | 3.0 秒 | ターンの切れ目 |

**CUDA は使っていない (既定 `decode_device="cpu"`)。** これは実測に基づく選択で、
GPU はローカル LLM の清書に空けてある。`"auto"` で CUDA を使うこともできるが遅くなる。
ブラウザ版は ORT Web の WASM (CPU) のみ。

### 5.1 この履歴から読み取れること

1. **合成側をいじると実信号が落ち、実信号側を上げると合成が落ちる**という逆相関が
   3 回繰り返し観測された。両立できない可能性がある。
2. **唯一の例外が実信号 FT** で、これだけが両方を改善した。
   → **ラベル付き実録音を増やすことが最も確度の高い投資**。
3. 合成分布を広げる方向 (低 SNR 拡張・手打ちジッタ拡張) は**すべて失敗している**。
   分布を広げると実信号に転移しない手掛かりを覚える。
4. デコード側 (確定戦略・辞書補正) の改善は**低コストで確実に効く**。
   2 段階確定と辞書補正は合わせて 4pt 以上の改善を再学習なしで得た。
5. 2026-08-14 の診断で 1〜3 の理由が判明した。**測れる統計量を実測どおりに
   合成しても実信号の難しさは再現できない** (3% 対 30%)。合成分布をいじる施策が
   ことごとく失敗したのは、そもそも合成が実信号の難所を含んでいないからである。

## 6. 現在わかっている課題

### 6.1 和文が欧文の 2 倍悪い (最大の課題)

オフライン全文脈でも欧文 15.9% に対し和文 32.6%。原因の候補:

- 和文の符号は長い (最大 6 要素) ので、1 文字あたりの誤り機会が多い
- 和文の文字数が多い (欧文 26 + 数字 に対し、カナ 48 + 濁点半濁点)
- 濁点・半濁点は独立トークンで、変換器側で前カナと合成する 2 段構え
- **辞書補正が和文に効いていない** (`EUROPEAN_LEXICON` は欧文のみ、和文は ±0.00pt)
- 実録音の学習データも欧文 30 : 和文 60 の原稿比だが、実際の打鍵時間比は未確認

**ただし §6.2 の追加測定で、この 31.73% の一部は「モデルが下手」ではなく
「信号が乱れていて人間でも読めない」分であることが分かった。**
熟練者が耳で読んでも 28.57% 間違える録音で、モデルは 34.92% だった。
和文の改善を測るときは、**人間の耳という上限**を意識すること。

### 6.2 「速い和文で文字が抜ける」は速度の問題ではなかった (2026-08-14 調査済み)

運用者から「早い和文を受信すると文字抜けがある」との報告があり、当初は
**(a) 学習 WPM 分布 (8〜50) の端**、**(b) メル窓 25 ms が高速時の短点を分解できない**
という 2 つの仮説を立てた。**録音 1 件を実測した結果、どちらも否定された。**

#### 測定対象

`data/real/20260814_052617_japanese.wav` (62.5 秒、和文、LAN 経由の実受信)

#### 測定 1: キーイングのタイミング (`scripts/analyze_keying.py --split-ms 130`)

| 項目 | 実測 | 教科書 | 学習分布 |
|---|---:|---:|---|
| 短点 | 66.1 ms | — | — |
| 長音 | 198.6 ms | — | — |
| 長短比 | **3.00** | 3.00 | 2.5〜4.0 |
| **実効 WPM** | **18.2** | — | 8〜50 |
| 要素間 | 0.66 dot | 1.0 | 1.0 固定 + σ |
| 文字間 | 2.54 dot | 3.0 | 3.0 固定 + σ |
| 語間 | 5.63 dot | 7.0 | 7.0 固定 + σ |
| 短点 σ | 0.216 dot | — | 0.05〜0.25 |
| 長音 σ | 0.413 dot | — | 0.05〜0.25 |

**実効 WPM 18.2 は速くない。** 学習分布 8〜50 のほぼ中央で、held-out の
`script_ja_01` (24 WPM) より遅い。仮説 (a)(b) はこの時点で成立しない。
特徴的なのは**間隔だけが 66〜80% に詰まっている**ことと、
**長音 σ 0.413 が学習分布の上限 0.25 を超えている**ことだった。

#### 測定 2: 信号品質

トーン 583 Hz、帯域内エネルギー 100%、クリッピング 0%、実効 SNR **13.2 dB**。
held-out の `script_ja_01` (13.2 dB) と同等で、**品質は悪くない**。

#### 測定 3: 対照実験 (合成で実測値を再現)

同一テキスト 8 文を 18.2 WPM / 583 Hz で合成し、要因を 1 つずつ実測値に寄せた。

| 条件 | TER | 差 |
|---|---:|---:|
| 基準 (教科書間隔 + σ0.15 + 20 dB) | 0.51% | (基準) |
| + 実測の間隔 (0.66 / 2.54 / 5.63) | 0.51% | +0.00pt |
| + 実測のジッタ (短点 .216 / 長音 .413) | 1.02% | +0.51pt |
| + 実測の間隔とジッタ | 3.05% | +2.54pt |
| + 実測 SNR 13 dB | 2.54% | +2.03pt |
| + QSB / QRN | 2.54% | +2.03pt |

**実測された特徴をすべて合成で再現しても TER 3% 止まり。** 実録音の誤り
(体感 25〜30%) とは 1 桁違う。間隔の圧縮は単独では**まったく劣化を生まない**。

#### 測定 4: リアルタイム vs オフライン

| 経路 | 出力 |

**ほぼ同一。** 確定戦略・commit_lag・2 段階確定といったストリーミング側の要因ではない。

#### 測定 5: held-out との比較 (`models/full/best_infer.pt`、オフライン)

| モード | TER | トークン数 |
|---|---:|---:|
| 欧文 (`script_eu_01`〜`10`) | 15.90% | 239 |
| **和文 (`script_ja_01`〜`10`)** | **31.73%** | 208 |
| 全体 | 23.27% | 447 |

**この録音の誤り率は、このモデルの和文の実力そのものである。** 異常な録音ではない。

#### 結論

「速い和文で文字が抜ける」の正体は **§6.1 の和文の弱さ**であり、速度・間隔・
ジッタ・SNR・ストリーミングのいずれでもない。そして最も重要なのは次の事実である。

> **実測どおりに合成した和文は TER 3%、同じ統計量を持つ実録音は TER 30%。
> 合成器は「実信号の和文を難しくしている要因」を捉えていない。**

これは過去 3 回の「合成を改善すると実信号が悪化する」という結果と整合する。
測れる統計量 (速度・比率・間隔・ジッタ・SNR) はすべて再現できているのに 10 倍の差が
残る以上、**合成分布をこれ以上いじっても和文は改善しない**と考えるべきである。

| 推測された原文 | ミハサノコチラノテンキハクモリクモリキオンハ22ド22ドデヒンヤリシテマスサクヤハソチラノホウハオオアメデタイヘンダツタデスカ |
| **運用者の耳の読み** | ミホヘサノコチラノ**カヘンキハ**クモリクモリキオンハ22ド22ドデ**ヒンヤヘタヘニカヘマス**サクヤハソチラノホウハオオアメデタイヘン**ダタタヘマスカホヘヘワネ** |
| **モデルの読み** | ササノコチラノ**ムンキニ**クモリクモリ**キンンハ**22ド22ドデ**ヒンヤリモロムマス**サクヤハソチラノホウハンオアメデタイヘン**ダタタヘマカホヘヘワネ** |

| 比較 | CER |
|---|---:|
| モデル → 推測原文 | 34.92% |
| **運用者の耳 → 推測原文** | **28.57%** |
| モデル ↔ 運用者の耳 (両者の差) | 25.68% |

**熟練した運用者が耳で読んでも 28.57% 間違えている。** モデルの 34.92% との差は
6.35pt しかなく、しかも両者の差 (25.68%) はそれぞれの原文との差より小さい。
つまり**モデルと人間は同じ箇所を同じように読み違えている**。
末尾の `ホヘヘワネ` に至っては 1 文字も違わず一致した。

##### 運用者の指摘「短点と長点の長さが少し不自然」の裏付け

| 項目 | 実測 |
|---|---|
| 短点 | 平均 68.8 ms、σ **26.0%**、範囲 **16〜122 ms** |
| 長音 | 平均 201.8 ms、σ 13.1%、範囲 139〜353 ms |
| 速度ドリフト | **無し** (10 秒ごとに 16.7〜18.6 WPM で安定) |
| 分類不能な中間長の要素 | 5 / 313 = 1.6% |

**短点が自分の長さの ±26% も暴れており、16 ms から 122 ms まで 8 倍の幅がある。**
長音の方が (相対的には) 安定しているという、教科書とも手打ちの実測とも違う非対称。
速度自体は安定しているので、これは「速度ドリフト」ではなく**要素ごとの乱れ**である。

#### 結論の訂正

前段の「和文の弱さ」という結論は**半分しか正しくなかった**。正しくは:

> **この録音に関しては、モデルは人間の運用者とほぼ同等に読めている (34.9% 対 28.6%)。**
> 信号そのものが乱れており、素の読み取りではどちらも 3 割前後間違える。
> **人間が実用的に読めているのは、文脈から語を推測して直しているからである。**

したがって、この事例で足りないのは**要素の読み取り精度ではなく、語の推測**である。
§7.4 (和文の文脈補正) の優先度を上げる根拠になる。

### 6.3 ラベル付き実録音が少ない

学習に使えるのは 90 件 24.8 分だけ。held-out は 21 件。
実信号 FT が唯一効いた施策である以上、ここが律速になっている。
1,000 step で頭打ちになるのもデータ量が原因 (90 件を 355 エポック相当なめる)。

### 6.4 評価指標の限界

- `synth_val` は合成データで、実信号の性能と逆に動くことが 3 回あった
- `keyed_val` は 20 件しかない
- 実運用の主観評価が最も実態に近いが定量化できない
- **held-out に正解ラベルで当てることだけが信頼できる**
  (代理指標「オフライン一括デコードとの一致率」で測った掃引は結論が逆だった)

### 6.5 未対応の実装課題

- **2 段階確定がブラウザ版に未移植** (`web/src/decode/render-mode.ts`)。
  デスクトップ版だけ 2.3pt 良い状態
- 30 秒より前に流れたターンは 1 段階のままで書き直されない
- `?` `,` `-` `@` の recall が 0% (打鍵済みの新データ 90 件でも全滅)
- ホレ/ラタが実信号で取れず自動モード切替が働かないことがある

## 7. 今後の改善案 (優先順位つき)

### 7.0 方針 (運用者、2026-08-14)

> **まずは文字通りデコードする。そして、モールス符号の乱れを意識して、
> 意味が通じるように補正する。**

§6.2 の追加測定がこの方針を裏づけている。熟練者が耳で読んでも 28.6% 間違えており、
実用になっているのは**文脈から語を推測して直しているから**である。したがって

- **読み取り層は「聞こえたまま」を出す。**「?」を消したり閾値を下げたりして
  無理に読める形にしない (実測で悪化する)
- **補正は独立した層で行う。** 寄せ先は必ず**符号 (・-) の距離**で選ぶ。
  素の編集距離では「点 1 個の差」という CW の誤りの構造が消える
- この 2 層構造は欧文では既に動いており (`src/infer/word_correct.py`、−2.09pt)、
  **和文に無いだけ**である

この方針は「音→符号」と「符号→文字」を分ける既存のアーキテクチャ原則と同じ形をしている。

### 7.1 【最優先】和文の文脈補正 (符号距離ベース)

現在の `word_correct` は欧文専用で、和文は ±0.00pt (何もしていない)。
§6.2 の測定から、**和文で足りないのは要素の読み取り精度ではなく語の推測**である
ことが分かったので、ここが最大の伸びしろになる。

実装の方針:

- `EUROPEAN_LEXICON` と同じ構造でカナ語彙を作る。定型交換の語
  (コチラハ / テンキ / キオン / ソチラ / アリガトウ / ヨロシク …)、
  地名、無線用語、数字の単位 (ド / ワツト / メガ)
- **寄せ先は符号距離で選ぶ。** 和文は符号長がばらつくので欧文以上に効くはずである
  (例: 今回の `ムンキニ` → `テンキハ` は符号としては近い)
- 歯止めは欧文と同じ: 数字を含む語 (コールサイン・RST)・プロサインは触らない。
  2 位との差 (margin) が無ければ寄せない
- **語彙はここを唯一の真正ソースにする。** `src/llm/prompt.py` の参考語彙も
  これを参照させる (書き写すと必ず食い違う)

和文特有の難所:

- **語の切れ目が曖昧。** 欧文はスペースが語境界だが、和文は文節の切れ目が
  打鍵者によってまちまちで、そもそも WORD_BREAK が正しく出ない
  → 欧文と同じ「語単位で寄せる」が使いにくい。**部分文字列での照合**が要るかもしれない
- **濁点・半濁点が独立トークン。** 補正が濁点を巻き込むと意味が変わる
- 効果が出なければ LLM 清書 (`llm_enabled`、現在は既定オフ) を和文で試す。
  ただし辞書補正はマイクロ秒で終わるので、まず辞書から

**成功条件**: held-out 和文 CER が改善し、欧文が悪化しないこと。
評価は §9 の held-out 20 件で行う。

### 7.2 【高優先】実受信の和文にラベルを付けて学習データにする

合成で再現できる要因はすべて潰しても 3% にしかならず、残りは実信号にしか
含まれていない。そして実信号 FT は唯一「実信号と合成の両方を改善した」施策である。

具体的な手順:

1. **今回の録音 (`20260814_052617_japanese.wav`) のラベルは入手済み** (§6.2)。
   ただし**運用者の推測を含む**ので、学習ラベルに使うか評価ラベルに使うかは
   区別して扱うこと。**推測で補った部分は「実際に送られた符号」とは限らない**
2. 同種の実受信を継続的に録り貯める。**相手局の実際の打鍵**は合成にも
   自分の打鍵にも無い多様性を持つ。現在の学習データ 90 件は**すべて自局の打鍵**で、
   打鍵者の多様性が学習分布に入っていない
3. 前処理は必須: BPF 600/400 Hz + 前後 0.4 秒の無音追加
   (未処理だと TER 97% → BPF で 14.4% → 無音追加で 10.6%)
4. **原稿はラベルではない**。録音後に実際に送られた内容へラベルを合わせる
   (2026-08-03 にラベル汚染 19 トークンで基準値を 2.6pt 誤っていた)

**注意**: 評価用に取り分ける分を先に決めること。今の held-out は 20 件しかなく、
和文は 208 トークンしかない。新しい録音を全部学習に回すと指標が育たない。

### 7.3 【高優先・低コスト】和文の誤りの中身を分類する

§6.2 で「和文が悪い」ことは確定したが、**何をどう間違えているかはまだ見ていない**。
欧文では「誤りの半分は WORD_BREAK の過剰挿入」という分解が打ち手に直結した。
和文でも同じ分解をする。

- 置換 / 脱落 / 挿入の比率 (欧文と同じ偏りか)
- 混同行列 — 特定のカナ対に集中しているか
  (例: 長音を含む符号どうし、濁点の付き外れ)
- 濁点・半濁点の合成が失敗しているのか、カナ本体を外しているのか
- `scripts/finetune.py` は `ft_confusion.json` を出す仕組みを既に持っている。
  評価だけ回して同じものを取れるようにする

**これは 1 時間の作業で、次の一手の精度を大きく上げる。**

### 7.4 【低優先に降格】メル時間分解能の見直し

窓長 25 ms / hop 10 ms を 窓 15 ms / hop 5 ms にする案。

**2026-08-14 の測定で、少なくとも今回の事例の原因ではないことが分かった** ため
優先度を下げた。18.2 WPM (短点 66 ms) では現行の 10 ms hop で 6.6 フレームあり、
分解能はまったく足りている。

理屈の上では 50 WPM 付近 (短点 24 ms < 窓 25 ms) で効くはずだが、
**その速度の実録音をまだ 1 件も持っていない**。実際に 40 WPM 超の録音が
手に入り、そこで誤りが集中することを確認してから着手する。

- コスト: フル学習 10 時間 + ONNX 再エクスポート + golden 更新 + ブラウザ版再検証
- リスク: T が 2 倍になり推論時間も約 2 倍 (CPU 112 ms → 220 ms 程度)

### 7.5 【中優先】FT レシピの見直し

2026-08-06 の実験で、**対照群も同じだけ悪化した**ことから FT レシピ自体が
疑わしいと分かっている。次に試すこと:

- 起点を `ft_1k` ではなく素の `models/full/best.pt` にする
- ステップ数と学習率を下げる
- 実データ比率を下げる (`--real-ratio 0.5` → 0.3)

### 7.6 【低優先】2 段階確定のブラウザ版移植

デスクトップ版で 2.3pt の効果が確認済み。ブラウザ版に同じ利得を与える。
装飾位置の付け替えが要る (`。` 改行と同じ問題)。

### 7.7 【再学習の機会に同時実施すること】

トークン ID がずれる変更は、学習をやり直すときにしかできない。
**次にフル学習を回すときにまとめて入れる**:

- 和文の括弧 `「` = `-・--・-` / `」` = `・-・・-・` を語彙に追加
- 語彙の見直し全般 (現在 72 トークン)
- `scripts/export_tokens.py` / `export_onnx.py` / `export_golden.py` の再実行

### 7.8 【最後の手段】アーキテクチャ刷新

Conformer 等への変更は、上記をすべて実施して改善が止まった場合にのみ検討する。
現状はモデル容量よりも**評価方法・データ構成・実験順序がボトルネック**である
という 2026-07-30 の結論が今も有効。

## 8. 実験の原則 (踏んだ穴から)

新しい実験を始める前に必ず読むこと。すべて実際に踏んだ失敗から来ている。

1. **対照群を置く。** 「手打ち分布が悪い」と結論しかけたが、対照群を足したら
   同じだけ悪化した。悪かったのは分布ではなく FT レシピだった
2. **評価は held-out に正解ラベルで当てる。** 代理指標 (一致率) で測った掃引は
   結論が逆だった。一致率は正しさではない
3. **参照表を書くときは実装を見ない。** 段落 `・-・-・・` の誤記は参照表も同じ
   間違いをしていたので照合テストが 2 か月素通りした
4. **掃引の形が変なときは実装のバグを疑う。** 「余白を増やすほど悪くなる」という
   逆向きの結果が、実際には書き直しを諦める分岐のバグだった
5. **周辺分布が正しくても同時分布が空になりうる。** σ を対数一様にしても
   「間隔ちょうど 1/3/7 かつ σ 小」の組合せは 20,000 件中 0 件だった。
   制約は同時条件で検証する
6. **原稿はラベルではない。** 打鍵計画と実際に打鍵された音は違う
7. **`?` を消しても精度は上がらない。** 確信度閾値を下げると CER は悪化する。
   `?` の裏に正解は隠れていない。減らしたいなら表示層でやる
8. **`--num-workers 0` (FT 時)。** Windows で Ctrl+C すると worker が孤児化して
   RAM を握り続ける
9. **`--steps` は絶対値。** resume すると step が復元されるので `base + N` を渡す
10. **結果文書に実行コマンドをそのまま残す。** 現行モデルの学習コマンドが
    正確に残っていないため、対照実験に設定ドリフトの疑いが残っている
11. **仮説は合成で再現して確かめてから対策する。** 2026-08-14 に「速い和文」
    「間隔の圧縮」という 2 つのもっともらしい仮説を立てたが、実測すると
    速度は 18.2 WPM (速くない)、間隔の圧縮は再現しても劣化 0.00pt だった。
    **合成器は仮説を数分で否定できる道具である。** 学習を回す前に必ず通すこと
12. **「異常」と決める前に平常値を測る。** 今回の録音の誤り率は、held-out 和文の
    31.73% とほぼ同じだった。異常な録音ではなかった
13. **人間の耳と比べる。** モデルの 34.92% は「悪い」と見えるが、同じ録音を
    熟練者が耳で読んでも 28.57% 間違えていた。**上限を知らずに改善目標を立てると、
    達成不可能な数字を追ってデータや分布をいじり続けることになる。**
    実録音の評価には「人間ならどこまで読めるか」を併記すること

## 9. 再現コマンド集

```bash
# 評価 (keyed_val + synth_val)
python scripts/eval_model.py --ckpt models/full/best_infer.pt \
  --keyed-dir data/keying_scripts --noise-dir data/noise/val \
  --out models/eval/next.json --device cuda

python scripts/train.py \
  --steps 102000 --batch-size 8 --num-workers 2 \
  --ckpt-dir models/full_next --eval-interval 2000 --log-interval 500 \
  --device cuda --seed 42

# 実信号 FT (約 9 分)
python scripts/finetune.py \
  --data-dir data/real/train --resume models/full/best.pt \
  --ckpt-dir models/ft_next --steps 1000 --lr 5e-5 --batch-size 16 \
  --mix-synth --real-ratio 0.5 --tone-center 490 --tone-span 60 \
  --num-workers 0

# 実録音のキーイング統計を測る (谷の位置を見て --split-ms を明示すること)
python scripts/analyze_keying.py data/real/<file>.wav --split-ms 130

# その統計を合成で再現し、どの要因が劣化を生むかを切り分ける (§6.2 の手順)
python scripts/ablate_keying_factors.py --mode japanese \
  --wpm 18.2 --ratio 3.00 --tone 583 --spacing 0.66 2.54 5.63 \
  --sigma-dot 0.216 --sigma-dash 0.413 --snr 13.2

# 1 ファイルをオフライン全文脈でデコードする (正解ラベル不要)
python scripts/decode_user_wav.py --wav "japanese:data/real/<file>.wav"

# 打鍵録音の取り込み (BPF + 前後無音の付加は既定で入る)
python scripts/import_keying_recordings.py \
  --european-dir data/欧文 --japanese-dir data/和文 \
  --out-dir data/real/train --dry-run   # 確認後 --dry-run を外す

# 再学習後に必ず実行
python scripts/export_tokens.py
python scripts/export_onnx.py
python scripts/export_golden.py
```

**注意**: `--data-dir data/real` は使えない (直下の 4 ファイルが角括弧表記で
`text_to_codes` が `KeyError`)。`data/real/train` を使うこと。
