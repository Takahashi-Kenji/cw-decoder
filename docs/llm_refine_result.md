# LLM 清書の測定 (2026-08-08)

## 何を決めたかったか

辞書補正 (`docs/word_correct_result.md`) で欧文が読めるようになった後、
LLM に何を任せるか。運用者の判断は次のとおり。

* **和文の主目的は漢字かな交じりへの変換。** 電文がカタカナなのは和文モールスの
  仕様上どうにもならないが、読む側は漢字かなの方が楽
* **文字変換だけなら小さいモデルで足りるはず**
* **thinking モードは不要なはず**
* **CW デコードは CPU、GPU はローカル LLM に**

## デコードは CPU の方が速かった

30 秒窓 / `models/full/best_infer.pt` / hop 0.5 秒に間に合う必要がある。

| デバイス | 中央値 | 最悪 | hop に対する余裕 |
|---|---|---|---|
| CPU 2 スレッド | 164 ms | 192 ms | 2.6x |
| **CPU 4 スレッド** | **112 ms** | **134 ms** | **3.7x** |
| CPU 8 スレッド | 149 ms | 155 ms | 3.2x |
| CUDA | 139 ms | 175 ms | 2.9x |

**CPU 4 スレッドが CUDA より速い。** モデルが小さく、GPU はレイヤごとの起動費用が
勝ってしまう (特に BiLSTM)。GPU を LLM に空けるのは損失どころか得だった。

既定を `decode_device="cpu"` / `decode_threads=4` にした。`--device cuda` で戻せる。

## thinking を切るのは正しかった

`think: false` で書式の破綻 (絵文字の羅列・同じ句の繰り返し) が消え、
待ち時間も大幅に縮んだ。**清書は文字の変換であって推論ではない。**

暴走対策として `num_predict: 512` と `repeat_penalty: 1.15` も入れた
(gemma3:12b が記号を延々と繰り返す暴走を実際に起こしたため)。

## 小さいモデルで足りるか → **半分だけ正しい**

held-out 和文 4 件 (定型 3 + 平文 1) を目視で比べた。

| モデル | 速度 | 質 |
|---|---|---|
| qwen3.5:2b | 1.6 秒 | **破綻**。絵文字の羅列と繰り返し |
| gemma3:4b | 0.9 秒 | 不可。`テンキ ハ ハレ`(晴れ) を「天気が悪いですね」と逆に取る |
| qwen3.5:4b | 2.6 秒 | まちまち。定型は取れるが平文は崩れる |
| **gemma4:e4b** | **0.8 秒** | **最良**。「天気は晴れです。暑いです」「天気は曇りです」 |
| gemma3:12b | 11.8 秒 | 大きいのに**悪い**。記号の暴走、禁止したはずの謝罪文 |

**速度は小さいモデルで十分** (0.8 秒/件)。**質は大きさに比例しない** —
12b が e4b より悪かった。現時点の推奨は **gemma4:e4b**。

## プロンプトが重すぎた (2026-08-08 追記)

上の比較は**重いプロンプト (1403 文字)** で測ったものだった。短い版 (207 文字) に
すると同じモデルの出力が明確に良くなる。

```
正解 : オハヨウ、アツイ デス、シカタ ナイ
重い : こちらは、暑いです。仕方ないですね。      ← 「おはよう」が消える
短い : おはよう、暑いです、仕方ない              ← 正確

正解 : テンキ ハ ハレ、アツイ デス、チヌリイズヌ
重い : ⟦天気は晴れ、暑いです。チューリップですね⟧  ← チューリップを捏造
短い : 天気は晴れ、暑いです、ちぬりいずぬ。       ← 正確
```

決定的だったのは `schroneko/gemma-2-2b-jpn-it` で、**入力を無視して
``_JP_CLEANUP`` の例文をそのまま返した** (4 件すべて「こんにちは。天気は晴れです」)。
例文が模範解答として扱われている。

規則 5 項目 + カナ→欧文対応表 (48 行) + 語彙 + プロサイン説明は、クラウドの
大きいモデルには効くが 4B 前後には多すぎる。設定 `llm_compact_prompt` (既定 True)
で切り替える。

**プロサインは箇条書き 1 行にすると効く。** 同じ内容を段落で書いた重い版では
`[ホレ]` が「これは」「晴れ」になったが、1 行版では消えた。指示の量が問題であって
内容ではなかった。

## 日本語特化モデルは向かない

| モデル | 結果 |
|---|---|
| `7shi/gemma-2-jpn-translate:2b` | **何を送っても `OK` としか返さない**。翻訳専用の入出力形式を前提にしている |
| `translategemma:4b` | **流暢に捏造する**。`オハヨウ、アツイ デス、シカタ ナイ` → 「こんにちは。お元気ですか？今日はいい天気ですね」 |
| `schroneko/gemma-2-2b-jpn-it` | 短い版でも変換がほとんど進まない |
| `hf.co/alfredplpl/gemma-2-2b-jpn-it-gguf:Q4_K_M` | 変換せずほぼ素通し。一度スペイン語 (`térmica`) を出した |

**翻訳特化モデルは目的が逆を向いている。** 翻訳モデルは「流暢な訳文を作る」よう
訓練されており、こちらが欲しいのは「壊れた入力に忠実な変換」である。

**2B は日本語特化でも足りない。**

`hf.co/elyza/Llama-3-ELYZA-JP-8B-GGUF` も試したが、**速いが変換しない**。

| 入力 | gemma4:e4b | ELYZA-JP-8B |
|---|---|---|
| `オハヨウ、アツイ デス、シカタ ナイ` | **おはよう、暑いです、仕方ない** | ホレの様子が良い、アツいです、しかたない |
| `テンキ ハ ハレ、アツイ デス` | **天気は晴れ、暑いです** | 天気は晴れ、アツいです |
| `テンキ ハ クモ リ` | 天気は雲り | テンキーはくも り |
| 速度 | 0.8 秒 | 0.5 秒 |

ELYZA はカナをカナのまま残す傾向が強く、漢字かな交じりにするという目的に届かない。
`[ホレ]` を「ホレの様子が良い」と勝手に解釈もした。

**ローカルでの推奨は `gemma4:e4b` + 短いプロンプト (0.8 秒/件)。**
大きさでも日本語特化でもなく、この組み合わせが一番良かった。

## 総合順位 (短いプロンプト、held-out 和文 4 件)

| モデル | 速度 | `[ホレ] テンキ ハ クモ リ[ラタ]` | `[ホレ]オ ハ ヨウ、アツイデス、シカタ ナイ` |
|---|---|---|---|
| **claude-haiku-4-5** | **1.0 秒** | **[ホレ] 天気は曇り[ラタ]** | **[ホレ]おはようございます。暑いです。仕方ないですね。** |
| gpt-5.6-luna | 3.3 秒 | **[ホレ] 天気は曇り[ラタ]** | **[ホレ]おはよう、暑いです、仕方ない** |
| gemma4:e4b (ローカル) | 0.8 秒 | 天気は雲り⟦らた⟧ | おはよう、暑いです、仕方ない |
| ELYZA-JP-8B (ローカル) | 0.5 秒 | テンキーはくも り | ホレの様子が良い、アツいです |

**Haiku 4.5 がクラウドの正確さをローカル並みの速さで出す。** 「曇り」を正しく
出せたのはクラウド 2 つだけで、ローカル勢は全滅した (雲り / くも り / 雲)。

## クラウド (`gpt-5.6-luna`) は明確に上

| 入力 | gpt-5.6-luna | gemma4:e4b | ELYZA-JP-8B |
|---|---|---|---|
| `[ホレ] テンキ ハ クモ リ[ラタ]` | **[ホレ] 天気は曇り[ラタ]** | 天気は雲り | テンキーはくも り |
| `[ホレ]オ ハ ヨウ、アツイデス、シカタ ナイ` | **[ホレ]おはよう、暑いです、仕方ない** | おはよう、暑いです、仕方ない | ホレの様子が良い、アツいです |
| 速度 | 3.3 秒 | 0.8 秒 | 0.5 秒 |

**ローカル勢が全滅した「曇り」を正しく出した**唯一のモデル。プロサインも保持する。
速度は 4 倍かかるが、清書は送信の区切りでしか走らないので実用上の差は小さい。

### 短いプロンプトは大きいモデルでも有利だった

同じ `gpt-5.6-luna` で比べると、短い版の方が**速く、かつ忠実**だった。

| | 平均 | 平文サンプルの出力 |
|---|---|---|
| 短い版 | **3.3 秒** | `ない？ キキマ」ラガニヘンチ」ンジタラタ` (読めない部分を残す) |
| 重い版 | 6.8 秒 | `⟦何か聞きます。⟧` (捏造) |

**「大きいモデルには重い指示が効く」という当初の想定は外れた。**
短い版を既定のままにしてよい。

Haiku 4.5 でも同じで、重い版は `こちらは好様` という崩れを出し、`[ホレ]` を
「こんにちは」と誤読した。**ローカル・OpenAI・Claude の 3 つすべてで短い版が勝った。**

### Ollama で HuggingFace の GGUF を引くとき

`hf.co/` の接頭辞と量子化タグの両方が要る。片方でも欠けると失敗する。

```
ollama pull hf.co/mmnga/sarashina2.2-3b-instruct-v0.1-gguf:Q4_K_M
ollama pull hf.co/alfredplpl/llm-jp-3-3.7b-instruct-gguf:Q4_K_M
ollama pull hf.co/elyza/Llama-3-ELYZA-JP-8B-GGUF:Q4_K_M
```

`realm host "huggingface.co" does not match original host "hf.co"` は、
**リポジトリが存在しないとき**にもこの文言で出る。名前を疑うこと。

## 欧文は CER で測れた — そして LLM は悪化させる

和文と違い**欧文は出力が欧文のままなので CER で測れる**。温度 0 に固定して 3 回。

| | CER |
|---|---|
| 素のデコード | 19.25% |
| **+ 辞書補正 (現行)** | **17.15%** |
| + LLM 清書 (3 回平均) | 18.27% (**+1.12pt**) |

**辞書補正が既に機械的な直しを済ませており、LLM は誤りを足す側に回る。**
良い直し (`?QZ QRL` → `QRZ? QRL?`) と悪い直し (`RST` を落とす、`FM7Y6GGB` を
`FM 1Y6 GGB` に割る) が混ざり、差し引きで悪化する。

欧文で清書を使うかは**読みやすさと正確さの取引**であって、精度のためではない。

### 温度を固定するまで測定が壊れていた

最初の比較では、**同じプロンプトの 2 回の実行で CER が 16.32% と 20.92% に割れた**。
差 4.6pt は効果より大きく、プロンプトの善し悪しを読んでいたつもりが実際には
ぶれを読んでいた。温度 0 でぶれは 0.42pt に収まった。

**清書は校正であって創作ではない。** 温度は 0 でよい (Ollama も 0.2 にしてある)。
この件で出した「欧文は短い版より重い版が良い」等の結論は**すべて根拠を失った**ので
撤回する。欧文が重い版を使うのは、短縮数字の規則と無線語彙をそこに置いたためである。

## 短縮数字 (cut numbers)

CW は数字を短い符号の文字で送る慣習がある (`5NN` = `599`)。運用者の要望で
欧文プロンプトに入れた。

**歯止めが 2 つ要る。** 規則だけを入れたところ、正しく取れていた `559` を
「599 の方が普通だから」と書き換え、`RST` を丸ごと落とす例が出た。

* 文字を数字にするだけ。**既にある数字は絶対に変えない**
* 語を消さない

辞書補正 (`word_correct`) ではこれを直せない。数字を含む語は「触らない」と
決めており、それはコールサインを守るための規則だからである。

## 測れていないこと (重要)

**上の「質」は 4 件の目視である。** 清書は表記が変わるので CER では測れず、
読みやすさは運用者が判断するしかない。したがってこの表は**傾向であって
順位ではない**。実運用で試して判断すること。

プロンプトの調整 (プロサインの説明を足す等) も同じ理由で効果を確認できなかった。
4 件を目視で比べて良し悪しを決めるのは、このプロジェクトが繰り返し戒めてきた
「代理指標で測る」誤りと同じである。

## 本当の限界は和文デコードの質

```
正解    : ナイトキキマネカラ カラダニヘンチヨウヲカンジタラタ
デコード: ナイ? キキマ 」ラガニヘンチ」ンジタラタ
```

**平文ではデコード自体がここまで壊れる。** どのモデルもこれは復元できなかった。
和文の CER は 41% で、欧文 (19%) の 2 倍以上ある。
**LLM のプロンプトを詰めるより、和文のデコード精度を上げる方が効く。**

## 和文の辞書補正 (作ったが未採用)

欧文と同じ「割れ直し」を和文でも試した。

| | CER | 差 |
|---|---|---|
| 補正なし | 41.26% | |
| 独立語彙 / 全被覆のみ | 37.67% | −3.59pt |
| **独立語彙 / 部分被覆** | **34.98%** | **−6.28pt** |
| 汚染語彙 / 部分被覆 | 31.84% | −9.42pt |

**「独立語彙」と「汚染語彙」を分けたのは、評価データが台本だから。**
held-out 和文 10 件は学習用テキスト生成器の語句リスト
(`_JA_GREETINGS`/`_JA_WEATHER`/`_JA_RIG`) をそのまま並べたもので、
そこから語彙を作れば当然当たる。独立版は `keying_corpus` の実運用 60 文だけから
語彙を作っている。**汚染版の数字は上限であって実力ではない。**

運用者の判断で**不採用**。実運用の和文は平文が主で、固定辞書では届かないため。
実際、唯一の平文サンプルは辞書がまったく触れなかった。
試作は `scratchpad/ja_reseg.py` に残してある。

## 実装

* 清書は**増分方式** — 未清書分だけを送り、直前は「参考。出力しないでください」
  として添える。結果は積み上げ表示。手動ボタンは全体を清書し直す
* 和文は**読みやすさ優先**、欧文は**確実さ優先** (コールサイン・RST を捏造されると
  実害が出る)。従来は全モードで「不確実だと分かる出力を優先」としており、
  これが和文の要望と正面から矛盾していた
* モデル候補は Ollama の `/api/tags` から取る (埋め込み専用は除外、クラウドは後ろへ)。
  コードに書き固めると、入っていない名前が既定になる
* 推測箇所の赤表示は切替可能 (赤が多いと読みにくいという指摘による)
