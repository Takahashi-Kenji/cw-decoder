# 手打ちキーイングの合成モデル拡張 設計書

作成日: 2026-08-06
対象: `src/synth/keying.py`, `src/synth/dataset.py`, `scripts/finetune.py`, `scripts/eval_model.py`
関連: `docs/accuracy-improvement-evaluation-and-roadmap.md`, `docs/commit_lag_sweep_result.md`

---

## 1. 背景と問題

ブラウザ版デコーダを実信号で運用したところ、**誤認が 10% 程度**という報告があった。
「?」にマウスを乗せて種別を確認したところ、**ほとんどが LOW_CONFIDENCE**
(CTC 事後確率が閾値未満) で、TABLE_MISS (変換表に無い符号) ではなかった。
入力レベルは −40〜−10 dBFS の適正範囲に収まっており、音声経路自体は健全である。

決定的な手掛かりは運用者の観察だった。

> エレキーのようなきれいな符号は誤り率が低いが、手打ちの場合、しかも早いと誤り率が多くなる。

エレキーは学習データとタイミングが一致する。手打ちは一致しない。
つまり**学習データの分布と実信号の分布がずれている**という仮説が立つ。

## 2. 実測による裏付け

運用者から実録音 2 本の提供を受け、包絡線からキーイングのタイミングを実測した。

計測方法: 8 kHz へリサンプル → トーン周波数を FFT のピークで推定 → その ±150 Hz で
バンドパス → ヒルベルト変換で包絡線 → 5 ms 平滑化 → 局所ピークの −6 dB で ON/OFF 判定。
**1 秒窓のコントラスト (95%tile / 20%tile) が 15 dB 未満の区間は除外**する。

### 2.1 計測上の落とし穴 (最初に踏んだ)

最初の計測ではノイズ区間を符号として拾い、**長短比 4.90・文字間 1.41 dot という
誤った数値**を出した。ON 長のヒストグラムに山が 3 つ (約 10 ms / 65 ms / 165 ms) 現れており、
10 ms の山はノイズ区間で閾値がばたついた断片だった。

**教訓**: ON/OFF のヒストグラムを必ず出力し、**山が 2 つでなければ測定の破綻を疑う**。
数値だけを見て判断しない。この検証は解析スクリプトに組み込む。

また短点/長音の分類境界を分位点から自動推定すると、80〜110 ms の短い長音を短点側に
混ぜてしまった。**ヒストグラムの谷を目視で確認して境界を指定する**。

### 2.2 実測結果

| 項目 | 遅い (23.1 WPM) | 速い (30.0 WPM) | 学習分布 | 判定 |
|---|---|---|---|---|
| トーン | 527 Hz | 526 Hz | 400〜900 Hz | 範囲内 |
| 短点 dot | 52.0 ms、σ **0.064** dot | 40.0 ms、σ **0.107** dot | σ 0.05〜0.25 (全要素共通) | 範囲内 |
| 長音 dash | 158.8 ms、σ **0.681** dot | 153.5 ms、σ **1.195** dot | 同上 | **上限の 4.8 倍** |
| 長短比 dash/dot | 3.06 | 3.84 | 2.5〜4.0 | 上端 |
| 要素間 | 1.18 ± 0.26 (最小 0.13) | 1.25 ± 0.42 (最小 0.17) | **1.0 固定** | **σ が範囲外** |
| 文字間 | 3.07 ± 0.65 | 2.86 ± 0.82 | **3.0 固定** | **σ が約 3 倍** |
| 語間 | 15.90 (n=2) | 7.55 ± 3.23 (n=3) | **7.0 固定** | データが薄い |

対象ファイル: `20260806_163838.wav` (20.6 秒、クリーン 20.0 秒)、
`20260806_164535.wav` (25.0 秒、クリーン 24.0 秒)。

### 2.3 実測から分かったこと

**(a) 速度を上げても長音の長さは変わらない。縮むのは短点だけである。**

158.8 → 153.5 ms (−3%) に対し、短点は 52.0 → 40.0 ms (−23%)。
運用者の「短点が極端に短くなる傾向」という観察は、
**速度を短点だけで稼いでいる**という形で実際に起きている。結果として長短比が
3.06 → 3.84 に上がる。

**(b) ばらつきが非対称である。短点は正確で、長音だけが暴れる。**

短点 σ は 0.064 / 0.107 dot と小さいが、長音 σ は 0.681 / **1.195** dot と一桁大きい。
速度を上げるとさらに広がる。

物理的にも整合する。短点は「叩く」弾道的動作で再現性が高く、長音は「押している時間を
自分で判断する」開ループ制御なので分散が大きい。**エレキーはこの分散がゼロ**であり、
「エレキーは誤りが少ない」という観察と一致する。

速い録音では長音 153.5 ± 47.8 ms、短点 40.0 ± 4.3 ms。2σ で見ると 58 ms 対 49 ms まで
接近しており、**ほぼ重なりかけている**。誤りが増えて当然の状況である。

**(c) 現在の合成器はこの形を原理的に作れない。**

`element_jitter_sigma_ratio` は**全要素に共通の 1 つの σ** であり、上限は 0.25 dot。
「短点は σ 0.06 で正確、長音だけ σ 1.2」という非対称は表現できない。
スペースの平均長 (要素間 1.0 / 文字間 3.0 / 語間 7.0) は**リポジトリのどこからも
変更されていない**。`src/` `scripts/` `tests/` を全て確認済み。

**(d) 当初の仮説のうち 2 つは実測で否定された。**

- **速度ドリフト**: 短点 +0.2% / −6.1%、長音 −9.6% / +5.1% と小さい。
  `intra_sample_wpm_drift` は定義だけあってどこからも参照されていない
  デッドパラメータだが、**実装する優先度は低い**。
- **相関ジッタ (AR(1) / ランダムウォーク)**: 1 次自己相関は −0.29〜+0.18 で、
  **正の相関は見られない**。むしろ負に寄っており「長く押しすぎた次は短くする」
  という補正の動きに見える。**採用しない**。

仮説として妥当に見えたものが実測で否定された。これを設計に残しておく。

### 2.4 証拠の限界

- 録音 **2 本**、打ち手 **1 人**、語間サンプルは計 **5 個**しかない
- 語間の範囲推定は特に弱い。広めに取って学習側で吸収させる
- 速い方の録音は**運用者自身も解読できない**。後述のとおり評価には使わない

## 3. 設計

### 3.1 合成器の拡張

`KeyingParams` を、要素種別ごとに独立したパラメータへ分解する。

| パラメータ | 現在 | 変更後 | 根拠 |
|---|---|---|---|
| `dash_dot_ratio` | 2.5〜4.0 | **2.5〜5.0** | 実測 3.06 / 3.84 に余裕を持たせる |
| 短点のジッタ σ | 共通 0.05〜0.25 | **0.02〜0.20** (独立) | 実測 0.064 / 0.107 |
| 長音のジッタ σ | 共通 0.05〜0.25 | **0.05〜1.30** (独立) | 実測 0.681 / 1.195 |
| 要素間スペース | 1.0 固定 | 平均 **1.0〜1.3**、σ **0.05〜0.50** | 実測 1.18 / 1.25、σ 0.26 / 0.42 |
| 文字間スペース | 3.0 固定 | 平均 **2.6〜3.2**、σ **0.05〜0.90** | 実測 3.07 / 2.86、σ 0.65 / 0.82 |
| 語間スペース | 7.0 固定 | 平均 **5〜16**、σ **0〜4** | 実測 7.55 / 15.90 (n=5 と薄い) |
| 速度ドリフト | 未実装 | **実装しない** | §2.3(d) |
| 相関ジッタ | 未実装 | **実装しない** | §2.3(d) |

**設計上の縛り**: エレキー相当 (σ 最小・比 3.0・間隔ちょうど 1/3/7) を
**部分集合として必ず残す**。過去に「片方を上げると片方が下がる」を繰り返し踏んでいる
(§4.2)。エレキーの精度を落とす変更は採用しない。

### 3.2 σ のサンプリング分布 (トレードオフへの対処)

長音 σ を 1.30 dot まで許すと、**人間にも解読できない領域**まで学習データに入る。
運用者は速い方の録音について「私も解読できません」と述べている。

そこまで学習させると、モデルが「曖昧なら当てずっぽうで出す」方向に振れ、
**きれいな符号での精度を落とす**恐れがある。

対処:

- σ は**対数一様**に引く。すなわち `sigma = exp(rng.uniform(log(sigma_min), log(sigma_max)))`。
  一様分布と違い、小さい σ に確率質量が集まり、極端な値は少数になる
- **「極端テールあり / なし」を A/B して判断する**。テールが synth_val を悪化させるなら
  上限を下げる

これは実装前に決め切れない。**評価で決める設計とする**。

### 3.3 実装上の制約 (CLAUDE.md 準拠)

- 波形生成は numpy ベクトル化。**for ループ禁止**
- 乱数は `np.random.Generator` を引数で受け取る。グローバル `np.random` を使わない
- 符号定義は `src/tokens/morse_tokens.py` を唯一の真正なソースとする
- 新パラメータは既定値を現行の挙動と一致させ、後方互換を保つ

## 4. 学習と評価

### 4.1 学習方法

- **起点**: `models/ft_1k/best.pt`。`models/full/best_infer.pt` と同一世代とみられる
  (`model_state` の辞書順先頭テンソル 1 個の MD5 が一致。`models/ft_2k` や
  `models/full/best.pt` とは一致しない)。**これは抜き取り検査であって全パラメータの
  一致を証明したものではない**ので、着手時に全テンソルで照合する
- **方式**: `scripts/finetune.py --mix-synth`。合成側のサンプラ (`src/synth/dataset.py`) を
  拡張するので、合成データが自動的に新分布になる
- `--num-workers 0` を使う (過去に GPU の孤児プロセスを踏んでいる)
- **ステップ数は 1000 を基準**とし、1000 と 2000 の両方を評価してから選ぶ
  (`models/ft_2k` は採用に至っていない)
- `--real-ratio` は既定 0.7 と 0.5 の 2 通りを見る
- `finetune.py` の resume には過去に落とし穴が 3 件見つかっている。着手時に再確認する

### 4.2 評価

`scripts/eval_model.py` に `--keyed-dir` と `--baseline` が既にあるのでそのまま使う。

- **主指標**: `keyed_val` 20 件 (`data/keying_scripts/script_eu_01`〜`10` /
  `script_ja_01`〜`10`、手打ちの held-out) の TER / CER
- **副指標**: `synth_val` (WPM × SNR グリッド)。役割は
  **エレキー相当の精度を落としていないことの確認**
- **採用基準**: **keyed_val が改善し、かつ synth_val が悪化しないこと。
  片方だけなら不採用**

最後の基準は過去の経緯から来ている。B1 再学習・実ノイズ混合 FT・WORD_BREAK 閾値掃引と、
**3 回続けて「片方だけ良くなった」ものを不採用にしている**。同じ基準を引き継ぐ。

**今回の録音 2 本は評価セットに使わない。** 速い方は運用者自身が解読できず、
信頼できる正解テキストを作れない。正解の無いデータを評価に使うのは、過去に踏んだ
ラベル汚染 (`keyed_val` のラベルに音の無いトークンが 19 個混入し、baseline を
23.35% と誤読していた) と同じ失敗である。**σ の実測ソースとしてのみ使う**。

遅い方 (`20260806_163838.wav`) は運用者から送信内容の提供を受けたので追加した。
ただし**末尾は波形レベルで曖昧だったため 18.22 秒で切り落とし**、確実な範囲だけを
`data/keyed_extra/20260806_163838_cut.{wav,txt}` として置いた。切り落とした理由と
波形の根拠はその `.txt` のヘッダに記録してある。

**置き場所を `data/keying_scripts/` にしてはいけない。** `discover_real_samples` は
`rglob("*.wav")` でディレクトリ全体を拾うため、そこに 1 件足すと **keyed_val が
20 件から 21 件に変わり、過去の数値 (23.35% / 25.95% / 23.27%) と比較できなくなる**。
指標が黙って変わるのはこのプロジェクトが繰り返し踏んできた失敗なので、
**keyed_val は 20 件のまま固定し、新しいサンプルは別ディレクトリで別指標として測る**。

**再現性**: 固定シード。評価 JSON に checkpoint のハッシュと対象ファイル一覧を記録する。

### 4.3 テスト

- **統計の往復検証 (最重要)**: 実測値 (長音 σ 1.195 dot 等) を合成器に与えて大量生成し、
  **生成物を同じ解析スクリプトにかけて、入れた値が返ってくるか**を検証する。
  合成器が「指定した分散を実際に持つ波形」を作れていなければ学習しても意味がない
- **後方互換テスト**: 新パラメータを既定値にすると従来と**完全に同一の波形**になること
- **決定性テスト**: 同じ `Generator` シードで同じ波形になること
- 数値検証は既存方針どおり波形時間 ±5% で判定する
- 解析スクリプトを `scripts/analyze_keying.py` としてリポジトリに入れる。
  §2.1 の検証 (ヒストグラム出力、山の数の確認、分類境界の明示指定) を組み込む

## 5. スコープ外

今回やらないもの。理由とともに記録する。

- **BPF のトーン追従**: ブラウザ版の BPF は中心 600 Hz 固定だが、運用者の受信ピッチは
  527 Hz で約 5 dB 減衰し、混信の多い 550〜750 Hz を素通しさせている。
  ただし**主因ではない** (エレキーで誤りが低いなら SNR は足りている)。合成器の件が
  片付いてから着手する
- **「?」の表示改善**: LOW_CONFIDENCE のとき最尤文字を薄字で出す案。認識率自体は
  上がらないので後回し
- **速度ドリフト・相関ジッタ**: §2.3(d) のとおり実測が否定した

### 5.1 記録すべき懸念: メル窓長が天井になる可能性

速い録音では要素間が最小 **0.17 dot = 7 ms** まで詰まっていた。
一方メル特徴の窓長は **25 ms** (`MelConfig.win_ms`)、ホップは 10 ms である。
**7 ms の隙間は 25 ms の窓では原理的に分解できない。**

合成器を直しても、この解像度が天井になる可能性がある。窓長を変えると
`FRAME_HOP_SAMPLES`・ONNX・`web/src/generated/tokens.ts`・時間軸の定数まで波及し、
フル再学習が必要になる。**今回はスコープ外だが、合成器の拡張で頭打ちになった場合の
次の一手**として記録する。

### 5.2 副産物: 「実信号でホレ/ラタが取れない」問題への手掛かり

長年未解決の問題として「実信号で ホレ/ラタ が検出できず、自動モード切替が働かない」が
ある (原因候補を潰しても特定できていない)。今回の波形解析で、その説明になりうる事実が
見つかった。

**和文終了プロサイン `ラタ` (・・・-・) は、`ラ`(・・・) + `タ`(-・) と符号列が完全に同一である。**
区別は間の隙間だけで、文字間なら 3 dot、プロサイン内なら 1 dot になる。

`20260806_163838.wav` の 18.62 秒の実測値は **1.48 dot** で、**どちらとも判定できない**。
本設計の実測が示すとおり、手打ちでは文字間が σ 0.65〜0.82 dot でばらつき、
最小 1.91 dot まで詰まる。つまり**手打ちでは `ラ`+`タ` と `[ラタ]` が原理的に
区別できない場面が普通に起きる**。

同じことは他のプロサインにも当てはまりうる。本設計のスコープ外だが、
自動モード切替の問題に戻るときの出発点として記録する。

### 5.3 Phase 2: 語句としての予測

運用者の指摘:

> 後の録音の方は私も解読できません。おそらく、解読には予測に語句として捉える必要があります。

タイミングだけでは天井がある。人間の熟練者も、曖昧な符号を**語句の文脈**で補って読んでいる。

ただし**適用先はデスクトップ版に限る**。運用者の指示:

> ブラウザ版は語句予測は不要です。なお、デスクトップ版は、ある程度、精度が上がったら、
> 長い語句ではなく、もっと短い語句で予測していきたいです。これは後の話です。

したがって:

- **ブラウザ版は対象外**。`src/llm/` のブラウザ移植は**やらない**。
  ブラウザ版はあくまで「音 → 符号 → 文字」の決定論的な経路に留める
- **デスクトップ版のみ**が対象。ただし現在の `src/llm/` (Ollama / Claude / OpenAI 対応の
  LLM 清書機能) は**文章単位のまとまった清書**を行う設計である。運用者が求めているのは
  **もっと短い単位での予測**であり、方向が違う。既存の清書機能をそのまま使うのではなく、
  短い単位 (語・コールサイン・RST・定型略語など) を対象とした別の仕組みを検討する
- 着手条件は「**ある程度、精度が上がったら**」。つまり**本設計 (合成器拡張) の結果を
  見てから**であり、順序が逆にならないようにする

候補としては、CTC の beam search に CW の定型語彙 (CQ, DE, 599, RST, コールサイン形式
など) の短い言語モデルを組み合わせる方向が、この「短い語句で予測」という要件に近い。

いずれも本設計のスコープ外。合成器拡張の効果を測ってから、残った誤りの性質を見て選ぶ。

## 6. 完了条件

1. 合成器の新パラメータが往復検証テストを通る (指定した σ・平均が生成物から復元できる)
2. 既定値で従来と同一波形になる後方互換テストが通る
3. `scripts/analyze_keying.py` がリポジトリにあり、ヒストグラム検証を含む
4. FT 後のモデルが **keyed_val で改善し、synth_val で悪化しない**
5. 上記を満たさない場合は**採用しない**。その判断と数値を記録する
