# 経歴 — 欧文用と和文用の分離、および編集画面 設計書

2026-08-12。`2026-08-11-reply-templates-design.md` の続き。
**`2026-08-12-european-span-design.md` (`「…」` の欧文区間) の後に作る。**

本書は**設計は 1 本、実装は 2 つの計画**に分ける。構造の変更 (`profile.py` /
`templates.py` / `reading.py` にまたがる) と編集画面 (純粋に画面) は、
片方が壊れたときにもう片方の原因だと分かるようにするため。

---

## 1. なぜ要るか

**理由は 2 つある。**

### 1.1 経歴を書く手段が無い

`~/.cw-decorder/operator.json` に置く決まりで `load_profile()` は送信ダイアログが読んでいるが、
**`save_profile()` は本番のどこからも呼ばれていない** (テスト専用)。運用者は JSON を手で書くしかなく、
**運用者の環境にはまだこのファイル自体が無い**。

経歴が空だと型の `{自局コール}` `{名前}` が埋まらないので、**型が 1 つも実用にならない**。

### 1.2 欧文と和文で中身そのものが違う

いまの `ProfileField` は `display` + `reading` で「同じものを 2 通りに書く」形だが、
**運用者が必要としているのは独立した 2 つの値**である (2026-08-12 の聞き取り)。

```
              欧文用          和文用
名前          TARO           タロウ
QTH           YOKOHAMA         ヨコハマシ
リグ          FT991           「FT991」
```

`「FT991」` は `FT991` の「読み」ではない。別の値である。

## 2. 経歴の構造

### 2.1 欄

| 欄 | 形 | 備考 |
|---|---|---|
| `callsign` | **1 つだけ** | コールサインは和文交信でも欧文で送る。分ける意味が無い |
| `name` `qth` `rig` `antenna` `power` | **欧文用 / 和文用の 2 値** | |
| `notes` | 1 つ | 自由記述。第 4 段の LLM に渡す |
| `reading_dictionary` | 1 つ | 運用者が育てる 語 → 読み |

**天気と気温は経歴に置かない** (§5)。

### 2.2 値が無いときは `?` を打つ

**差し込む値が無ければ `?` を入れる。欄による例外を作らない。**

```
経歴も相手コールも空の状態で「応答」の型を使うと:
  ? DE JH0ILL RST 599 {HORE}コンニチハ、ナマエ ハ ?{RATA} K
```

`?` は**和文表にも欧文表にもある** (`-0123456789?@` が両方にある) ので、
どちらのモードでも送れる。CW では「分からない」を意味するので、交信としても通る。

**もう一方の側で代用しない。** 和文側が空でも欧文側の値は使わない。書き忘れと区別がつかなくなる。

**通知しない。** 運用者は送信文に出た `?` を見て、必要なら日本語ボックスを
直してから確認・送信する (2026-08-12 の運用者の判断)。

これにより「埋まっていない欄があります」で送信を止める仕組みは**廃止する**。

### 2.2.1 【重要】確認の関門は変わらない

**廃止するのは「埋まっていない欄で止める」仕組みだけである。**
`[確認]` を押すまで `[送信]` を押せないこと、編集したら `[送信]` が無効に戻ることは
**そのまま残る** (`2026-08-11-reply-templates-design.md` および
`2026-08-10-lan-cw-transmit-design.md` §6)。

| | どうなるか |
|---|---|
| `[確認]` を押すまで `[送信]` を押せない | **変わらない** |
| 編集したら `[送信]` が無効に戻る | **変わらない** |
| 打鍵側が符号化して秒数を返す | **変わらない** |
| 送信できない文字があれば赤く出る | **変わらない** |
| 埋まっていない欄で止める | **廃止** (代わりに `?` が送信文に見える) |

`?` は符号表にある正当な文字なので `[確認]` を通る。**運用者が送信文を目で見て
判断する**という関門の役目は、むしろこの変更で素直になる — 止められるのではなく、
何が出るかがそのまま見える。

### 2.3 `field_readings()` を廃止する

いまの `reading.py` は経歴の欄を変換辞書に注ぎ込んでいる。

```python
# src/tx/reading.py:202
lookup.update(profile.field_readings())   # 表示形 -> 読み
```

**これが「欧文が壊れる」欠陥の発生源である。** 辞書が本文全体に当たるため、
欧文の本文の `TARO` が `タロウ` に置き換わり、カタカナが混ざってモードが和文に倒れ、
文中の欧文がまるごと送れなくなる (2026-08-11 に実測)。

**欧文用と和文用を独立した値にすると、この仕組み自体が要らなくなる。**
差し込みのときにモードで選べば済むので、変換辞書に注ぐ理由が無い。

**`field_readings()` を消す。** 引き継いだ欠陥のうち**経歴に由来する分は構造的に無くなる**。
運用者が育てる `reading_dictionary` の分は残るが、そちらは意図して入れたものなので
警告で足りる (§4.3)。

### 2.4 既存のファイルの扱い

**移行は書かない。** `operator.json` は運用者の環境に存在せず、
`load_profile` は壊れた/読めない内容を空の経歴として扱う。
**旧い形のファイルがあれば空として読まれる** — それでよい。書き直せば済む。

## 3. 差し込みの規則

`profile_values(profile, mode)` がモードで側を選ぶ。

| 型の `mode` | 使う側 |
|---|---|
| `japanese` | 和文用 |
| `european` / `any` | 欧文用 |

**`any` が欧文側なのは、`any` の型が欧文の略語 (`PSE AGN AGN K`) を主とするため。**

値が空なら `?` (§2.2)。`callsign` は 1 つしかないので常にそれを使う。

## 4. 編集画面

`src/app/profile_dialog.py` (新規)。送信ダイアログ (既に 625 行) には**ボタン 1 つだけ**足す。

```
型 [応答 ▼] [型を使う]  [経歴…]      <- ここに 1 つ
```

`load_profile` / `save_profile` をそのまま使う。保存先も `~/.cw-decorder/operator.json` のまま。

**閉じたら送信ダイアログが経歴を読み直す。** 書いてすぐ型に反映されないと確かめようがない。

### 4.1 画面

```
自局コール  [JH0ILL              ]                      <- 1 つだけ

            欧文用                和文用
名前        [TARO            ]  [タロウ            ]
QTH         [YOKOHAMA          ]  [ヨコハマシ           ]
リグ        [FT991            ]  [「FT991」          ]
アンテナ    [DP               ]  [「DP」             ]
出力        [50W              ]  [「50W」            ]

自由記述 (AI の返信案に渡します)
+--------------------------------------------------+
+--------------------------------------------------+

読み辞書
+----------------+------------------+
| 語             | 読み             |   [追加] [削除]
| 東京           | トウキョウ        |
+----------------+------------------+

                                     [保存] [閉じる]
```

**両方とも手で入れる。自動候補を出さない。** 固有名詞の誤読が一番痛く、
`横浜市` を `オウヒンシ` と読まれても気づきにくい (2026-08-12 の運用者の判断)。

### 4.2 保存するときに検証する

**書いた値が本当に送れるかを、保存の前に見せる。**

| 見るもの | 出す文言の例 |
|---|---|
| 欧文用の値が**欧文の文の中で**送れるか | 「欧文で送れません: 名前 の 佐藤」 |
| 和文用の値が**和文の文の中で**送れるか | 「和文で送れません: 名前 の TARO」 |

判定は `encoder.find_unsendable` を使う。**符号表を書き写さない** (アーキテクチャ原則 2)。

**実際に通る道と同じ道を通すこと。** 生の値だけを見ると誤判定する。実測:

```
'ニジュウド' を生で判定       -> NG: 小書きの ュ が符号表に無い
実際の経路 (to_sendable_kana) -> ニジユウド に倒れて送れる
```

型の検証 (`unsendable_in_template`) が同じ理由で `to_sendable_kana` を通しており、揃える。

**和文側は `「…」` を含みうる** ので、`2026-08-12-european-span-design.md` の規則が
効いた状態で判定すること。`「FT991」` は和文の文の中で送れる。

**警告しても保存は妨げない。** 書きかけを保存できないと育てるのが苦痛になる。

### 4.3 読み辞書と、残る欠陥

読み辞書は「語 → 読み」の表で、追加・削除ができる。

`field_readings()` を消しても (§2.3)、**運用者が自分で入れた読み辞書は本文全体に当たる**。
欧文の語を入れると欧文の交信が壊れる。

**画面で警告する。入力は妨げない。**

```
警告: 読み辞書に欧文の語があります (TARO)。
      欧文の交信でこの語を打つと送れなくなります。
```

運用者の自由を奪わない。見せるだけにする。

## 5. 天気・気温の欄

`PLACEHOLDERS` に `天気` `気温` を足す。**値は送信ダイアログの欄から取る。経歴からは取らない。**

```
相手 [JA1ABC]  相手名前 [    ]  送る RST [599]
天気 [ハレ]    気温 [20]                          <- 増える行
```

**天気と気温を経歴に入れない理由**: 運用のたびに経歴の画面を開いて書き換えることになる。
相手コールや RST と同じ「その交信のもの」である。

**気温は数字で書く** (`20`)。数字は両方の表にあるので、型に `キオン ハ {気温} ド` と
書けば和文で通る (実測で確認済み)。

**既定値は空にする。** 空なら `?` が出る (§2.2)。前回の値が残っていると、
書き忘れたまま嘘の天気を送ることになる。

## 6. 異常時のふるまい

| 起きること | どうする |
|---|---|
| 経歴のファイルが壊れている | 空として扱い画面に出す。**上書きしない** (手で直せる余地を残す) |
| ファイルが無い | 空の画面から始める。保存で作る |
| 保存が途中で失敗 | **既存のファイルを壊さない** (型と同じアトミック書き込み) |
| 値が空 | **`?` を打つ。**止めない。通知しない |
| 送れない値がある | 保存時に警告。**保存は妨げない** |
| 読み辞書に欧文の語がある | 警告。**入力は妨げない** |
| 読み辞書の語が空 | その行を捨てる (保存しない) |

## 7. テスト

**画面もファイルも実物を使わず試験できる。**

| 対象 | 見ること |
|---|---|
| 2 値の差し込み | 和文の型で和文側、欧文の型で欧文側が入ること |
| `any` の型 | 欧文側が入ること |
| 空のとき | **`?` が入ること。**もう一方で代用しないこと |
| `callsign` | 1 つしかなく、どちらのモードでも同じものが入ること |
| `field_readings` の廃止 | **欧文の本文の `TARO` が `タロウ` に化けないこと** |
| 保存・読み込み | 一時パス。**利用者の実ファイルを壊さない** |
| 壊れたファイル | 空として扱い、**上書きしない**こと |
| 保存の失敗 | 既存のファイルが壊れないこと |
| 読み辞書 | 追加・削除。**語が空の行を捨てる**こと |
| 保存時の検証 | 欧文用の漢字・和文用のローマ字が警告されること |
| 検証の経路 | 小書きカナが誤判定されないこと |
| 保存を妨げないこと | 警告が出ても保存できること |
| 読み直し | **閉じたら送信ダイアログが経歴を読み直す**こと |
| 天気・気温 | 型の `{天気}` `{気温}` に欄の値が入ること。**既定が空**であること |
| 例文 10 個 | **新しい構造の経歴で引き続き全部送れること** |

画面は既存の offscreen の型 (`tests/test_tx_dialog.py`) に倣う。

## 8. 実装の分け方

| 計画 | 中身 |
|---|---|
| **1** | 経歴の構造 (2 値・`field_readings` 廃止・`?`)、`{天気}` `{気温}`、送信ダイアログの欄 |
| **2** | 編集画面 (`profile_dialog.py`)、保存時の検証、読み辞書の警告 |

計画 1 が終われば**経歴を手で書けば型が実用になる**。計画 2 はそれを画面から書けるようにする。

## 9. 確認できていないこと

- **読み辞書をどれくらい育てるかは未知。** 行が増えたときの見せ方 (並び替え・検索) は
  実際に使ってから決める
- **自由記述 (`notes`) はまだ誰も読んでいない。** LLM 返信案で使う
- **`?` が実際の交信で相手に通じるかは運用でしか分からない。** 運用者の判断による
- **`reading_dictionary` が本文全体に当たる問題は残る。** 警告は出すが根本は直さない
