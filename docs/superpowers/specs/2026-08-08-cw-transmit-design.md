# CW 送信機能 設計書

2026-08-08

## 1. 目的

受信・デコードに加えて、**返信を書いて送信する**までをアプリ内で完結させる。
和文の交信を主な対象とする。

送信は USB シリアル変換器の **DTR / RTS** を上下させて電鍵を叩く。
無線機側の設定で線の割り当てが変わるため、**どちらが電鍵でどちらが PTT かは設定で変える**。

**あくまで拡張機能**であり、既存の受信・デコード・清書の動作には影響を与えない。
送信ダイアログを閉じていれば、これまでと完全に同じ挙動である。

## 2. 段階分け

| 段階 | 範囲 |
|---|---|
| **第 1 段** | シリアル打鍵、送信ダイアログ、日本語→カタカナ変換、経歴・読み辞書 |
| **第 2 段** | AI による返信案の生成 |

**第 1 段だけで「自分で書いて送る」が完成する。** 電波が正しく出ることを確かめてから
AI を乗せる。第 2 段は第 1 段の `返信 (日本語)` 欄を埋める機能にすぎず、
送信経路には手を入れない。

本設計書は両段を記述するが、実装は第 1 段から行う。

## 3. 全体の流れ

```
  相手の清書 (既存)
        │
        ▼
  返信 (日本語で編集)  ←── AI が下書き (第 2 段)
        │
        ▼  読み辞書 → 経歴の読み → pykakasi
  送信内容 (カタカナ)   ←── 直接編集も可。これが唯一の真実
        │
        ▼  符号表と照合。送れない文字があれば送信を止める
  検証
        │
        ▼  codes_to_waveform (既存の合成器)
  試聴 ── 聴くまで [送信] は押せない
        │
        ▼  最終確認ダイアログ
  送信 ── PTT ↑ → 打鍵 → PTT ↓
```

## 4. 日本語 → カタカナ変換

### 4.1 なぜ変換が要るか

和文モールスの符号表にあるのは**カタカナ・数字・`、`・`」`・`?`・`-`・`@`・長音 `ー`・
濁点 `゛`・半濁点 `゜`だけ**である。漢字もひらがなも小書き文字 (ャュョッェ) も無い。

読みやすい日本語で編集し、送信直前にカタカナへ変換する
(**案 B**。案 A「AI に両方書かせる」案 C「カタカナだけ」は不採用。運用者の選択)。

### 4.2 変換の順序

1. **読み辞書** — 運用者が育てる `語 → 読み` の一覧。最優先で当てる
2. **経歴の読み** — 名前・QTH 等、経歴の欄に併記された読み
3. **pykakasi** — 上で当たらなかった残りを機械変換
4. **小書き → 大書き** — `ャ→ヤ  ュ→ユ  ョ→ヨ  ッ→ツ  ァ→ア  ィ→イ  ゥ→ウ  ェ→エ  ォ→オ  ヮ→ワ`
5. **句読点の対応** — `。→、`  `！→、`  `．→、`  `，→、`  `「→` (削除)  `」→」`

**固有名詞の誤読が最も痛い。** 自局のコールサイン・名前・QTH は経歴の欄に
読みが併記されるので、構造的に誤読が起きない。それ以外の重要語は運用者が
読み辞書に登録する。

### 4.3 検証

変換後の文字を 1 文字ずつ符号表 (`JAPANESE_CHAR_TO_CODES` / 数字 / 記号) と照合する。

- 該当が無い文字は**赤く表示し、[送信] を無効にする**
- **黙って落とさない。** 落とすと相手には意味の通らない符号が届く

### 4.4 追従と切り離し

日本語欄を編集するとカタカナ欄が自動で追従する。
カタカナ欄を直接編集した時点で追従を切り、「手で直しました」と表示する。
日本語欄を再度編集すると追従が戻る (確認を出す)。

**画面に出ているカタカナと電波が必ず一致する。**

## 5. 送信ダイアログ

メインウィンドウの **[送信…]** ボタンで開く。モードレスで、デコードは止まらない。

```
┌─ CW 送信 ──────────────────────────────────────────────────┐
│ 相手の清書                                        (読取専用) │
│ │ こんにちは。天気は晴れです。信号は 599 です。どうぞ       │ │
│                                                              │
│ [AI に返信案を作らせる]   定型: [CQ] [応答] [RST 交換] [終了] │
│                                                              │
│ 返信 — 日本語で編集                                          │
│ │ こんにちは。こちらも晴れです。信号は 599。どうぞ          │ │
│                          ↓ 自動変換                          │
│ 送信内容 — カタカナ  ★これがそのまま電波になります★         │
│ │ コンニチハ、コチラモ ハレ デス、シンゴウ ハ 599、ドウゾ   │ │
│                                                              │
│ 20 WPM ／ 約 18 秒 ／ 送れない文字なし                       │
│ [x] ホレ/ラタ で囲む                                         │
│                                                              │
│ 速度 [20] WPM    [試聴]    [送信]    [中止]        [閉じる]  │
└──────────────────────────────────────────────────────────────┘
```

| 欄 | 編集 | 送信されるか |
|---|---|---|
| 相手の清書 | 不可 | — |
| 返信 (日本語) | 可 | されない |
| **送信内容 (カタカナ)** | **可** | **される** |

**定型ボタン**は経歴の欄からテンプレートを差し込む。AI を通さないので誤りが入らない。

| ボタン | 生成例 |
|---|---|
| CQ | `CQ CQ CQ DE JH0ILL JH0ILL K` |
| 応答 | `<相手> DE JH0ILL` |
| RST 交換 | `RST 599 599 NAME タロウ QTH ヨコハマシ` |
| 終了 | `TNX QSO 73 SK` |

**「ホレ/ラタ で囲む」** を ON にすると、和文の本文を `{HORE}` … `{RATA}` で囲む
(`text_to_codes` の既存マーカー)。和文の運用作法どおり。

## 6. 安全

運用者の選択は **「試聴 → 確認 → 送信」**。実装は次のとおり。

1. **[送信] は試聴するまで無効。** 送信内容を編集すると再び無効になる。
   **聴かずに電波が出る経路を作らない**
2. [送信] を押すと最終確認ダイアログ。カタカナ全文・速度・所要時間を見せてから RF
3. **[中止] は送信中いつでも効く。** 押した瞬間に電鍵線を落とし、PTT も下げる
4. 所要時間が上限 (既定 120 秒) を超える文は送信前に止める。
   暴走した AI 出力がそのまま長時間送信されるのを防ぐ

### 6.1 ポートを開く瞬間の危険

**多くの USB シリアル変換器は、ポートを開いた瞬間に DTR と RTS を H にする。**
何もしなければ**ポートを開いただけで電鍵が押され、キャリアが出続ける。**

- `serial.Serial(port, dsrdtr=False, rtscts=False)` で開き、**開いた直後に両線を落とす**
- **アプリ起動時にポートを開かない。** 送信の直前に開き、終わったら閉じる
- 初回の結線確認は**ダミーロードか無線機の電源を切った状態で**行う (取説に明記する)

### 6.2 線を上げっぱなしにしない

- 例外・中止・ダイアログを閉じる・アプリ終了 — **どの経路でも必ず両線を落とす**
  (`try/finally` と `closeEvent`)
- **番犬**: キー ON が連続で規定時間 (既定 5 秒) を超えたら異常とみなし、
  強制的に落として停止する。最長の長音でも 1 秒未満なので、5 秒続くのはバグかフリーズである

### 6.3 どうにもならない失敗

**送信中に USB を抜かれた場合、ソフトからは線を落とせない。** ポートが消えるため
`finally` も番犬も届かない。この場合は無線機側で止めるしかない。
取説に「送信中に USB を抜かない」と明記する。

アプリがクラッシュした場合は OS がポートを閉じ、通常は両線が落ちる。

## 7. シリアル層

### 7.1 構成

```
src/tx/
  encoder.py     テキスト → 符号列 → 要素列 (長さ秒, キー ON/OFF)
  keyer.py       要素列を時間どおりに叩く。ハードウェアを知らない
  serial_key.py  KeySink の実装。pyserial で DTR/RTS を上下させる
  reading.py     日本語 → カタカナ
  profile.py     経歴・読み辞書の保存と読み込み
```

**`keyer.py` はハードウェアを知らない。** `KeySink` という窓口に向かって叩く。

```python
class KeySink(Protocol):
    def key(self, on: bool) -> None: ...
    def ptt(self, on: bool) -> None: ...
```

本番は `SerialKeySink`、テストは記録するだけの `RecordingKeySink` を差す。
**打鍵タイミングをハード無しで検証できる。**

### 7.2 要素列の生成

既存の `src/synth/keying.py` の `_build_element_sequence` を再利用する
(公開名 `build_element_sequence` に改める。合成器と送信の 2 箇所から使うため)。

```python
codes = text_to_codes(katakana_text, mode="japanese")   # 既存
durations, is_on, _, _ = build_element_sequence(
    codes,
    word_break_after=(),          # WORD_BREAK_CODE が codes に入っている
    dot_sec=1.2 / wpm,
    dash_dot_ratio=3.0,
    inter_char_space_units=3.0,
    inter_word_space_units=7.0,
    intra_element_space_units=1.0,
)
```

**送信ではジッタを一切かけない。** 合成器は学習データに人間らしい揺れを混ぜるが、
送信は機械的に正確であるべきである。`KeyingParams` のジッタ σ は全て 0 にする。

試聴も**同じ `codes` から** `codes_to_waveform` で波形を作る。
**聴いているものと出るものが一致する。**

### 7.3 タイミングの担保

Windows の既定タイマ精度は約 15.6 ms、25 WPM の短点は 48 ms。そのままでは使えない。

1. **`timeBeginPeriod(1)`** — `winmm` を ctypes で呼び、タイマ精度を 1 ms に上げる。
   **送信中だけ。**終わったら `timeEndPeriod(1)` で戻す
2. **絶対時刻で刻む** — `sleep(要素の長さ)` を積み上げると誤差が累積する。
   開始時刻からの**累積目標時刻**を持ち、そこへ向けて待つ。1 要素の遅れが次に伝播しない
3. **混合待ち** — 目標の 2 ms 前まで `time.sleep`、最後は空回り (`while perf_counter() < target`)
4. **専用スレッド** — `QThread` で GUI と切り離し、優先度を上げる

**実測した揺れをダイアログに出す** ("短点 48 ms / 実測ずれ 最大 1.8 ms")。
数字が出ていれば、環境が悪化したときに気づける。

### 7.4 PTT

```
PTT ON → (先行 50 ms) → 打鍵 … 打鍵 → (後追い 100 ms) → PTT OFF
```

PTT を使わない設定 (無線機のブレークインに任せる) も選べる。

### 7.5 設定

`AppSettings` に `tx_` 接頭辞で追加する (既存の `llm_` `bpf_` と同じ流儀)。

| 設定 | 既定 | 内容 |
|---|---|---|
| `tx_port` | `""` | COM ポート名 |
| `tx_key_line` | `"DTR"` | 電鍵の線 (`DTR` / `RTS`) |
| `tx_ptt_line` | `"RTS"` | PTT の線 (`DTR` / `RTS` / `NONE`) |
| `tx_key_invert` | `False` | 電鍵の極性 |
| `tx_ptt_invert` | `False` | PTT の極性 |
| `tx_wpm` | `20.0` | 送信速度 |
| `tx_ptt_lead_ms` | `50.0` | PTT 先行 |
| `tx_ptt_tail_ms` | `100.0` | PTT 後追い |
| `tx_max_duration_s` | `120.0` | 送信の長さの上限 |
| `tx_key_watchdog_s` | `5.0` | キー ON が続いてよい上限 |
| `tx_wrap_hore_rata` | `True` | 和文をホレ/ラタで囲む |

**[線をテスト] ボタン**を付ける。電鍵線を 1 秒 ON にするだけで、テスターや LED で
結線を確認できる。

### 7.6 経歴と読み辞書の保存

設定ではなく**内容**なので、`settings.json` とは別ファイルにする。

```
~/.cw-decorder/operator.json
```

```json
{
  "callsign": {"display": "JH0ILL", "reading": "JH0ILL"},
  "name":     {"display": "太郎",  "reading": "タロウ"},
  "qth":      {"display": "横浜市", "reading": "ヨコハマシ"},
  "rig":      {"display": "IC-7300", "reading": "アイシー7300"},
  "antenna":  {"display": "ダイポール", "reading": "ダイポール"},
  "power":    {"display": "50W", "reading": "50ワツト"},
  "notes": "アマチュア無線歴 30 年。和文中心。趣味は…",
  "reading_dictionary": {
    "東京": "トウキョウ",
    "神奈川県": "カナガワケン"
  }
}
```

`notes` は第 2 段 (AI) で文脈として渡す。第 1 段では保存するだけ。

## 8. AI による返信案 (第 2 段)

既存の LLM プロバイダ層 (`src/llm/`) をそのまま使う。**新しいプロバイダは作らない。**

入力:

- 相手の清書 (直近のやり取り)
- 経歴の欄と `notes`
- 「返信を日本語で書く」指示

出力は `返信 (日本語)` 欄に入る。**そこから先は第 1 段と同じ経路**を通る
(カタカナ変換 → 検証 → 試聴 → 確認 → 送信)。

**AI の出力がそのまま電波になることはない。** 必ず人が読み、聴いてから送る。

温度は 0 に固定する (清書と同じ理由。`docs/llm_refine_result.md`)。

## 9. テスト

| 対象 | 方法 |
|---|---|
| 打鍵タイミング | `RecordingKeySink` + 偽の時計。要素列と累積目標時刻を検証 |
| 中止 | 送信中に中止フラグを立て、**両線が落ちる**ことを確認 |
| 番犬 | 異常に長いキー ON を注入し、強制停止することを確認 |
| ポートを開く瞬間 | 開いた直後に両線を落とす呼び出しが入っていることを確認 |
| カタカナ変換 | 読み辞書の優先、小書き→大書き、句読点、符号表に無い文字の検出 |
| 検証 | 送れない文字があるとき `[送信]` が無効になること |
| 試聴と送信の一致 | 同じ `codes` から波形と要素列が作られること |
| ダイアログ | 試聴前は `[送信]` が無効、編集で再び無効になること |

**実機を使うテストは自動化しない。** 電波が出るため。結線確認は取説の手順とする。

## 11. 法令について

送信は免許人の責任で行う。本機能は**電鍵を叩く道具**であって、
自動応答装置ではない。

- **人が読み、聴き、確認してから送る**設計を崩さない
- 自動送信・無人運用の経路は作らない
- 相手局の呼出符号と自局の呼出符号は運用者が確認する

## 12. 確認できていないこと

- **DTR/RTS がポートを開いた瞬間に H になるかは変換器による。** 実機で確認する必要がある
- **タイミングの揺れの実測値はまだ無い。** 実装後に測り、ダイアログに出す。
  許容できない場合は外部キーヤ (WinKeyer 等) への切り替えを検討する
- pykakasi の読み精度は語による。読み辞書でどこまで実用になるかは運用で確かめる
- 和文の `?` `-` `@` は符号が長く、デコード側の認識率がほぼ 0% である。
  送信はできるが、相手のデコーダによっては読まれない可能性がある
