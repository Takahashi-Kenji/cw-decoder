## 1. なぜ LAN 越しにするか

**アプリと無線機が別の PC にいる。**

| | この PC (GPU PC) | 無線機 PC |
|---|---|---|
| 役割 | デコード (torch/CUDA) | 無線機に繋がっている |
| 有線 | 192.168.0.20 | **192.168.0.10** |
| COM ポート | **1 本も無い** | 電鍵線・PTT 線がここに刺さる |

運用者は**無線機 PC の前に座り、リモートデスクトップで GPU PC のアプリを見ている**。
音声は `scripts/audio_send.py` が無線機 PC → GPU PC へ流している (ポート 45678)。

したがって:

* アプリの画面は RDP 経由で運用者の手元に出る → **送信ダイアログは既存アプリに置いてよい**
* 電鍵線は無線機 PC にある → **打鍵はあちらでやるしかない**

元の設計書は「アプリと無線機が同じ PC にいる」ことを暗黙の前提にしており
(`tx_port` = COM ポート名)、この構成では成立しない。

## 2. 役割分担

| 部品 | 置き場所 | 動く PC | 責務 |
|---|---|---|---|
| 送信ダイアログ | `src/app/tx_dialog.py` (新規) | GPU PC | 日本語入力、カタカナ確認、確認と送信の関門 |
| カナ変換 | `src/tx/reading.py` (既存) | GPU PC | 漢字かな交じり → カタカナ、読み辞書 |
| LAN クライアント | `src/tx/net_key.py` (新規) | GPU PC | 接続、`check`/`send`/`stop`、**心綱の拍** |
| **打鍵 CLI** | `scripts/cw_key_server.py` (新規) | 無線機 PC | 待ち受け、符号化、打鍵 |
| 符号化 | `src/tx/encoder.py` (既存) | 無線機 PC | テキスト → 符号 → 要素列 |
| 打鍵エンジン | `src/tx/keyer.py` (既存) | 無線機 PC | 要素列を時間どおりに刻む |
| シリアル | `src/tx/serial_key.py` (既存) | 無線機 PC | DTR/RTS を上下させる |

**既存の `src/tx/` 5 モジュールは 1 行も変更しない。** 実行される PC が分かれるだけ。
`keyer.py` が `KeySink` という窓口しか知らない設計になっているため、この分割が成立する。

### 2.1 なぜ「テキスト」を流し、「要素列」を流さないか

要素列 (長さと ON/OFF の並び) を GPU 側で作って流す案も検討したが、**テキストを流す**。

* **CLI が単独で使える。** GPU PC が落ちていても、運用者が座っている無線機 PC だけで
  打てる (`--text`、§7.2)。アプリはその CLI に文字を渡す一経路にすぎなくなる。
  ただし CLI はカナ変換を持たないので、単独で打つときは**カタカナと欧文で書く**
* ログがそのまま読める。`netcat` で叩ける
* 試聴を廃したため (§6)、「試聴した音と出る電波がずれる」という
  元設計書 §7.2 の懸念は発生しない

**代償**: 送れない文字の判定を、アプリ側 (表示用) と CLI 側 (実行用) の
両方が持つ。両 PC のリポジトリがずれると食い違う。

**歯止め**: (1) CLI は受け取ったテキストを**必ず再検証し、送れない文字があれば
打鍵せずに撥ねる** — ずれても出るのは誤った電波ではなくエラーである。
(2) `hello` で**符号表の指紋**を交換し、違えばアプリが繋いだ時点で警告する (§4.1)。

## 3. LAN に流すもの

**確定したテキスト**と**速度**だけ。

```
JH0ILL DE JA1ABC {HORE}コンニチハ、テンキ ハ ハレ{RATA} K
```

日本語 → カタカナの変換は**アプリ側**で済ませ、運用者が目で確認したあとの文字列を流す。
CLI はカナ変換を持たない (`pykakasi` は無線機 PC に不要)。

結線の設定 (COM ポート・DTR/RTS の役割・極性・PTT の有無・PTT の前後余裕・番犬) は
**流さない**。無線機に属する情報であり、アプリが知る必要がない。CLI 側の設定とする。

## 4. プロトコル

**1 行 1 メッセージの JSON** (UTF-8、`\n` 区切り)。テキストを流す以上、ログが読めて
`netcat` で叩けることに価値がある。

向きは音声と同じ。**無線機 PC が待ち受け、GPU PC が繋ぎに行く。**
運用の癖 (無線機 PC でスクリプトを起こしてからアプリを繋ぐ) が音声と揃う。

ポートは **45679** (音声の 45678 と分離)。同時に両方動く。

暗号化しない。家庭内 LAN 前提であり、外部に公開するポートに割り当てないこと。
`--bind` で待ち受けアドレスを絞れる。

### 4.1 メッセージ

**`hello`** (CLI → アプリ、接続直後に 1 回)

```json
{"type":"hello","protocol":1,"tokens_fingerprint":"a1b2c3d4",
 "wiring":{"port":"COM3","key":"DTR","ptt":"RTS"},"dry_run":false}
```

`tokens_fingerprint` は符号表 (`EUROPEAN_CHAR_TO_CODE` + `JAPANESE_CHAR_TO_CODES` +
マーカー) から決定的に作る短いハッシュ。`src/tx/fingerprint.py` (新規) に置く。

**`morse_tokens.py` は触らない。** 単一の真正ソースであり、変更すると
`scripts/export_tokens.py` の再実行が要る (CLAUDE.md)。指紋は読むだけの別モジュールにする。

アプリは自分の指紋と比べ、違えば**警告を出す**が接続は続ける (打鍵側の再検証が
本当の歯止めであるため、ここで塞ぐ必要はない)。

**`check`** (アプリ → CLI) — **打鍵しない検査**

```json
{"type":"check","text":"...","wpm":20.0}
```

CLI は符号化だけ行い、シリアルには触らない。

```json
{"type":"checked","chars":38,"elements":412,"seconds":34.2}
```

`chars` は送信テキストの文字数 (マーカーを 1 文字と数えない)。`seconds` は要素列の合計。

送れない文字があれば `error` (`code` は `unsendable`) を返す。

**`send`** (アプリ → CLI) — 打鍵する

```json
{"type":"send","text":"...","wpm":20.0}
```

完了すると打鍵の実測を返す。

```json
{"type":"done","elements_sent":412,"aborted":false,"watchdog_tripped":false,
 "seconds":34.2,"max_error_ms":1.8,"mean_error_ms":0.4}
```

**`stop`** (アプリ → CLI) — 直ちに中止。`{"type":"stop"}`

**`ping`** (アプリ → CLI) — 心綱の拍。`{"type":"ping"}`

**`error`** (CLI → アプリ)

```json
{"type":"error","code":"unsendable","message":"...",
 "unsendable":[{"index":12,"char":"髙"}]}
```

`code` は `unsendable` / `serial` / `busy` / `bad_request` / `lifeline` / `too_long`。

## 5. 心綱 (接続そのものを安全装置にする)

**LAN が止まったら打鍵を止める。**

* アプリは送信のあいだ TCP を張り続け、**0.25 秒ごとに `ping` を送る**
* CLI は**打鍵中のみ**、1.0 秒 (`--lifeline-timeout`) 何も受け取らなければ
  異常とみなして中止し、鍵と PTT を落とす
* `stop`・切断・拍の途絶は**すべて同じ停止経路**に合流する

**なぜ EOF だけでは足りないか**: ソケットが閉じたことはアプリが落ちれば分かるが、
**LAN ケーブルが抜けたときやアプリが固まったときには分からない** (TCP は黙ったまま)。
「止まったら止める」を字義どおり満たすには拍が要る。

**代償**: 1.0 秒を超える LAN の詰まりは正常な送信を途中で切る。有線側
(192.168.0.10) を使う前提なら実害は出にくいが、Wi-Fi 経由では切れうる。
閾値は CLI の引数に出す。

待機中は timeout を掛けない (掛けると接続が常に落ちる)。

## 6. 試聴は作らない

元の設計書は **試聴 → 確認 → 送信** の 3 段だった。**試聴は作らない** (2026-08-10 の判断)。

運用者は無線機の前に座っており、実際の送信は**無線機自身のサイドトーン**で聞こえる。
送信前の確認は画面のカタカナを目で読めば足りる。

代わりに **`check` が関門になる**。`[確認]` を押すと CLI が打鍵せずに符号化し、
文字数・所要秒数・送れない文字の有無を返す。**それが返って初めて `[送信]` が有効になる。**

ローカルのチェックボックスより強い。電波を出す前に次の 3 つが確定する:

1. CLI が生きていて繋がっている
2. そのテキストが**打鍵側の符号表**で通る
3. 何秒間 電波が出るのか

**編集したら `[送信]` は無効に戻る。** 確認していない文字列は送れない。

CLI は音を鳴らさない。無線機 PC に `sounddevice` の出力経路は要らない。

## 7. 打鍵 CLI (`scripts/cw_key_server.py`)

無線機 PC で動かす。`audio_send.py` と同じ流儀 (手で起こす、Ctrl+C で終わる)。

```
python scripts/cw_key_server.py --port COM3
python scripts/cw_key_server.py --port COM3 --ptt-line NONE --key-invert
python scripts/cw_key_server.py --dry-run          # シリアルに触らない
python scripts/cw_key_server.py --port COM3 --check-lines
python scripts/cw_key_server.py --port COM3 --text "CQ CQ DE JA1ABC K"   # 単発
```

### 7.1 引数

| 引数 | 既定 | 内容 |
|---|---|---|
| `--port` | (必須) | COM ポート名。`--dry-run` 時は不要 |
| `--key-line` | `DTR` | 電鍵の線 |
| `--ptt-line` | `RTS` | PTT の線 (`DTR`/`RTS`/`NONE`) |
| `--key-invert` / `--ptt-invert` | off | 極性 |
| `--ptt-lead-ms` | `50` | PTT 先行 |
| `--ptt-tail-ms` | `100` | PTT 後追い |
| `--key-watchdog-s` | `5.0` | キー ON が続いてよい上限 |
| `--max-duration-s` | `120.0` | 1 回の送信の長さの上限。超えたら `too_long` |
| `--lifeline-timeout` | `1.0` | 拍が途絶えたとみなす時間 |
| `--listen` | `45679` | 待ち受けポート |
| `--bind` | `0.0.0.0` | 待ち受けアドレス |
| `--dry-run` | off | **シリアルに一切触らない。**それ以外は全部通す |
| `--check-lines` | off | 結線確認モード (§7.4)。`--port` が要る |
| `--text` | — | 単発送信モード (§7.2)。LAN を待たない |
| `--wpm` | `20.0` | `--text` 使用時の速度 |

### 7.2 単発送信モード (`--text`)

LAN を待たず、渡されたテキストを 1 回打って終わる。GPU PC が落ちていても
無線機 PC だけで送れる経路を残すため。

**カナ変換は無い。**カタカナと欧文で書く (`{HORE}コンニチハ{RATA}`)。
送れない文字があれば打鍵せず、位置つきで表示して終了コード 1 で終わる。

心綱は無い (相手がいない)。**中止は Ctrl+C。**`finally` が両線を落とす。

### 7.3 ポートを開く時機

**起動時には開かない。送信の直前に開き、終わったら閉じる。**
`serial_key.py` の docstring どおり、開いた瞬間に DTR/RTS が H になる変換器があるため。
`check` はシリアルに触らないので、ポートを開かない。

### 7.4 `--check-lines` (結線確認モード)

LAN を待たず、電鍵線と PTT 線を**ゆっくり交互に上下させるだけ**。
テスターか LED で結線と極性を確かめる。

**必ず無線機の電源を切るかダミーロードで使うこと。**

元設計書 §7.5 の「[線をテスト] ボタン」の置き換え。ボタンはアプリ側 (GPU PC) にあっても
COM ポートがそこに無いので意味をなさない。

### 7.5 一度に 1 つ

同時に扱う接続は 1 つ。**打鍵中に来た `send` も `check` も `busy` で撥ねる。**
二重打鍵しないため、また `check` の符号化が打鍵の時間刻みを邪魔しないため。

待機中にもう 1 つ接続が来たら、`busy` を返して閉じる (先に繋いだ側を優先する)。

### 7.6 依存

無線機 PC に要るもの: **`pyserial`**、`numpy`。
`pykakasi` は要らない (カナ変換はアプリ側)。`sounddevice` も要らない (音を鳴らさない)。
`torch` は要らない。

無線機 PC にはリポジトリが既に置いてある (`audio_send.py` が動いている)。
**両 PC のリポジトリを揃えること。** ずれた場合は §2.1 の歯止めが働く。

## 8. アプリ側

### 8.1 設定

`AppSettings` に 2 つだけ足す。`CURRENT_SETTINGS_VERSION` を 14 → 15 に上げる。

| 設定 | 既定 | 内容 |
|---|---|---|
| `tx_endpoint` | `""` | 打鍵側の `host:port`。**空でも `[送信…]` は出す**（下記） |
| `tx_wpm` | `20.0` | 送信速度 (手動固定)。ダイアログで変えたら設定に書き戻す |

**`tx_endpoint` が空でも `[送信…]` ボタンは出す** (実装がそうなっており、そちらが
妥当なので設計をこちらに合わせた)。初回は必ず空であり、隠すと**設定を入れる場所が
どこにも無くなる** — 打鍵側の `host:port` を入れる欄はそのダイアログの中にしか
無いためである。空のまま開いても電波は出ない (接続していなければ `[確認]` も
`[送信]` も押せない)。

`tx_endpoint` の解析は `src/infer/net_audio.py` の **`parse_endpoint` を再利用する**
(既に `host:port` / `host` / IPv6 を扱える)。既定ポートだけ 45679 を渡す。

**元設計書 §7.5 の表は破棄する。** 結線系 (`tx_port` = COM ポート名、`tx_key_line`、
`tx_ptt_line`、`tx_key_invert`、`tx_ptt_invert`、`tx_ptt_lead_ms`、`tx_ptt_tail_ms`、
`tx_key_watchdog_s`、`tx_max_duration_s`) はすべて CLI 側へ移る。
`tx_wrap_hore_rata` は本文をホレ/ラタで囲むかの表示上の選択なのでダイアログ内の
チェックボックスとし、設定には持たない。

### 8.2 操作の流れ

```
日本語で書く → カタカナに直る → 目で確認 → [確認] → 秒数と結果が返る
   → [送信] が有効になる → [送信] → 打鍵
```

* 編集したら `[送信]` は無効に戻る
* 送信中は `[中止]` だけが押せる
* 未接続なら `[確認]` `[送信]` とも無効。理由を出す

### 8.3 接続の保ち方

**待機中は自動で繋ぎ直す** (`NetworkAudioCapture` と同じ流儀。打鍵側を後から起こしても繋がる)。

**送信中は繋ぎ直さない。** 切れたら中止として扱い、運用者に出す。繋ぎ直して
続きから打つようなことはしない — 何がどこまで出たのか分からない状態で電波を出さない。

### 8.4 経歴と読み辞書

元設計書 §7.6 のまま (`settings.json` とは別ファイル)。この設計では変えない。

## 9. 異常時のふるまい

| 起きること | 打鍵側 | アプリ側 |
|---|---|---|
| CLI が起きていない | — | 繋がらない。`[確認]` `[送信]` を無効にし理由を出す |
| 送信中に LAN が切れる / アプリが固まる | 1.0 秒で中止、**両線 OFF** | 接続断を表示 |
| `stop` を押した | 直ちに中止、両線 OFF | 中止したと表示 |
| COM を開けない (無い・使用中) | 打鍵しない。`serial` を返す | 表示する |
| 送れない文字が混じっていた | **撥ねる。打鍵しない** | 撥ねられた文字を位置つきで表示 |
| 送信中にもう一度 `send` | `busy` で撥ねる。**二重打鍵しない** | 送信中は `[送信]` を押せない |
| 長さの上限を超えた | `too_long` で撥ねる | 表示する |
| 符号表の指紋が違う | — | 警告を出す。接続は続ける |
| 送信中に USB を抜かれた | ソフトからは落とせない。`serial` を出して終わる | 表示する |
| CLI 自体が落ちた | 線はドライバ既定に戻る。**落ちる保証はない** | 接続断を表示 |

最後の 2 行は `serial_key.py` の docstring が言う「どうにもならない失敗」である。
**そのときは無線機側で止めるしかない。** 隠さず取説に書く。

## 10. テスト

### 10.1 この PC で通せるもの (COM ポート不要)

`--dry-run` があるため、LAN の経路は**端から端まで**この PC で試験できる。

| 対象 | 方法 |
|---|---|
| プロトコルの解析 | 不正な JSON・未知の `type`・欠けた欄を投げて `bad_request` |
| 再検証 | 送れない文字を含む `check`/`send` が `unsendable` で撥ねられる |
| **打鍵しないこと** | `check` がシリアルを一度も触らないこと (偽 sink で確認) |
| 心綱 | 拍を止めて中止すること、**両線が落ちること** |
| `stop` | 送信中に投げて中止すること、両線が落ちること |
| 切断 | ソケットを閉じて中止すること、両線が落ちること |
| 二重 `send` | 打鍵中の `send` も `check` も `busy` で撥ねること |
| 長さの上限 | `too_long` で撥ねること |
| 単発モード | `--text` が LAN 無しで打つこと、送れない文字で**打鍵せず**終了コード 1 |
| 繋ぎ直し | 待機中は繋ぎ直し、**送信中は繋ぎ直さず中止**として扱うこと |
| 指紋 | 表を変えると指紋が変わること、同じなら安定すること |
| 端から端まで | CLI を `--dry-run` で起こし、**本物の TCP** で `net_key` から叩く |
| 打鍵タイミング | 既存の型 (偽の時計 + `RecordingKeySink`) をそのまま使う |
| ダイアログ | 確認前は `[送信]` 無効、編集で無効に戻ること |

**テスト駆動で進める** (CLAUDE.md)。実装前にテストを書く。

### 10.2 実機でしか確かめられないもの

**自動化しない。電波が出るため。** 取説の手順とする。

1. **ポートを開いた瞬間に DTR/RTS が H にならないか** (`--check-lines`、無線機の電源オフ)
2. 電鍵線・PTT 線の割り当てと極性 (テスターか LED)
3. タイミングの実測ずれ (`done` の `max_error_ms` が短点長に対し十分小さいか)
4. PTT の前後余裕が足りているか

## 11. 確認できていないこと
