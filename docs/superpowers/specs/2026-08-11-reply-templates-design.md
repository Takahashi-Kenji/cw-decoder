## 1. 何を作るか

**返信の文案を用意する道具**である。出どころは 2 つあり、置き場は 1 つにする。

| 型の出どころ | いつ作る | 使う場面 |
|---|---|---|
| **前もって登録** (10 個ほど) | 交信の外で運用者が書く | **こちらが主導するとき** (CQ、こちらから呼ぶ、締め) |
| **LLM の案を保存** | 交信中に良い案が出たとき | 相手に応答するとき |

こちらが主導する場面には受信内容が無いので、**LLM の出番がない**。前もって書いた型を呼ぶのが確実である。

## 2. 段階

**第 1 段だけで CQ と定型交換が回る。** LLM は要らない。第 2 段が落ちても第 1 段は動く。

| 部品 | 段 | 責務 |
|---|---|---|
| `src/tx/templates.py` (新) | **1** | 型の保存・読み込み・欄の差し込み・検証 |
| `src/tx/qso_fields.py` (新) | **1** | 受信テキストから相手のコール・名前を拾う |
| `src/app/tx_dialog.py` (改) | **1** | 型の選択、拾った欄、差し込み、**赤字判定の修正 (§3)** |
| `src/llm/base.py` ほか (改) | **2** | `chat()` を足し、`transform()` をその上に書き直す |
| `src/llm/reply.py` (新) | **2** | 返信案のプロンプトと生成 |

第 1 段が終わった時点で一度使ってもらい、第 2 段はその後に着手する。

## 3. 【最初に直す】画面の赤字判定が壊れている

**いま出荷されている画面の欠陥である。** 送信ダイアログは `reading.find_bad_chars` で
「送信できない文字」を出しているが、**これは和文表だけで照合している**
(`_SENDABLE = frozenset(JAPANESE_CHAR_TO_CODES) | {" "}`)。

実測:

```
JA1ABC DE JH0ILL {HORE}コンニチハ{RATA} K
  画面の判定   : JAABCDEJQCWK が送れない   <- 誤り
  打鍵側の判定 : 問題なし                   <- 正しい
```

**定型交換は必ずコールサインを含む。** この機能を作る前に直さないと使い物にならない。

**直し方**: 画面が赤く出す判定を、打鍵側と同じ `encoder.find_unsendable` に寄せる
(モードを見る正しいほう)。`reading.find_bad_chars` は「カタカナ変換で落ちなかった
漢字等」を見るためのものとして残すが、**画面の可否判定には使わない**。

これは設計書 `2026-08-10-lan-cw-transmit-design.md` §2.1 が「代償」として挙げた
食い違い (アプリ側と CLI 側が別の規則で判定する) の、アプリ側が誤っていた分である。

## 4. 型の形

置き場は `~/.cw-decorder/templates.json`。**経歴 (`operator.json`) と同じ流儀で、
設定 (`settings.json`) とは分ける。** 設定ではなく内容だからである。

```json
{
  "templates": [
    {
      "name": "応答",
      "mode": "japanese",
      "text": "{相手コール} DE {自局コール} RST {RST} {HORE}コンニチハ、ヨロシク{RATA} K"
    }
  ]
}
```

| 欄 | 内容 |
|---|---|
| `name` | 画面の一覧に出す名前 |
| `mode` | `"european"` / `"japanese"` / `"any"`。**デコーダのモードに合う型だけを一覧に出す** |
| `text` | 本文。漢字かな交じりで書いてよい (§6 の順序で変換を通る) |

### 4.1 差し込む欄

**これだけに絞る。** 増やすほど型が書きにくくなる。

| 欄 | どこから |
|---|---|
| `{自局コール}` `{名前}` `{QTH}` `{リグ}` `{アンテナ}` `{出力}` | 経歴 (`OperatorProfile`) |
| `{相手コール}` `{相手名前}` | 拾った値、または運用者が打った値 |
| `{RST}` | **運用者が決める欄** (既定 `599`) |

**`{RST}` は「こちらが相手に与える RST」である。** 相手からもらった値ではない。
混同すると誤った電波が出るので、**相手の RST は拾わない** (§5)。

### 4.2 知らない `{…}` はそのまま残す

これが効くのは `{HORE}` と `{RATA}` である。型の中に書いたマーカーが差し込みで壊れない。

**差し込み漏れは安全側に倒れる。** `{相手コール}` が埋まらないまま送ろうとすると、
`{` や `相` が符号表に無いので**送信できない文字として赤く出て、送信が止まる**。
`{相手コール}` という文字列が黙って電波に出ることはない。

**ただしそのメッセージは不親切である。** 実測 (相手コールを埋めずに通した結果):

```
送信できない文字があります: {}DEJQCWRST
```

埋め忘れた欄が変換器を通ってカタカナになり、そのせいでモードが和文に倒れ、
**関係のない欧文まで巻き添えで並ぶ**。原因が読み取れない。

そこで**差し込みの直後に、埋まらなかった欄が無いかを名指しで調べる**。

```
埋まっていない欄があります: 相手コール
```

符号化による歯止めは残す (二重の守り) が、**運用者が読むのはこちらである**。

### 4.3 保存するときに検証する

**型に書く欧文はホレの外に置く必要がある。** 実測:

```
... {HORE}コンニチハ、RST 599 デス{RATA} K
                       ~~~ 和文モードの中なので R S T が送れない
```

運用上も正しい姿だが (RST は欧文で送る)、**型を書くときに間違えやすい**。
保存時に、欄をすべて埋めた状態で `encoder.find_unsendable` に通し、
送れない文字があれば**警告して理由を見せる**。交信中に気づくのでは遅い。

**警告しても保存は妨げない。** 書きかけの型を保存できないと、育てるのが苦痛になる。
一覧では送れない型に印を付け、選んだときにも警告を出す。

## 5. 欄の拾い方

**`DE` を手掛かりにする。** CW は `<相手> DE <自分>` の順で送るので、
**`DE` の次に来るのが送信者 = 相手のコール**である。

```
JH0ILL DE JA1ABC K
       ~~~~~~~~ 相手のコール
```

`DE` が無いときは、コールサインの形をした語のうち**自局のコールでないほう**を採る
(経歴の `{自局コール}` と突き合わせる)。

拾うのは 2 つだけである。

| 欄 | 拾い方 | 確実さ |
|---|---|---|
| **相手コール** | `DE` の次。無ければ自局でないコール形の語 | 高い |
| **相手名前** | `NAME` / `OP` / `ナマエ ハ` の次 | **当てにならない** |

**相手の RST は拾わない** (§4.1 の理由)。

**拾えなかった欄は空のままにする。** 当てにならないものを黙って埋めない。
名前は特に外しやすいので、「拾えませんでした」と分かる見せ方にする。

### 5.1 入力は清書済みテキスト

`main_window` が持つ**清書済みテキスト** (`_llm_refined_html` に積んだもの) を、
ダイアログを開くときに渡す。生のデコード (`_committed_text`) より誤りが減っている。

**清書結果には推測箇所の `⟦…⟧` マーカーが入っている** (`src/llm/markup.py`)。
拾う前に外すこと。清書していない (LLM を使っていない) ときは `_committed_text` を渡す。

## 6. 画面

送信ダイアログに 2 行足す。

```
打鍵側 [192.168.0.10:45679] [接続]        速度 [20.0] WPM
相手 [JA1ABC]  相手名前 [    ]  送る RST [599]        <- 拾った欄 (直せる)
型  [応答          ▼] [型を使う]                       <- 第 2 段で [返信案] [型として保存] が増える
日本語 (漢字かな交じりで可):
...
```

### 6.1 型を使う順序

**欄を差し込んでから日本語ボックスへ入れる。** 逆にすると `{相手コール}` が
変換器 (pykakasi) を通って壊れる。

日本語ボックスに入れるので、**型は漢字かな交じりで書ける**。変換も関門も既存の経路が
そのまま働き、**`[送信]` は無効に戻る** (確認していない文字列は送れない)。

### 6.2 マーカーの前後に語間が入る

実測: `{HORE}こんにちは{RATA}` は変換後 `{HORE} コンニチハ {RATA}` になる。
符号上は語間が 1 つ増えるだけで、**壊れてはいない**。今回は許容する。

## 7. LLM の入口 (第 2 段)

いまの `LLMProvider` は `transform(生テキスト, モード)` しか持たず、**中で清書用の
プロンプトを固定して呼んでいる**。別の問いを投げる口が無い。

`chat(messages, *, timeout) -> LLMResult` を `LLMProvider` に足し、
**`transform()` をその上に書き直す**。

```python
def transform(self, raw_text, mode, *, timeout, lead_text=None, compact=False):
    return self.chat(build_messages(raw_text, mode, lead_text, compact), timeout=timeout)
```

各プロバイダの HTTP の形 (Claude は system を分ける、OpenAI/Ollama は messages 一本) は
そのまま `chat` に移る。**清書の中身は 1 行も変わらない。**

選ぶ理由は 2 つ。3 プロバイダに似たコードを二重に持たずに済むこと。そして
**既存の清書のテストがそのまま安全網になる**こと — `transform` の振る舞いが
変わっていないことを、既にあるテストが保証する。

返信案のプロンプトは `src/llm/reply.py` に置き、清書用 (`src/llm/prompt.py`) とは分ける。
**目的が違うプロンプトを同じファイルに混ぜない。**

### 7.1 コールサインと RST は LLM に書かせない

**文章は LLM に作らせるが、`{相手コール}` と `{RST}` は拾った値・打った値を
そのまま差し込む。** LLM に返す形は「型と同じ `{…}` 入りの本文」とし、
差し込みは §4 と同じ経路を通す。

文面の自由度を落とさずに、**LLM が相手のコールを作り変える事故だけを構造的に防ぐ**。

### 7.2 気に入った案を型として保存する

`[型として保存]` で、いま日本語ボックスにある文を型にする。名前を聞く。
**差し込んだ後の文ではなく、`{…}` の入った元の文を保存する** (使い回せなくなるため)。

## 8. 異常時のふるまい

| 起きること | どうする |
|---|---|
| 型ファイルが壊れている | 空として扱い、画面に出す。**既存のファイルを上書きしない** |
| 差し込み漏れ (`{相手コール}` が空) | **埋まらなかった欄を名指しで出す** (§4.2)。符号化の歯止めも残す |
| 相手コールが拾えない | 欄が空。運用者が打つ |
| 相手名前が拾えない | 欄が空。**当てにならないので黙って埋めない** |
| 送れない型を保存しようとした | 警告して理由を見せる。**保存は妨げない** (§4.3) |
| 一覧に合う型が無い | 「この モードの型がありません」と出す |
| LLM が落ちている (第 2 段) | **型は使える。**第 1 段は無傷 |
| LLM が `{…}` を壊して返した | 差し込み後に検証し、送れない文字として見せる |

## 9. テスト

**LLM もデコーダも実機も無しで全部試験できる。**

| 対象 | 方法 |
|---|---|
| 型の保存・読み込み | 一時パス。**利用者の実ファイルを壊さない** (`profile.py` と同じ約束) |
| 壊れたファイル | 空として扱い、上書きしないこと |
| 差し込み | 経歴と拾った値が入ること |
| `{HORE}` が残ること | 知らない `{…}` を触らないこと |
| 差し込み漏れ | **埋まらなかった欄を名指しで出すこと。**符号化でも弾かれること |
| 型の検証 | ホレの中に `RST` を書いた型が警告されること |
| コールの抽出 | `DE` の次を採ること。`DE` が無いとき自局でないほうを採ること |
| 抽出できないとき | 空のままであること (**でたらめを埋めないこと**) |
| `⟦…⟧` の除去 | 清書のマーカーを外してから拾うこと |
| モードの絞り込み | 合わない型が一覧に出ないこと |
| 画面 | 型を使うと**関門が閉じ直る**こと (offscreen) |
| 赤字判定 (§3) | コールサインを含む文が誤って赤くならないこと |
| LLM (第 2 段) | 偽のプロバイダを差す (`chat()` が入口なので差しやすい) |

## 10. 確認できていないこと

- **相手名前の抽出がどれくらい当たるかは未知。** 実際の交信で確かめる。
  当たらないようなら欄を残したまま抽出だけやめる
- **10 個という数に根拠は無い。** 運用者の見込み。増えて困るようなら分類を足す
- **LLM が和文の返信案をどれくらい書けるかは未知。** 清書では実績があるが、
  作文は別の能力である。第 1 段を使ってもらってから着手する
