# 実信号評価基盤の整備 (Phase A 残り) — 設計書

作成日: 2026-07-18
対象: `cw-decorder` / CODEX_REVIEW_RESULT.md §6 Phase A の残タスク
前提: Phase A の metrics 拡張・詳細 JSON 出力は実装済み
(`feature/eval-token-error-analysis`, コミット 8ffbd8f/ddbbd4f/fdafede)

## 1. 目的

CW デコーダの認識率改善の「改善前後を定量比較できる評価基盤」を完成させる。
今回の作業は **評価セットの整備** と **評価の正確さの修正** に絞り、
モデル・推論ロジック本体は変更しない (Phase B 以降)。

## 2. 調査で判明した事実 (この設計の根拠)

ユーザー提供の実データ (打鍵録音20件 + 実ノイズ22分) を今回の評価基盤で
分析して、以下を **実測** で確認した。すべて再現スクリプトは作業時のもの。

### 2.1 合成器のノイズは受信機 BPF の前に加わる → SNR が 9.5 dB 甘い

`synthesize_from_text` の処理順は `... → AWGN → 受信機 BPF`
(`synthesizer.py:105-115`)。AWGN は広帯域に乗るが直後の BPF が帯域外を捨てる
ため、**公称 SNR と BPF 後の実効 (帯域内) SNR に約 +9.5 dB の差** が出る。

| 公称 SNR (学習で指定) | BPF 後の実効 SNR |
|---|---|
| +20 dB | +29.5 dB |
| 0 dB | +9.5 dB |
| −5 dB | +4.4 dB |
| −10 dB (学習の最低値) | −0.5 dB |

学習は `snr_db = uniform(-10, 20)` なので、実効では **−0.5〜+29.5 dB** しか
学習していない。ノイズを BPF 前に置く順序自体は物理的に正しい (実受信機でも
ノイズはフィルタ前段から入る)。問題は **SNR をフィルタ前の値で指定・記録** して
いるため難易度を 9.5 dB 過大評価している点。

### 2.2 実ノイズ 0 dB で TER が崖のように崩壊 → 実運用 50% 頭打ちと一致

合成キーイング + ユーザー実ノイズ (帯域内、下駄なし) の SNR ラダー:

| WPM | 実ノイズ SNR | TER | 短点のみ recall | 長点のみ recall |
|---|---|---|---|---|
| 17 | +5 | 1.5% | 100% | 100% |
| 17 | **0** | **44.7%** | 52.2% | 63.0% |
| 17 | −5 | 96.0% | 5.4% | 9.1% |
| 25 | **0** | **53.5%** | **33.3%** | 60.9% |
| 25 | −5 | 93.2% | 8.9% | 12.2% |

- +5 dB → 0 dB で TER が **1.5% → 45%** と崖。0 dB 付近が実運用「50% 頭打ち」の正体。
- ノイズ下では **短点連続が長点連続より明確に弱い** (25 WPM 0 dB で 33% vs 61%)。
  速度が上がるほど短点が悪化 = ユーザー体感「EIH5 が落ちる」を裏付ける。

### 2.3 6要素符号 (プロサイン・記号) の認識が壊滅

打鍵20件 (高 SNR) での符号長別 recall:

| 符号長 | 出現 | recall |
|---|---|---|
| 1〜5 | 多数 | 94〜98% |
| **6** | 15 | **26.7%** |

内訳: `?`(`・・--・・`) recall 0% (5回全脱落)、`[SK]`(`・・・-・-`) 0%、
`[ラタ]`/`[SN]`(`・・・-・`) 0% (7回全置換)、`[ホレ]`(`-・・---`) は認識 85.7% だが
**無い所に7回幻覚挿入**。高 SNR でも壊れているので、ノイズではなくモデルの問題。

### 2.4 WORD_BREAK 過剰検出が最大の誤り源

打鍵20件で挿入誤り53件中 **33件 (62%) が WORD_BREAK**。和文で顕著
(`テンキハクモリ` ⇄ `テンキ ハ クモリ`)。和文の CER が TER の2倍以上になる主因。

### 2.5 録音先頭のゴミトークン (AGC 初期ランプ疑い)

複数の録音で先頭に無い符号 (`?E TU ES...`, `RE6E GY5...`)。合成では出ない、
実受信経路由来の現象。Codex 原因候補 #4 と一致。

### 2.6 ユーザーのセットアップ実測値

- トーン: **494〜496 Hz** (20件すべて安定)。学習既定の 600 Hz とずれ。
- 実効速度: 14.6〜19.4 WPM (原稿の 24 WPM 見積より遅い)。
- 実ノイズ: エネルギーの 97.6% が 300〜550 Hz (受信機 BPF 後の帯域ノイズ)。

## 3. 評価セット設計

性質の異なる3つの評価セットを **別々に** 保持・報告する。1つに混ぜると
「ノイズ耐性は上がったが実信号は変わらない」を見逃す。

| セット | 中身 | 役割 | 分散 |
|---|---|---|---|
| `synth_val` | 合成キーイング + 実ノイズ、実効 SNR グリッド、seed 固定 | 主指標 (改善追跡) | 小 |
| `keyed_val` | 打鍵20件から6件を予約 | 実受信経路の健全性診断 (AGC 先頭ゴミ等) | 大 |
| `onair_val` | 実 QSO の切り出し (未整備、次フェーズ) | 本命の標的 | 大 |

### 3.1 synth_val (主指標)

- `make_fixed_eval_set` を実ノイズ対応に拡張 (決定的生成を維持)。
- SNR グリッドは **実効 (帯域内) SNR で指定・記録** する。§2.1 の下駄を消す。
- グリッド案: WPM {17, 25} × 実効SNR {+10, +5, 0, −5} × mode {eu, ja}。
  0 dB 前後を厚くする (崖の周辺が改善追跡の主戦場)。
- ノイズは `data/noise/val/` (train と別録音) から供給。同じノイズ波形が
  train と val の両方に入るとモデルがノイズ自体を覚えるため分離必須。

### 3.2 keyed_val (診断用)

- 打鍵20件のうち **原稿ベースで6件を val 予約** (残り14件は train)。
- モード別に評価できるよう欧文3・和文3を目安に予約。
- 主指標にはしない (打鍵の癖がオンエア代表でないため)。合成では出ない
  実受信経路の現象 (先頭ゴミ) を捕まえる診断値として使う。

### 3.3 onair_val (本命、今回は枠だけ)

- 単位: 80秒丸ごとではなく **5〜20秒に切る** (学習分布 3〜30秒に合わせる、
  ラベルの正確さ確保)。
- 量: 参照トークン数で管理。**欧文40区間・和文20区間 (各 ~1000 / ~600 トークン)**
  を初期目標。TER 50% 付近で 10ポイント改善を検出するのに必要。
- 中身: **他局の送信のみ** (自局サイドトーン除外)、S5〜S7 の「読めるが楽でない」
  信号を優先、速度・混信・QSB・日/バンド/局を分散。
- 鉄則: **自信のない区間は捨てる**。誤ラベルは1件でも指標を壊す。
- 限界: 人間が読めない信号はラベル化できないため val は「人間可読域」に偏る。
  受け入れる制約として明記する。

## 4. コード変更

モデル・推論・特徴量・decode は変更しない。評価と収集の周辺のみ。

### 4.1 実効 SNR ユーティリティ (`src/synth/noise.py`)

- 信号とノイズを受信機 BPF に通した後のパワー比から実効 SNR を計算する
  純関数 `effective_snr_db(sig, noise, center_hz, bandwidth_hz, sr)` を追加。
- 逆に「目標実効 SNR」からノイズスケールを決める補助も追加し、synth_val 生成が
  実効 SNR グリッドを直接指定できるようにする。
- 既存 `add_awgn` / `add_real_noise` / `apply_cw_filter` は変更しない。

### 4.2 固定評価セットの実ノイズ対応 (`src/synth/dataset.py`)

- `make_fixed_eval_set` に `noise_pool` / 実効SNRグリッド引数を追加
  (デフォルト None で **既存挙動を完全維持**)。決定的生成を保つ。
- 実ノイズ指定時は「高SNRクリーン合成 → 実効SNR目標で実ノイズ加算」
  (学習経路と同じ手順)。

### 4.3 metrics に実効 SNR 別集計 (`src/train/metrics.py`)

- 既存 `EvalReport.by_snr` は公称 SNR ビン。新たに **実効 SNR** で集計できる
  よう `EvalRecord` に `eff_snr_db` を追加 (任意フィールド、デフォルト None、
  既存テストに影響なし)。
- `DetailedEvalReport` の JSON に実効 SNR 別内訳を含める。

### 4.4 固定 val での評価 (`scripts/finetune.py`)

- `--eval-dir` を追加。指定時は乱数分割 (`split_train_validation`) の代わりに
  そのディレクトリを固定 val とする。`--data-dir` は train 専用になる。
- 既存の `--eval-ratio` 経路は後方互換で残す。
- synth_val / keyed_val を別々に評価してログ・JSON に分けて出す。

### 4.5 ラベル検品ツール (`scripts/inspect_real_labels.py`)

- 今回の分析スクリプトを製品化。録音を原稿/ラベルと照合し、TER 降順で
  「打鍵ミス疑い」を提示。符号長別 recall、token 別 recall、confusion を出力。
- 新規録音のラベル品質を **聴かずに** 検査する運用ツール。

### 4.6 オンエア切り出しツール (`scripts/clip_onair.py`)

- 長い QSO 録音から時間区間を指定して 5〜20秒に切り出し、ラベルを付けて
  `data/real/onair/` に実信号 TXT 形式で保存する。
- ラベルは `text_to_codes` で即検証 (`apply_script_label` と同じ方式)、
  トークン化不能なら弾く。

### 4.7 ラベル書式の往復修正 (`src/tokens/converter.py` 周辺 or 収集ツール)

- 現状 `TokenConverter` の出力 (`[ホレ]`, `[SK]`, `?`) は `text_to_codes` が
  受理しない (`[` で KeyError、`?` は疑問符符号と衝突)。オンエアの擬似ラベル
  運用にはこの往復が必須。
- 方針: 収集ツール側に **正規化関数** を置き `[ホレ]→{HORE}`, `[ラタ]→{RATA}`,
  `[SK]→{SK}` へ変換する。`[SN]`/`[KN]`/`[HH]` は合成入力マーカーが未定義のため、
  当面その区間を採用しない運用とする (§4.6 の鉄則に従う)。
- `?` の扱いを一意に決める: ラベル本文の `?` は **常に疑問符符号** (`・・--・・`)
  として扱う。「判別不能」を `?` で表す旧運用は誤ラベルの温床なので廃止し、
  判別不能な区間は **その区間ごと捨てる** (中途半端に埋めない)。
  収集ガイド (`phase4_data_collection.md`) の該当記述もこの方針に更新する。
- **注意 (ラベル vs UI 表示)**: 上記は「学習・評価の正解ラベル」の話。
  ライブ UI で低信頼度・表未定義をどう見せるか (非表示 / 赤字 `?` の切替え) は
  別軸の表示機能であり、§7 に切り出す。ラベル方針とは独立。
- `morse_tokens.py` の符号定義・語彙は変更しない (単一ソース維持)。

### 4.8 データ保護 (`.gitignore`)

- `data/keying_scripts/*.wav` を追加 (原稿 TXT は追跡継続、wav のみ除外)。
  `noise_sample.wav` は 87MB あり、誤コミットすると履歴に残り取り返しがつかない。
  現時点で対象 wav はすべて未追跡 (`git status` で `??`) なので、除外追加だけで
  安全。既にコミットされていないことを実装時に再確認する。

## 5. テスト方針

- `effective_snr_db`: BPF 後パワー比と一致する数値テスト (§2.1 の +9.5 dB を再現)。
- `make_fixed_eval_set` の実ノイズ対応: 決定性テスト (同 seed → 同結果)、
  noise_pool=None で既存出力が bit 一致すること。
- `EvalRecord.eff_snr_db`: 既存 metrics テストが壊れないこと + 実効SNR別集計。
- ラベル正規化: `[ホレ]→{HORE}` 等の往復が `text_to_codes` を通ること。
- 切り出しツール: 区間指定・境界・トークン化不能ラベルの拒否。
- 既存 538 テストを壊さない。符号表の e-Gov 照合は不変。

## 6. スコープ外 (Phase B 以降)

今回の発見はすべて Phase B の標的だが、この設計では **対策を実装しない**。
評価基盤で「改善したか」を測れる状態を作るところまで。

- SNR 学習範囲の拡張 (実効 −5 dB まで) — §2.1/2.2
- WORD_BREAK 閾値・損失調整 — §2.4
- プロサイン/6要素符号の認識改善 — §2.3
- AGC 初期ランプ除外 — §2.5
- トーン中心のピーク追従 (494 Hz 実測) — §2.6
- 短点連続の後処理 — §2.2

## 7. 別件メモ: 判別不能の UI 表示切替え (Phase A 外)

ユーザー要望。**今回のスコープ外**、別ブランチ・別 PR で対応する。ここには
実装に必要な情報だけ記録する。

- 要望: ライブ UI で判別不能 (低信頼度 `LOW_CONFIDENCE` / 表未定義 `TABLE_MISS`)
  の箇所を「**記さない**」か「**赤字の `?`**」で表示するか切り替えたい。
- 既存資産: `ConvertResult.fallback_log` に `FallbackEvent` (position / input_index /
  token_id / code / kind / confidence) が既にある (`converter.py`)。表示側
  (`workers.py` の `committed_text_changed` / `provisional_text_changed`) が
  これを使っていないだけ。符号→文字変換ロジックの変更は不要。
- 実装の骨子: 設定に表示モード (hide / red-question) を追加し、変換後テキストの
  fallback 位置を表示側で加工 (削除 or 装飾)。位置ずれ防止のため
  `fallback_log[].position` を使う。
- ラベル (§4.7) とは無関係。学習・評価の正解には一切影響しない。
