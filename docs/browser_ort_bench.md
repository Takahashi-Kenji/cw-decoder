計測日: 2026-08-05
モデル: models/full/best_infer.pt → web/public/model/cw.onnx (17,384,186 bytes)

このタスクではブラウザを操作できないため、以下の 2 系統に分けて記録する。

- **Node 計測** (このタスクで実測済み): `onnxruntime-web` を Node.js から
  import すると `package.json` の `"node"` export 条件により
  `dist/ort.node.min.mjs` が解決される。これはネイティブアドオン
  (`onnxruntime-node`) ではなく、ブラウザ版と**同じ** `ort-wasm-simd-threaded.wasm`
  バイナリを Node 上で動かすビルドである (`web/node_modules/onnxruntime-web/dist/`
  で実ファイルを確認済み)。そのため wasm バックエンドの性能の代理として意味がある。
- **ブラウザ計測**: 未実施。**コントローラが後で埋める。**
  `cd web && npm run dev` でサーバを起動し、表示された URL に `?threads=1` を
  付けて開き 1 スレッドの数値を、別タブで `?threads=4` を付けて開き
  4 スレッドの数値をそれぞれ読むこと (`web/src/bench/bench.ts` のページ本文および
  devtools コンソール出力)。**同一ページ内で両方測ろうとしないこと** —

## 実測: Node (onnxruntime-web wasm バックエンド)

実行環境:
- CPU: Intel(R) Core(TM) i7-14700F (論理コア数 28)
- Node.js: v25.2.1
- onnxruntime-web: 1.27.0 (`^1.20.0` の範囲内で解決された最新版)
- 実行コマンド: `cd web && npm run bench:node` (`web/scripts/bench-node.mjs`)
- 計測方法: 5.0 秒・8.5 秒のトーンバースト波形 (`Math.sin(2π·600·t)` ×
  `Math.sin(2π·4·t) > 0` のエンベロープ、8000 Hz)、ウォームアップ 1 回のあと
  5 回実行の平均

**重要な落とし穴 (計測中に発見):** ORT Web の wasm スレッドプールは、プロセス内で
最初に `InferenceSession.create()` を呼んだ時点の `numThreads` に固定される。
同一プロセス内で `ort.env.wasm.numThreads` を後から変更しても反映されない。
ブリーフの元の `bench.ts` はページ内で `benchmark(1)` → `benchmark(4)` の順に
同一ページ・同一 wasm ランタイムで呼ぶ構造だった。これを検証するため一時的に
単一プロセスで 1→4 の順に計測したところ、4 スレッド側も 1 スレッド相当の速度の
ままだった (8.5 秒で 155.9 ms、フレッシュプロセスで 4 スレッドを最初から設定した
場合の 57 ms 前後と食い違う) ことを確認した。

この発見を受けて **`web/src/bench/bench.ts` をブリーフから変更した**:
`benchmark(1)` → `benchmark(4)` を連続で呼ぶのをやめ、URL クエリパラメータ
`?threads=N` で指定した 1 つのスレッド数だけをそのページ読み込みで計測する
構成にした。1 スレッドと 4 スレッドを両方測るには `?threads=1` と `?threads=4`
でページを別々に開き直す必要がある (詳細は `web/README.md` および
`web/src/bench/bench.ts` 冒頭のコメント参照)。`web/scripts/bench-node.mjs` も同じ理由で
スレッド数ごとに**別プロセス**を起動する構成にした。

### 再現性・ばらつきについて

上表は `npm run bench:node` の 1 回分。念のため 4 スレッド条件のみ独立に 3 回
追加実行したところ、8.5 秒の値は 51.8 ms 〜 128.6 ms の範囲でばらついた
(多くは 50〜60 ms 台、1 回だけ 128.6 ms の外れ値)。1 スレッド条件は複数回とも
153.8 ms 〜 156.9 ms とほぼ安定していた。4 スレッド側のばらつきは、このマシンが
他プロセスと共有されている環境でのスレッドスケジューリングの影響と推測されるが、
原因の特定はしていない。上表の値は代表的な 1 回の実行結果であり、4 スレッドの
下限は 30〜35 ms 台 (5.0 秒) / 50 ms 台 (8.5 秒) 程度、悪いケースでは 130 ms 近くまで
悪化しうる、という幅を持って読むこと。

## 判定

- **(a) LSTM は動いたか**: 動いた。ONNX Runtime Web の wasm バックエンド (Node 版
  ビルド、ブラウザ版と同一の wasm バイナリ) で `InferenceSession.create` および
  `session.run` がエラーなく完了し、出力フレーム数も期待通り (5.0 秒→501,
  8.5 秒→851) だった。設計全体の前提を崩すブロッカーは見つからなかった。
- **(b) 8.5 秒のデコードが hop 1.0 秒に対して余裕があるか**: Node 計測の限りでは
  大きな余裕がある。1 スレッドでも 155.5 ms (RTF 0.018)、4 スレッドなら
  代表値 58.3 ms (最悪ケースでも 128.6 ms) であり、hop 1.0 秒は全く問題にならない
  水準。設計書 §3 の事前見積もり (0.2〜0.45 秒) よりも大幅に速かった。
  **ただし、これは Node (wasm バックエンド) の数値であり、ブラウザでの実測は
  別途必要。** Node と実ブラウザでは JIT・メモリ管理・タブのスロットリング等の
  条件が異なりうるため、この判定は「ブラウザでも同程度なら」という条件付き。
- **(c) hop 0.5 秒にできそうか (デコード時間 < 0.35 秒か)**: Node 計測では
  1 スレッドの 155.5 ms でも 0.35 秒を大きく下回っており、余裕を持って満たせそう。
  ブラウザ確認待ち。

## 判定に基づく決定

Node 計測の結果は良好だが、ブラウザでの実測が済むまでは最終決定を保留する。
ブラウザ計測でも同水準 (少なくとも 1 スレッドで 8.5 秒が 0.35 秒未満) であれば、
以下を採用可能と考えられる。**コントローラがブラウザ計測後に確定させること。**

- `hop_s` の採用値: (ブラウザ確認待ち。Node 数値だけを見れば 0.5 秒でも余裕がある)
- `decode_left_context_s` の採用値: (ブラウザ確認待ち。変更不要の可能性が高い)
- int8 量子化の要否: (ブラウザ確認待ち。Node 数値だけを見れば不要と考えられる)
