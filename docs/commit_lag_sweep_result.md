# commit_lag 掃引 結果

実施日: 2026-08-05（初回測定）/ 2026-08-06（レビュー指摘を受けた再測定、**結論が反転**）
対象: `data/real/train`（90 ファイル）
チェックポイント: `models/full/best_infer.pt`
比較単位: トークン ID 列（文字に変換する前）

**重要な注意（データの性質）**: `data/real/train` は `models/full/best_infer.pt` の
実信号ファインチューニング（1,000 step）に使われた**学習データそのもの**である
（`docs/design.md` §8.1、コミット `580613f`）。真に未学習の held-out セット
（`keyed_val` = `script_eu_01`〜`10` / `script_ja_01`〜`10` のような `t` なしファイル）
はこのチェックアウトに存在しないため使えなかった。したがって**この掃引の絶対値
（CER・一致率）は楽観的な可能性が高い**。一方、比較対象は同一モデル・同一音声で
`commit_lag_s` だけを変えたものなので、**lag 間の相対順位は学習データ汚染の影響を
受けにくく、判断材料としては有効**と考える。サンプル数も 90 ファイルに留まるため、
結論の確度はこの範囲に限定される。

## 0. 参照計算のバグを発見・修正した（初回測定前）

タスクブリーフに記載されていた `sweep()` の参照計算は以下だった:

```python
references = [
    simulate_commit(engine, w, commit_lag_s=0.0, hop_s=hop_s, finalize=True)
    for w in waves
]
```

これは `simulate_commit` がループ中に毎回 `decoder.redecode()` を呼ぶ実装だった
ため、`commit_lag_s=0.0` を渡すと**ループの途中で（右文脈がほぼ無い状態のまま）
早期確定してしまい**、末尾の `finalize()` はごく僅かな残りトークンにしか効かなかった。
つまり「参照 = 右文脈が最大限ある状態」という前提が壊れていた。

**実測で検証**: `models/full/best_infer.pt` で5ファイルを比較したところ、
`commit_lag_s=1000`（ループ中は何も確定させない）で計算した参照は、音声全体を
一度に `decode_chunk` した結果と完全に一致した。一方 `commit_lag_s=0.0` で計算した
「参照」はそれと最大 50% も乖離しており、実質的には「最短 lag 相当の早期確定結果」
になっていた。このバグが残ったまま掃引すると、lag を大きくするほど参照から
遠ざかるという逆向きの（無意味な）結果が出る。

この発見自体はレビューでも「本物で価値が高い判断」と評価された。現在の実装では
参照計算を `reference_decode()` という専用関数に分離し（§2 のレビュー対応）、
`engine.decode_chunk(wave)` の単発デコードと一致することを回帰テストで担保している。

## 1. 【訂正】初回測定 (2026-08-05) で誤って「採用値 1.5s」と判断した経緯

**初回の判断 (採用値 1.5s、現行既定値 2.5s は 1.5s より悪い) は誤りだった。
以下、削除せず経緯を残す。**

### 初回の測定方法とその欠陥

初回の `simulate_commit`（仮説側）は、hop を最後まで投入した後 `redecode()` の
スナップショットで確定列を得ていた（`finalize()` を呼ばない）。この場合、
ファイル末尾の `commit_lag` 秒以内で終わるトークンは「音声がまだ続くかもしれない」
とみなされ、**未確定のまま結果から消える**。`commit_lag` が大きいほどこの
「未確定のまま消える末尾」の秒数が大きくなるため、参照（音声全体を使った
`finalize` 相当の結果）と比べたときの編集距離（欠落）が commit_lag にほぼ比例して
増えてしまう。これは実運用（ライブ受信で音声が終わらない）には存在しない、
**有限長ファイル特有の測定アーティファクト**であり、測りたかった「右文脈が増える
ほど確定精度が上がる」効果とは無関係のノイズだった。

### 見逃した理由（自己レビューの失敗）

初回の自己レビューで「lag を伸ばすと末尾が単に未確定のまま欠落するのでは」という
同じ疑いを一度持ち、**15 ファイル**で `len(got)`（各 lag での確定トークン数）と
`len(ref)`（参照長）を比較する追加診断を行った。しかしこの 15 ファイルは
（`sorted(glob("*.wav"))` の並び上）**すべて欧文スクリプト**という非代表的な
部分集合であり、そこでは lag=2.5 で短くなるファイルが 1 件しかなかったため
「末尾切り捨てによる測定アーティファクトではない」と誤って判断してしまった。
全 90 ファイルで見ると lag=2.5 で 32 件が参照より短く、合計 34 トークンの
欠落があった。標本抽出（先頭 15 件）が非代表的だったことが誤判定の直接原因。

### レビューでの独立検証

レビュアーが全 90 ファイルで独立に検証した結果:

| commit_lag | 初回の指標（末尾非対称あり） | 末尾を `finalize()` で確定した場合 | 末尾切り捨てだけで説明できる編集数 |
|---|---|---|---|
| 1.5 | edits 39 / CER 0.0191 | edits 40 / CER 0.0196 | 1 |
| 2.5 | edits 50 / CER 0.0245 | **edits 22 / CER 0.0108** | **22（50件中44%）** |

lag=2.5 の 50 編集のうち 22 件（44%）が末尾切り捨てだけで説明できる。末尾を実機と
同様に扱うと、**2.5 は 1.5 より明確に良く**、理論通り「右文脈が増えるほど改善する」
単調な関係になる。

## 2. レビュー対応: 全 lag を同じ音声区間で比較する指標に修正

### 修正方針

末尾の非対称性を消す方法として、以下の 2 つを実装した（レビュー指摘）。

- **主指標（採用）**: 参照・仮説の**両方**から、ファイル末尾 `max(lags)`
  （既定なら 2.5 秒）以内に終わるトークンを除外してから比較する。連続受信では
  あるトークンは `now > abs_end + lag` になった時点で確定されるので、
  ファイル末尾で確定されないのは「音声が尽きた」という有限長特有の現象であって
  実運用には存在しない。除外後は全 lag が全く同じ音声区間で評価されるため、
  差は「確定時に右文脈がどれだけあったか」だけになる。
- **副指標（cross-check として併記）**: 実運用でストリーム終了時に `finalize()`
  を呼ぶ挙動（`src/app/workers.py` の `stop()`）を模して、仮説側でも末尾で
  `finalize()` を呼び、末尾を除外しないフル参照と比較する。ただし `finalize()`
  は右文脈ゼロで末尾を確定するため、この指標には「右文脈量の効果」以外の
  ノイズ（末尾一括確定の精度）が混ざる。主指標ではなく参考値として使う。

### 実装

- `scripts/sweep_commit_lag.py` の `simulate_commit` は元のブリーフ通り
  hop ごとに常に `redecode()` を呼ぶ実装に戻し、`finalize: bool` （末尾で追加
  `finalize()` を呼ぶ cross-check 用）と `trim_tail_s: float | None`
  （末尾 N 秒を除外する主指標用）の 2 つの直交したオプションを追加した。
- 参照計算は `simulate_commit(commit_lag_s=0.0, finalize=True)` という
  紛らわしい呼び方をやめ、`commit_lag_s` を受け取らない専用関数
  `reference_decode()` に分離した（レビュー Minor 7 対応）。`window_s`
  （既定 30 秒）を超える音声を渡すと、リングバッファの切り詰めで参照の先頭が
  黙って失われるため例外を送出するようにした（レビュー Important 4 対応。
  `data/real/` には 80.3 秒の `20260612_200209_european.wav` が実在する）。
- 回帰テストを「`finalize=True` の結果は `commit_lag_s` に依存しない」という
  自明な性質（修正後は当該引数が未使用になるため自明に成立してしまう）から、
  本来の不変条件「参照 == `engine.decode_chunk(wave)` の単発デコード結果」に
  差し替えた（レビュー Important 5 対応）。`window_s` 超過時に例外になることも
  別テストで担保。

### 性能上の注意

主指標・副指標をそれぞれ独立に `simulate_commit` で計算すると、掃引で最もコストの
大きい hop ごとの `redecode()` ループを 2 回実行することになり、90 ファイルの
掃引が計算上 15 分を超える見込みになった（5 ファイルで実測 55.5 秒 → 90 ファイル
換算で約 16.7 分）。ループは commit_lag が同じなら主指標・副指標で共有できる
（`redecode()` は状態を追加するだけで消さないため、ループ後に
`redecode()` → `finalize()` の順で呼んでも独立に呼んだ場合と同じ結果になる）ため、
`sweep()` 内部専用の `_simulate_both()` でループを 1 回だけ実行し両方を得るように
最適化した。5 ファイルで結果が変わらないこと（バイト単位で一致）を確認した上で
採用し、90 ファイルの実測時間は 8 分7秒に収まった。

## 4. 判断（訂正後）

**採用値の提案: 現行既定値 `commit_lag_s = 2.5` を維持する（下げられない）**

根拠:
- 90 ファイルの実測で、テストした 6 つの commit_lag（0.5〜2.5s）のうち **2.5s が
  主指標・副指標の両方で最も CER が低く一致率が高かった**。0.5s→2.5s まで
  一貫して単調に改善しており、途中に「これ以上伸ばしても効果が薄い」という
  プラトーは見られなかった。
- したがって「commit_lag を下げると確定結果が壊れ始める」という当初の懸念は
  **その通りだった**。1.5s まで下げると編集数が約38（対2.5sの約20から+18、
  約1.9倍）に増える。
- CER がテスト範囲の上限 (2.5s) まで単調に改善し続けていることから、**むしろ
  2.5s より長い lag の方がさらに良い可能性すらある**が、これは「下げられるか」
  という本タスクの問いの範囲外であり、今回は追加で測定していない（都合の良い
  結論を作るために条件を追加で振ることは避けた）。

留保:
- `data/real/train` は学習データそのものであり真の held-out ではない。真に未知の
  実信号（`keyed_val` 相当）での追試を推奨する。
- サンプル数は 90 ファイルに留まる。
- `src/infer/settings.py` の既定値は指示通り変更していない（今回の結論も
  「変更しない」なので、そもそも変更の必要がない）。

**「下げられない」という結論になった。** これはタスクブリーフが明示的に許容していた
結果であり、失敗ではなく成果として記録する。当初 (2026-08-05) は測定方法の欠陥により
逆の結論 (1.5s へ下げるべき) を出してしまったが、レビューでの指摘と再測定により
訂正した。

## 7. 【重要】掃引結果を他の hop に適用するときの注意

**この掃引は `hop_s = 1.0`（既定値）で実施した。** §5 に記載のとおり、環境は
`hop_s=1.0` 固定である。したがって上の表の `commit_lag` 列を、別の `hop_s` を
使う実装（例: ブラウザ版の `HOP_S = 0.5`）にそのまま持ち込んではいけない。

### 効くのは `commit_lag_s` 単独ではなく `commit_lag_s + hop_s / 2`

確定境界は `totalConsumed - commit_lag_samples` であり、`redecode()` は `hop_s`
ごとにしか呼ばれない。したがって「終端が時刻 t のトークン」が実際に確定される
のは `t + commit_lag` を最初に超えた hop 境界であって、そのとき使えている右文脈は

```
[commit_lag, commit_lag + hop)    平均 commit_lag + hop/2
```

の範囲に散らばる。**測定で効いていたのはこの実効右文脈**であって、
`commit_lag_s` という設定値そのものではない。

| 実装 | `hop_s` | `commit_lag_s` | 実効右文脈（平均） |
|---|---|---|---|
| 掃引の最良点（§3） | 1.0 | 2.50 | **3.00 秒** |
| ブラウザ版（当初、hop だけ縮めた） | 0.5 | 2.50 | 2.75 秒（← 0.25 秒短い） |
| ブラウザ版（訂正後） | 0.5 | **2.75** | **3.00 秒** |

§3 の表は 2.0 秒（CER 0.0144）→ 2.5 秒（CER 0.0100）と**プラトー無しで単調改善**
していたので、実効右文脈を縮めた分はそのまま精度低下側に効く。ブラウザ版は体感
遅延を減らすために hop を 1.0 → 0.5 に縮めていたが、その際に `commit_lag_s` を
据え置いたため、実効右文脈が静かに 0.25 秒失われていた。

### ルール

> **掃引結果を他の `hop_s` に適用するときは `commit_lag_s + hop_s / 2 = 3.0` を保つこと。**

これは「`commit_lag_s` を下げてはいけない」（§4）に反する変更ではない。むしろ
hop の短縮で静かに失われていた右文脈を戻す変更であり、確定までの遅延も
hop 1.0 時代と同じ 3.0 秒に戻る（短くなるのは暫定表示の更新間隔だけ）。

該当箇所: `web/src/ui/app.ts` の `COMMIT_LAG_S`（= 2.75、hop 0.5 用）。
デスクトップ版 `src/infer/settings.py` の既定値（hop 1.0 / lag 2.5）は
実効 3.0 秒なので変更不要。

## 8. 【重要】2026-08-07 の再測定で結論が変わった

**§4 の「2.5 を維持する (下げられない)」という結論は、held-out の実録音では成り立たなかった。**

### 何が違うのか

| | §1〜§4 の掃引 (2026-08-05/06) | 今回 (2026-08-07) |
|---|---|---|
| 対象 | `data/real/train` 90 件 (**学習データそのもの**) | `data/keying_scripts` 20 件 + `data/keyed_extra` 1 件 (**held-out**) |
| 指標 | オフライン一括デコードとの**一致率** (代理指標) | **正解ラベルとの CER** |
| hop | 1.0 | 0.5 (ブラウザ版と同じ) |

§0 で自ら「この掃引の絶対値は楽観的な可能性が高い」と書いていたとおりだった。
加えて**指標が違う**。「オフライン結果とどれだけ一致するか」は「正しいか」ではない。
オフライン結果自体が間違っていれば、それに一致することは良いことではない。

### 実測 (hop=0.5、確信度閾値 0.5、モデル `models/full/best_infer.pt`)

| `commit_lag` | 実効右文脈 | CER |
|---|---|---|
| 0.75 | 1.00 s | 25.45% |
| 1.00 | 1.25 s | 23.38% |
| 1.25 | 1.50 s | 21.56% |
| 1.50 | 1.75 s | 21.82% |
| **2.00** | **2.25 s** | **19.74%** ← 最良 |
| 2.75 (旧設定) | 3.00 s | 20.78% |

**2.00 は 2.75 より 0.75 秒速く、かつ CER も 1.04pt 良い。** 単調改善ではなく
2.25 秒付近に最良点があった。

### 採用した値

- ブラウザ版 `web/src/ui/app.ts`: `COMMIT_LAG_S` 2.75 → **2.0** (hop 0.5、実効 2.25 秒)
- デスクトップ版 `src/infer/settings.py`: `commit_lag_s` 2.5 → **1.75** (hop 1.0、実効 2.25 秒)

**`commit_lag + hop/2` が効くという関係自体は変わらない。** 変わったのはその目標値で、
**3.0 秒 → 2.25 秒**である。hop を変えるときはこの和を保つこと。

### 限界

21 ファイル。1pt 程度の差は誤差かもしれない。**「2.00 が 2.75 より確実に良い」とまでは
