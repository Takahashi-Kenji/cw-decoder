# Phase 4 データ収集ガイド — 実交信50件に頼らない方法

実交信の録音+書き起こしは負荷が大きいため、**ラベル作業ゼロ〜最小**で
実環境への適応 (ドメインギャップ解消) を進める 3 本立ての収集戦略を使う。

| 手段 | 得られるもの | ラベル作業 | 目安工数 |
|------|-------------|-----------|---------|
| ① 実ノイズ録音 | 本物のバンドノイズ・QRM・空電 | **不要** (合成テキスト) | 放置録音 30〜60 分 |
| ② 自己打鍵録音 | 本物の手送りの癖 + 完全ラベル | **不要** (原稿=ラベル) | 1 晩で 20〜30 件 |
| ③ 実交信 (随時) | 実オペレータの多様性 | デコード結果の訂正のみ | 貯まった分だけ |

①+② が揃えば最初の FT を実行できる。③ は並行して貯める。

---

## ① 実ノイズ録音 (`data/noise/`)

受信機で**信号のいない周波数**のバンドノイズを録音する。
合成キーイングに混合され、「本物のノイズ + 正確なラベル」の学習データが
無制限に作れる (`--noise-dir`)。

### 手順

1. アプリを通常のライブ設定で起動する (**BPF ON、中心 600 Hz / 帯域 400 Hz** —
   ライブ運用と同一設定にすること。保存 WAV は BPF 通過後の音になる)
2. 7 MHz 帯などで CW 信号のいない周波数に合わせる
3. アプリの録音ボタンで 1〜5 分程度を数本録音する
   - 時間帯 (昼/夜)・コンディション (静か/QRN 多め/近接 QRM あり) を散らす
   - 合計 30〜60 分あれば十分
4. 録音された WAV を `data/noise/` に移動する
   - 対になる `.txt` は不要 (あっても無視される)
   - **弱い CW が混じっていないか再生確認する** (ラベルなし CW が混入すると
     学習を汚す。かすかに聞こえる程度なら QRM として逆に有益)

## ② 自己打鍵録音 (原稿 → `data/real/`)

既知の原稿を自分で打鍵して録音する。原稿がそのままラベルになるため
書き起こし不要で、手送りの癖・自局セットアップの音が学習に入る。

### 準備

原稿は `data/keying_scripts/` にある。**学習用と評価用をファイル名で分けている**。

| 原稿 | 用途 | 出所 |
|------|------|------|
| `script_eu_01..10` / `script_ja_01..10` (録音済み) | **評価 keyed_val**。学習に回さない | 乱数生成 (`generate_keying_scripts.py`) |
| `script_eu_t01..t30` / `script_ja_t01..t60` | **学習 train** | 手書きコーパス (`generate_corpus_scripts.py`) |

`t` 付きが学習用である。keyed_val 20 件は過去実験 (B1・実ノイズ FT・WORD_BREAK 掃引)
と同じ土俵で比較し続けるため固定し、**新規録音はすべて学習側に入れる**。

旧 `script_ja_11..20` (未録音・乱数生成) は語彙が狭く和文コーパスと重複するため削除した。
必要なら `git log -- data/keying_scripts` から復元できる。

### ラベルは「実際に打鍵したもの」でなければならない (2026-08-03 の教訓)

keyed_val 20 件のラベルに、**音に存在しないトークンが 19 個含まれていた**
(`{HORE}`7・`{RATA}`7・`{SK}`5)。原稿には書かれていたが打鍵されていなかった。
ref_tokens 447 の 4% にあたる。

これにより Phase A の「6要素符号 recall 26.7%、ノイズではなくモデルの問題」という
結論の一部が崩れた。`{RATA}` recall 0% は音に無いものを数えていただけだった。
一方 `{HORE}` recall 85.7% も実力ではない — **ラベルにホレが無い録音 3 件すべてで
モデルが冒頭に `[ホレ]` を出す**ため、和文冒頭で無条件にホレを吐く癖と
ラベルがたまたま一致していただけだった。

ラベル修正後の baseline: keyed_val TER **23.35% → 25.95%** (幻覚ホレが挿入誤りとして
正しく計上されるため悪化する)。`models/eval/base_keyed_fixed.json`。

**原則**: 原稿は打鍵計画であってラベルではない。ラベルは録音後に実際の打鍵内容へ
合わせること。オートキーヤーが送出できない符号は原稿から外す
(`tests/test_keying_corpus.py::test_no_prosign_markers` が再発を防ぐ)。

学習用原稿の再生成 (本文は固定なので何度実行しても同じ):

```
python scripts/generate_corpus_scripts.py
python scripts/generate_corpus_scripts.py --dry-run   # 中身の確認だけ
```

本文は `src/finetune/keying_corpus.py` が持つ。乱数生成をやめた理由は、
**6要素符号 (`?` `,` `.` `-` `@` `{SK}` `、` `」`) の出現数を設計値どおりに
保証するため** (Phase A の実測で recall 26.7%、`{HORE}` は無い所に 7 回幻覚挿入)。

| | 件数 | 内訳 | 打鍵時間 |
|---|---:|---|---:|
| 欧文 `script_eu_t*` | 30 | 実運用文 18 + 弱点重点 12 | 8.7 分 |
| 和文 `script_ja_t*` | 60 | 実運用文 36 + 弱点重点 24 | 17.4 分 |

**和文の表記**: 符号表に小書き文字 (ャ ュ ョ ッ ェ 等) は無く、和文モールスでは
拗音・促音も大書きで送る。原稿が「リヨウカイ」「ワツト」「シユウハスウ」表記なのは
このため。濁点・半濁点は独立トークンなので「ガ」は カ + ゛ の 2 打鍵になる。

本文を編集した場合は `tests/test_keying_corpus.py` がカバレッジ (符号単位) と
打鍵時間 (8〜20 秒)、ホレ/ラタの対応を検証する。

### 手順 (1 件あたり 1〜2 分)

1. サイドトーン (または練習発振器) の音が受信機/アプリに入るようにする。
   ピッチは**ライブ運用と同じ約 600 Hz**、アプリは BPF ON (①と同じ設定)
2. 原稿ファイル (例 `script_ja_01.txt`) の `---` 以下の本文を開く
   - `{HORE}` はホレ (-・・---)、`{RATA}` はラタ (・・・-・)、`{SK}` は ＳＫ (・・・-・-)、
     `、` は区切点、スペースは語間 (少し長めに空ける) として打鍵する
3. アプリの録音ボタンを押し、原稿を通しで打鍵して停止する
   - 打ち間違えたらそのファイルは捨てて録り直すのが簡単
   - **WPM は原稿ヘッダの値に従う** (`script_eu_t*` は 16 / 20 / 24 を指定済み)。
     実運用実測が 14.6〜19.4 WPM なので、学習用原稿は 16・20 を主体にしてある
   - **語間は文字間の 2 倍強を意識して空ける**。逆に区切点 `、` や `.` の後は
     語間を追加しない。打鍵20件の挿入誤り53件中33件が語間スペースの過剰検出で、
     これは打鍵リズムがそのまま学習に入る部分である
4. 保存された TXT に原稿ラベルを転記する:

```
python scripts/apply_keying_label.py data/real/20260712_190000_japanese.txt \
    --script data/keying_scripts/script_ja_01.txt
```

どの録音がどの原稿かをメモしておくこと (ファイル名の対応表など)。

### コーパス原稿を連番で録音した場合の取り込み

オートキーヤー等でコーパス 90 件を `t01.wav` … の連番で録音した場合は、
一括で取り込める:

```
python scripts/import_keying_recordings.py \
    --european-dir data/欧文 --japanese-dir data/和文
# 対応と時間差の確認だけ
python scripts/import_keying_recordings.py --european-dir data/欧文 --dry-run
```

`data/real/train/script_eu_t01.wav` + `.txt` の形で配置される。実録音長と
原稿の見積もり長の差が全件表示され、差が外れたものは警告が出る (対応ずれの検出)。

**取り込み時に必ず BPF と無音パディングを通す** (既定で有効)。実測値:

| 前処理 | keyed TER (90件) |
|---|---:|
| そのまま (アプリ外で録音) | **97.03%** |
| ＋ BPF 600Hz/400Hz | 14.44% |
| ＋ 前後 0.4 秒の無音 | **10.60%** |

- **BPF**: モデルはライブ運用でも BPF 通過後の音を受け取る。アプリ経由で録った
  録音は帯域内エネルギーが 99.9% あるが、オートキーヤーから直接録ると 64% しかなく、
  帯域外ノイズがそのまま特徴量に入って崩壊する
- **無音パディング**: 直接録音は 5ms 目から音が始まり先頭に無音が無いため、
  モデルが立ち上がりを符号と誤読して先頭にゴミトークン (`U` 等) を吐く。
  実測でこの挿入だけが誤り 297 件中 44 件を占めていた

アプリ経由で録音した場合は既に BPF 済みなので `--no-bpf` を付ける。

## ③ 実交信 (擬似ラベル + 訂正)

実交信は「録るだけ」で貯める。TXT にはモデルのデコード結果が保存されるので、
**ゼロから書き起こさず、間違い箇所だけ訂正**する。訂正済みのものから
FT に入る (本文が空のままなら自動で除外される)。

ラベル書式は `docs/phase4_finetuning.md` と同じ:
和文はカタカナで打鍵通り、漢字不可。

**判別不能箇所の扱い (重要):** 聞き取れない箇所を `?` で埋めてはいけない。
`?` は疑問符符号 (`・・--・・`) として学習・評価されるため、誤ラベルになる。
確信の持てない箇所を含む区間は **その区間ごと採用しない** (捨てる)。
評価セットは少数でも正確であることが最優先で、誤ラベルは 1 件でも指標を壊す。

デコード結果を修正してラベルにする場合は、表示プロサイン (`[ホレ]` / `[ラタ]` /
`[SK]`) が自動で `{HORE}` / `{RATA}` / `{SK}` に正規化される
(`normalize_label_markers` / `clip_onair.py`)。

## FT の実行 (①②が揃ったら)

```
python scripts/finetune.py --data-dir data/real --resume models/full/best.pt \
    --ckpt-dir models/ft --steps 2000 --lr 1e-4 \
    --real-ratio 0.5 --noise-dir data/noise
```

- `--noise-dir` 指定で `--mix-synth` は自動有効化。合成サンプルの 8 割
  (`--noise-prob`) に実ノイズが SNR -5〜15 dB (`--noise-snr-min/max`) で混合される
- 合成トーンは録音時 BPF 中心に合わせ 600±50 Hz に制約される
  (`--tone-center` / `--tone-span` で変更可)
- 和文重点なら `--mode-filter japanese`、実データが少ないうちは `--lr 5e-5`
- 学習後の体感確認: `python scripts/run_app.py --ckpt models/ft/best.pt`

## 実行順序の目安

1. ①ノイズ録音 (放置) + ②和文原稿 20 件を打鍵録音
2. FT 実行 → 実機で体感 → 効果を確認
3. ②欧文追加・WPM を散らして反復、③の訂正済み実交信を随時追加
