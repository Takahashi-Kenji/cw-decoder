## 準備

1. モデル・符号表・fixture が最新であることを確認する（未生成/古い場合は再生成）。

   ```bash
   # リポジトリルート (cw-decoder/) で実行
   .venv/Scripts/python.exe scripts/export_onnx.py
   .venv/Scripts/python.exe scripts/export_tokens.py
   .venv/Scripts/python.exe scripts/export_golden.py
   ```

2. dev server を起動する。

   ```bash
   cd web
   npm run dev
   ```

3. 無線機の音声出力を PC のマイク入力 (またはライン入力) に接続する。
4. 表示された URL (既定 `http://localhost:5173/`) をブラウザで開く。
   **`localhost` か `127.0.0.1` で開くこと。** `getUserMedia` はセキュアコンテキストを
   要求するので、LAN IP (`http://192.168.x.x:5173/`) だとマイクがブロックされる。

> **チェックポイントの注意 (デスクトップ版と比べるとき)**
>
> ブラウザ版が使う ONNX とゴールデン fixture は **`models/full/best_infer.pt`** から
> 生成される (`scripts/export_onnx.py` / `scripts/export_golden.py` の既定)。
> 一方 `models/full/best.pt` は学習用チェックポイントで `.gitignore` 対象であり、
> 手元に残っていても **別世代のモデル**であることがある。

> 踏んだ)。突き合わせは必ず `--ckpt models/full/best_infer.pt` で行うこと
> (`decode_user_wav.py` / `decode_demo_samples.py` の既定はこれに揃えてある)。

### 3. 暫定文字 (グレー) が 1〜2 秒で出るか

- [x] 実施済み (2026-08-06、WAV 入力での**音声時間**計測。ライブ受信での体感計測は未実施)
- **確認手順**: CW 受信中、`provisional` 側 (グレー表示) の文字が最初に現れるまでの
  時間を目視またはストップウォッチで計測する。
- **期待される結果**: 符号の入力開始からおおむね 1〜2 秒程度で暫定文字が表示される
  (`HOP_S = 0.5`s ごとに更新される設計)。
- **実際の結果**: `oubun.wav` を WAV 入力で流し、`#out-european` の DOM 更新を
  MutationObserver で数えた。29.0 秒の音声で更新は 62 回 (hop 0.5 秒 × 58 + finalize)
  で設計どおり。**暫定文字の初出は 3 hop 目 = 音声時間 1.5 秒**、確定文字の初出は
  8 hop 目 = 音声時間 4.0 秒 (`head_guard 1.0 + commit_lag 2.75` = 3.75 秒と整合)。
  期待どおり 1〜2 秒に収まっている。
  なお WAV 入力はバックプレッシャで押し込むため実時間ではなく音声時間での計測であり、
  **ライブ受信の体感遅延そのものではない**点に注意 (推論は hop に対し 5 倍以上の
  余裕があるので実時間でもほぼ同じになるはずだが、実測は項目 1・2 と同時に行うこと)。

### 4. 確定文字 (通常色) が後から固まり、確定後に書き換わらないか

- [x] 実施済み (2026-08-06、WAV 入力。ライブ受信での数分間観察は未実施)
- **確認手順**: 暫定文字がしばらく画面に出た後、`committed` 側 (通常色) に文字が
  移動して固定されるまで観察する。固定された文字がその後の受信で変化しないかを
  数分間観察する。
- **期待される結果**: `commit_lag_s = 2.75` 秒後に文字が確定し、**一度確定した文字は
  以降のいかなる入力でも書き換わらない**。
- **実際の結果**: 目視ではなく機械的に検証した。`レコーディング.wav` (28.4 秒) を
  WAV 入力で流し、`committed` 要素の値が更新されるたびに履歴へ積み、
  **「新しい確定テキストは必ず直前の確定テキストを prefix として含む」** (= 追記のみで
  書き換えが無い) ことを全更新について検査した。**更新 36 回、違反 0 件**。
  確定文字の初出は項目 3 のとおり音声時間 4.0 秒で、`head_guard + commit_lag` と整合。

### 5. 同じ音声をデスクトップ版でもデコードし、結果が一致するか

- [ ] 実施済み
- **確認手順**:
  1. ブラウザ版の「WAV を読む」機能を使い、無線機から録音した WAV ファイルを
     読み込んでデコードする（マイクのライブ受信ではなく、同一ファイルで比較する
     ことで再現性を確保する）。
  2. 同じ WAV ファイルを Python 側 (`scripts/decode_user_wav.py` 等) でデコードする。
  3. 両者のテキスト出力を突き合わせる。
- **期待される結果**: 完全一致、または軽微な差異のみ (Task 10 のゴールデンテストで
  トークン ID 列は完全一致することを確認済みなので、大きな差異が出た場合は
  デコード表示ロジック側の疑いが強い)。
- **実際の結果**: **合格 (軽微な差異のみ)**。2026-08-06 実施。
  ブラウザ版は WAV 入力 (Chromium)、Python 側は `SlidingWindowDecoder` を
  **ブラウザと同じ設定** (`hop 0.5 / commit_lag 2.75 / head_guard 1.0 /
  left_context 5.0`、`confidence_threshold 0.5`) で回して突き合わせた。
  チェックポイントは両者とも `models/full/best_infer.pt`。

  | サンプル | ブラウザ版 | デスクトップ版 (同設定) | 差 |
  |---|---|---|---|
  | `oubun.wav` (29.0s) | `?EJH0ILLPG? MNA 5NN? JH0ILL GA 5NN[SK]` | `QEJH0ILLPG? MNA 5NN? JH0ILL GA 5NN[SK]` | 1 文字目のみ (`?` / `Q`) |
  | `レコーディング.wav` (28.4s) | `CUN73GL?I RGLTU73EE TUDE 7 K3LAA1CC10?I` | `CUN73GLXI RGLTU73EE TUDE 7 K3LAA1CC10?I` | 8 文字目のみ (`?` / `X`) |
  | `wabun.wav` (90.4s, 和文表示) | `…ユワナ 7タ2マフ 6…リ アメ デス ??` | `…ユワナ 7タ2マ フ 6…リアメ デス ??` | 語間スペース 2 箇所のみ |
  | `20260729_204356.wav` (37.5s, 実打鍵) | `Q? ??I? EI?R? B` | `Q? ??I? ?EI?R? B` | 1 トークン |

  差はいずれも **閾値近傍のトークンが `?` (LOW_CONFIDENCE) に転ぶか転ばないか**と
  **WORD_BREAK の位置**であり、PyTorch と ONNX Runtime Web のカーネル差 (float32 の
  丸め) で説明がつく範囲。文字列としての意味は変わっていない。

  さらに強い証拠として、リサンプルを一切通さない生の 8 kHz float32 波形
  (`oubun.wav` を Python 側で 8 kHz 化したもの) をブラウザ内で
  `OnnxDecodeEngine.decodeChunk()` に直接与えたところ、**トークン ID 35 個が
  `web/tests/fixtures/golden.json` と完全一致**した。つまり推論エンジン自体は一致しており、
  上表の差は「ストリーミング境界 + 実装差」に閉じている。

  **注意**: `20260729_204356.wav` はブラウザ版・デスクトップ版の**どちらもほぼ
  デコードできていない** (両方とも `?` だらけ)。これはブラウザ移植の問題ではなく
  この録音自体の難しさ (既知の keyed CER 23〜26%) による。ブラウザ版の評価には
  使わないこと。

### 6. BPF オン/オフでデコード結果を比較する

- [ ] 実施済み
- **背景**: デスクトップ版 (`src/app/workers.py` の `_StreamingBPF`) は中心 600 Hz /
  帯域 400 Hz の BPF (scipy `butter(4, ..., btype='bandpass')`。bandpass 指定で
  次数が 2 倍になるため SOS は 4 セクション = 実効 8 次) を既定で有効にしている。
  ブラウザ版はこれを `BiquadFilterNode` 2 段 (RBJ バイカッド、4 次相当) で
  近似しており、**段数が半分でロールオフ (肩の落ち方) も約半分緩く、周波数特性は
  厳密には一致しない**。効果があるのか・逆効果になっていないかは実信号でしか
  判定できない。**この項目がブラウザ版 BPF を実地で評価する唯一の手段。**
  **注意**: 段数がデスクトップ版の半分であるため、オン/オフの比較で差が小さく
  出ても「BPF が無意味」と即断しないこと。段数差だけでロールオフに差が出うる。
- **確認手順**:
  1. 「受信開始」で受信し、BPF チェックボックスを**オン**(既定)にしたまま数分間
     受信して、確定テキストを控える。
  2. 「クリア」を押し、BPF チェックボックスを**オフ**にする (受信を止めずに
     切り替わる)。同じ条件で数分間受信して確定テキストを控える。
  3. 可能なら同じ交信を録音しておき、WAV 入力でも比較する。ただし
     **WAV 入力経路には BPF がかからない** (Python 側 `decode_user_wav.py` との
     突き合わせを汚さないための設計)。WAV での比較はライブ受信の BPF オフ相当に
     なる点に注意。
  4. 混信・ノイズが多い状況ほど差が出やすい。可能なら「静かなバンド」と
     「混信のあるバンド」の両方で試す。
- **期待される結果**: BPF オンのほうが `?` (LOW_CONFIDENCE) が少なく、誤字が少ない。
  スペクトル表示は BPF の状態にかかわらず変化しない (AnalyserNode は生の入力に
  繋がっているため) ことも同時に確認する。
- **実際の結果**: （記入してください。オン/オフそれぞれの出力を並べ、受信条件
  (バンド・混信の有無・S メータ) も記録すること）

### 7. `推論 XX ms` の表示が hop (1000 ms) より十分小さいか

- [ ] 実施済み
- **確認手順**: 受信中、診断表示 (`#diag`、`推論 XX ms / hop 0.5s / 確定遅延 2.75s / スレッド N`)
  の `推論 XX ms` 部分を確認する。
  - 備考: 現行実装の hop は `HOP_S = 0.5` 秒 (`web/src/ui/app.ts`)。ブリーフ記載の
    「hop (1000 ms)」は初期案の値であり、実装確定値である 500 ms を基準に判定すること。
- **期待される結果**: 推論時間が hop (500 ms) より十分小さい (Task 3 の実測では
  8.5 秒音声のデコードが 1 スレッド 155.5 ms、4 スレッド 58.3 ms であり、
  余裕があることを確認済み。実機・実ブラウザでも同様の余裕があるか確認する)。
- **実際の結果**: **合格**。2026-08-06、Chromium (Playwright)、
  `hardwareConcurrency = 28`、dev server は COOP/COEP 付きなので
  `crossOriginIsolated = true` → スレッド数 4。

  - WAV 入力 (`oubun.wav` 29.0 秒) の実運用経路で、診断表示の `推論 XX ms` は
    **中央値 66 ms / 最大 97 ms** (62 回の hop 更新)。`レコーディング.wav` では
    最大 132 ms。hop 500 ms に対して 4〜7 倍の余裕。
  - 1 hop 分の実デコード長 (`left_context 5.0 + commit_lag 2.75 + hop 0.5` = 8.25 秒)
    を直接 5 回ずつ測ると **1 スレッド 156 ms / 4 スレッド 158 ms** (中央値)。
    Task 3 の実測 (1 スレッド 155.5 ms) とよく一致する。
  - **1 スレッドでも hop の 1/3 で収まる**ので、COOP/COEP が付けられない配布形態
    (マルチスレッド不可) でも余裕がある。
    なおこの環境ではスレッドを増やしても速くならなかった (156 → 158 ms)。この規模の
    モデルではスレッド並列の効果が出ていない可能性があるが、**1 スレッドで十分**な
    ため実用上の問題はない。

### 2026-08-06: 見かけ上の大きな食い違い (原因はチェックポイント違い、実害なし)

最初の突き合わせで下記のような大きな差が出たが、**ブラウザ版のバグではなかった**。

```
入力ファイル: sample_wav/oubun.wav
デスクトップ版出力: QIJH0ILL EPGMO NJMN NT JH0ILL GA 5NN6A   ← models/full/best.pt (旧世代・git 管理外)
ブラウザ版出力    : ?EJH0ILLPG? MNA 5NN? JH0ILL GA 5NN[SK]   ← models/full/best_infer.pt (配布モデル)
```

`scripts/decode_user_wav.py` の既定チェックポイントが `models/full/best.pt` だった一方、
ブラウザ版の ONNX は `models/full/best_infer.pt` から生成されており、**別世代のモデル同士を
比べていた**。同じ `best_infer.pt` に揃えると差は 1 文字に縮む (項目 5 の表)。

対処: `decode_user_wav.py` / `decode_demo_samples.py` の既定を `best_infer.pt` に変更し、
本シートの「準備」にも注意書きを追加した。`models/full/best.pt` は `.gitignore` 対象で
clone 直後には存在しないため、既定として不適切でもあった。

### 2026-08-06: dev server がブラウザから見えないことがある

`npm run dev` は既定で IPv6 (`::1`) にしか bind しないことがあり、その場合
`http://127.0.0.1:5173/` では接続できない。`localhost` で開くか、
`npm run dev -- --host 127.0.0.1` で明示的に bind する。

**総合コメント** (2026-08-06 時点):

WAV ファイル入力で確認できる範囲では**問題は見つからなかった**。

- デコード結果はデスクトップ版と実質一致 (差は 1 文字〜語間スペース 2 箇所、項目 5)
- 推論エンジンはゴールデン fixture とトークン ID 完全一致
- 確定文字は追記のみで書き換わらない (36 更新・違反 0)
- 推論速度は 1 スレッドでも hop の 1/3

残るリスクは**ライブ受信経路にしか無いもの**に絞られた:

1. マイク入力 (`getUserMedia` → AudioWorklet → FIR デシメータ) が実デバイスで動くか
2. スペクトル表示・入力レベル表示が実信号で妥当か (項目 1・2)
3. `BiquadFilterNode` 2 段の BPF が実際に効くか (項目 6、デスクトップ版の scipy 実装とは
   段数が半分で特性が一致しない。**実信号でしか判定できない**)

つまり「Node 上のテストは全緑」と「ブラウザで動く」の距離は縮んだが、
**マイクから無線機の音を入れる確認はまだ誰も行っていない**。
