## 1. プロジェクト概要

### 1.1 目的

従来のルールベース (短点/長点のタイミング閾値判定) によるモールス信号デコーダを、機械学習 (深層学習) ベースに置き換える。手送り電鍵の打鍵揺らぎ、QSB (フェージング)、QRM (混信)、QRN (空電) など、実際の HF 帯 (主に 7 MHz) CW 運用で発生する信号劣化に対してロバストなリアルタイムデコードを実現する。

### 1.2 スコープ

1. **合成データジェネレータ** — 学習用 CW 音声を無限に合成生成
2. **学習パイプライン** — RTX 5060 Ti 16GB でモデル学習
3. **リアルタイム推論アプリケーション** — マイク/ライン入力からの音声を実時間でデコード、テキスト表示

### 1.3 対応符号

- **欧文モールス** (国際モールス符号): 英字 (A-Z)、数字 (0-9)、記号 (.,?/=+-@)、プロサイン (AR, BT, SK, SN, KN, HH)
- **和文モールス** (カタカナ): 全カナ 48 字 (ヰヱ含む)、濁点 (゛)、半濁点 (゜)、長音 (ー)、区切点 (、)、段落 (」)、和文記号 (ホレ・ラタ)
- **追加**: 語間スペース (WORD_BREAK) トークン

欧文/和文の切替は**ユーザー設定**で行う (受信内容からの自動判定は行わない、ただし将来拡張余地あり)。

## 2. アーキテクチャの基本方針

### 2.1 「音 → 符号 → 文字」の三層分離

```
音声入力 → [前処理: メルスペクトログラム]
        → [NN モデル: CNN + BiLSTM + CTC]
        → 符号トークン列 (全モード統合・約 72 種)
        → [変換表: ユーザー設定で 欧文表 / 和文表 を選択]
        → 表示テキスト
```

ニューラルネットワークの役割を「音声から**符号トークン列**を取り出すこと」に限定し、文字への変換は決定論的な変換表で行う。

**この分離を採用した理由**:

- 欧文と和文は同一符号パターンが別文字に対応する (例: `・-` は欧文 A / 和文 イ)。音響レベルでは曖昧性を持たせず、文字割当は後段に任せる
- チャンク単位のストリーミング推論で NN がモード文脈を保持する必要がなくなる
- NN の誤りと変換ロジックの誤りを切り分けてデバッグできる
- 変換表の追加・修正だけで表示仕様を拡張できる (例: 和文モードでの数字対応も**モデル再学習不要**で実現できた)

### 2.2 「?」出力の 2 分類

| 種別 | 発生箇所 | 動作 |
|---|---|---|
| **TABLE_MISS** | 変換表ルックアップ失敗 (例: 欧文モード中に和文専用符号を受信) | 「?」を表示、`FallbackEvent` に記録 |
| **LOW_CONFIDENCE** | CTC デコード時のトークン事後確率が閾値未満 | 「?」を表示、UI スライダで閾値調整可 |

### 2.3 単一ソース管理

符号定義は `src/tokens/morse_tokens.py` を**唯一の真正なソース**とする。合成器・学習・推論・テストすべてがこのモジュールを参照する。

ブラケット表示の特殊トークン (`[SK]` 等) を合成入力で指定するため、中括弧マーカーを導入:

```python
SPECIAL_INPUT_MARKERS = {
    "{HORE}": "-・・---",
    "{RATA}": "・・・-・",
    "{SK}":   "・・・-・-",
}
```

`text_to_codes` がこれらを符号に展開。例: `"73 TU {SK}"` → `[7, 3, T, U, SK]`。

## 4. 主要な改修と発見した問題

### 4.1 ストリーミングリサンプリング破壊 (最重大バグ)

#### 現象

- ライブ音声デコードでほぼ何も認識できない (1 token / 分)
- 同じ音声を WAV 保存してオフライン decode すると 37 token (正常)

#### 原因

`scipy.signal.resample_poly` は**ステートレス**。各ブロック (50ms) ごとに呼ぶと、フィルタ過渡応答がブロック境界で発生。CW の dot/dash 構造が破壊される。

検証実験:
| 方式 | 同じ音声でのトークン数 |
|---|---|
| scipy 全体 resample (オフライン) | 37 |
| scipy per-block (ライブ模擬) | **1** |
| scipy バッファ蓄積 (毎回全体 resample) | 2 |
| **soxr.ResampleStream** | **37** ✅ |

#### 解決

`soxr.ResampleStream` (libsoxr Python binding) はステートフルなストリーミングリサンプラ。内部状態を保持して連続音声を歪みなく変換。

ファイル: `src/infer/audio.py`

### 4.2 Qt クロススレッド直接呼出し問題

#### 現象

- モード切替時にクラッシュ (segfault)
- 停止ボタン押下時にクラッシュ

#### 原因

UI スレッド (main) からワーカースレッドのメソッドを直接呼出していた:

```python
# 悪い例
self._worker.set_mode(mode)   # 直接呼出し → race condition
```

#### 解決

Qt Signal を経由してキューイング接続に:

```python
# 良い例
class CWDecoderWindow:
    request_set_mode = Signal(str)
    
    def _on_start(self):
        self.request_set_mode.connect(self._worker.set_mode)  # AutoConnection で queued になる
    
    def _on_mode_changed(self):
        self.request_set_mode.emit(mode)   # キューイングで安全
```

### 4.3 リアルタイム音声デコード精度の限界

#### 現象

ライブストリーミングが**オフライン WAV decode より精度が低い**:
- オフライン (全体 80秒): 123 tokens
- ストリーミング 1.5s チャンク: 91 tokens
- ストリーミング 5s チャンク: 108 tokens
- ストリーミング 10s チャンク: 112 tokens

#### 原因

CTC モデルはチャンク単位の文脈で動作。短いチャンクほど文脈情報が少なく精度低下。

#### 解決

1. **デフォルトチャンク長を 5 秒に拡大** (元 1.5 秒)
2. **手動デコードモード追加** — 「デコード録音開始」+「デコード」ボタンで蓄積音声を全体 decode (オフライン精度)
3. **自動チャンクモード** — 語間の長い無音で自動 decode 実行

ユーザー観察: 「ストリーミングは参考程度、決定的判断はオフライン (= 全体デコード)」

### 4.4 無音検出による自動チャンク

#### 課題

固定時間チャンクだと:
- 文字途中で切れて誤認識
- 「先頭部分が決まって失敗する」現象

#### 解決

スキッシュ閾値 (= レベルメータの橙色破線) を再利用:

```python
block_rms = sqrt(mean(block^2))
block_db = 20 * log10(block_rms)
is_silent = block_db < squelch_threshold_db
```

連続無音 ≥ 1.2 秒 + バッファ ≥ 2 秒 で自動デコード発火。

#### ユーザーフィードバックによる重要修正

| 試行 | 結果 |
|---|---|
| 初版: 絶対振幅閾値 0.005 | 「何もデコードできない」 |
| 「先頭無音待ち」廃止 | 即時バッファ開始 |
| **スキッシュ閾値 (RMS dBFS) ベースに変更** | ✅ レベルメータ表示と一致、直感的 |

### 4.5 BPF (帯域通過フィルタ) 追加

#### 動機

実音声には CW 帯域外の広帯域ノイズ (空電・ハム) が混入。学習データには含まれない雑音パターンでモデルが混乱し、「?」を多発する。

#### 実装

- バターワース SOS (`butter(4, ..., btype='bandpass')`。bandpass 指定は次数を
  2 倍にするため SOS は 4 セクション = 実効 8 次)
- ステートフル (`scipy.signal.sosfilt` with zi)
- デフォルト: 中心 600 Hz、帯域 400 Hz (400-800 Hz 通過)
- UI で中心・帯域・有効/無効を調整可

#### 効果

ユーザーフィードバック: 「非常によくなった、? が減った」

### 4.6 リモートデスクトップ音声の罠

#### 現象

リモート PC の受信機音声を RDP で転送して decode しようとしたら、信号がほぼ届かない (常時 400Hz のキャリア漏れのような音のみ)。

#### 原因

RDP 音声経路:
- Opus 圧縮 (CW のクリック・細部消失)
- 帯域制限 (22 kHz 以下)
- RDP 側の AGC・ノイズリダクション処理
- 遅延・ジッタ

→ CW のような時間精度が重要な信号は壊滅的に劣化。

#### 解決

リモート PC 側にアプリ自体をインストールして実行。RDP は GUI 制御のみに使う。

### 4.7 デバッグツール群

問題切り分けのため作成したデバッグツール:

| ツール | 用途 |
|---|---|
| `scripts/decode_user_wav.py` | ユーザー実機 WAV をオフライン decode (UTF-8 結果ファイル出力) |
| `scripts/decode_demo_samples.py` | data/samples の合成サンプルを decode して TER/CER 評価 |

### 4.8 受信音から推定: 最適 CW トーン周波数

学習時のトーン周波数範囲: 400-900 Hz (一様)
→ **中央の 600-700 Hz が最も学習サンプル豊富**
→ 受信機 CW フィルタ中心を **600 Hz に設定**を推奨

### 4.9 和文モードでの数字未対応

#### 現象

和文モードで RST レポート (`599`) や周波数 (`14`) が「?」になる。

#### 原因

JAPANESE_TABLE に数字マッピング欠如。設計時に「和文 = カナのみ」と限定。

#### 解決

JAPANESE_TABLE に数字 0-9 と `? - @` を追加。

**重要**: モデル再学習不要。三層分離アーキテクチャの利点で、変換表の改修のみで対応。

## 5. 既知の課題

### 5.1 致命的でないクラッシュ (sounddevice + Qt + Windows)

- **症状**: アプリ終了時 (X ボタン) に segfault (exit 139)
- **原因**: sounddevice の Stream 終了タイミングと Qt cleanup のレースコンディション
- **影響**: 機能的には問題なし (アプリは閉じる)
- **対策**: `stream.abort(ignore_errors=True)` を試みているが完全には防げず
- **本質的解決**: 不明 (Windows + PortAudio + Qt の組合せの既知問題)

### 5.2 実音声デコード精度ギャップ

| 観点 | 合成データ | 実音声 |
|---|---|---|
| TER | 0% | 約 30% (推定) |
| 安定性 | 完璧 | コールサインが回毎に変わる |

#### 系統的な誤認識

実音声で頻繁に発生する文字混同:
- `D` ↔ `B` (`-・・` vs `-・・・`)
- `K` ↔ `T` (`-・-` vs `-`)
- `Y` ↔ `A` (`-・--` vs `・-`)
- `9` → `O` (`・----` vs `---`)
- `JIRO` → `JERO` (`I` → `E`)
- `NAME` → `EAME` (`N` → `E`)

#### 原因

学習データ (合成 raised-cosine キーイング + AWGN + バターワース BPF) と実音声 (操作者の手送り癖、受信機固有特性、伝搬チャネル) のギャップ。

#### 根本解決策

**Phase 4 (実信号 FT)** の本領発揮ポイント。これらの系統誤りは実信号学習で大幅減できる見込み。

### 5.3 短符号の認識不安定

欧文の E (`・`), T (`-`), I (`・・`), A (`・-`), N (`-・`) など短符号:
- ノイズ片との混同
- 確信度低下 → `?` 置換

→ 和文 (符号長平均 4-5 要素) より欧文 (平均 3 要素) の方が認識率劣る傾向

#### 対策

- 確信度閾値を下げる (0.2-0.3) で取りこぼし減少
- BPF を狭く (250 Hz) でノイズ削減
- Phase 4 FT が決定打

### 5.4 ストリーミング vs オフラインのギャップ

| 観点 | オフライン (全体) | ストリーミング (5秒チャンク) |
|---|---|---|
| 同一 80秒 QSO | 123 tokens | 108 tokens |
| 遅延 | なし (一括) | 6 秒 + 5 秒毎 |
| 精度 | 100% (モデル真の能力) | 約 88% (チャンク文脈損失) |

#### 対策

**手動デコードモード** + **自動チャンクモード** で実質的にオフライン精度を任意のタイミングで取得可能に。

#### Phase 6 で構造的に解消 (スライディングウィンドウ + prefix commit, 2026-06-13)

「切って捨てる」チャンク方式を廃止し、リングバッファ (既定 30 秒) を 1 秒ごとに**全体再デコード**し、文脈が確定した区間 (`[head_guard, now - commit_lag)`) のトークンだけを**不変 (immutable)** に確定する方式へ置換。各トークンは必ず前後数秒の文脈を持った状態の結果のみが確定するため、チャンク境界の文脈損失が構造的に消滅する。

実測 (`scripts/eval_streaming_vs_offline.py`, CPU, `models/full/best.pt`):

| ファイル長 | ストリーミング確定列 vs オフライン全体 | RTF | max redecode |
|---|---|---|---|
| 和文 11〜28 秒 (×3) | **100%** 一致 | 0.03〜0.05 | 51〜92 ms |
| 欧文 80 秒 (123 token) | 91.1% (`left_context=5s`) 〜 93.9% (`25s`) | 0.04〜0.10 | 61〜149 ms |

- **窓長 (30s) 以内に収まるファイルはオフライン完全一致**。これがストリーミング/オフライン文脈損失問題の構造的解消の証拠。
- **窓長を超える長尺ファイル (80s) は 92〜94% で頭打ち**: ストリーミングは各トークンを有界右文脈 (`commit_lag`) で確定する一方、オフラインは全体を一度に見るため、原理的に完全一致しない (これは低遅延化との本質的トレードオフであり、旧 5 秒チャンクの約 88% から改善)。`decode_left_context_s` を増やすと一致率は微増するが RTF も上昇する (既定 5.0 で RTF 0.04、十分な余裕)。
- 旧チャンク方式 (5 秒) の約 88% / 遅延 6 秒に対し、本方式は遅延 ≈ `hop + commit_lag + 推論` ≈ 3.5〜4 秒で確定。

### 5.5 リアルタイム CW 文脈損失

CTC モデルは双方向 LSTM を持つが、チャンク境界で文脈リセット。長い文字 (例: `FUKUSHIMA` 9文字) がチャンクをまたぐと精度低下。

#### 対策

- チャンク長を拡大 (5-10 秒) — 実装済
- 「全体デコード」モード — 実装済
- **Phase 6 スライディングウィンドウ + prefix commit — 本質的解決** (§5.4 参照)。長い文字も窓内に収まれば全文脈でデコードされてから確定するため、境界損失が起きない。

### 5.6 設定の永続化と起動時挙動

#### 課題

`~/.cw-decorder/settings.json` の値が古いと、コードのデフォルト変更が反映されない。

例: コードで `chunk_duration_s: float = 5.0` にしても、保存ファイルに `1.5` が残っていれば 1.5 が使われる。

#### 対策

- **マイグレーション機能 — Phase 6 で実装済 (`settings_version=2`)**: 起動時に旧 version の `settings.json` を読むと、欠損フィールドを新既定で補完し、旧既定値 (例 `chunk_duration_s=1.5`) を新既定 (5.0) へ置換する (ユーザーが明示変更した値は尊重)。`migrate_settings_dict` / `load_settings` 参照。移行時は `[settings-migrate]` ログを出力。
- 手動で `settings.json` を編集
- CLI 引数で上書き (`--chunk 5.0`)

### 5.6.1 Phase 6 の既知の制限: 確定テキストの全文 re-emit

ライブ連続モードのワーカー `_emit_live_view` は毎 hop で確定済み全体を再変換し全文 emit する。`committed` は無制限に成長するため、長時間運用 (数千トークン) では毎秒の全文変換 + `setHtml` 全置換になり、UI スクロールのちらつき/位置ジャンプの恐れがある。当面は既知の制限とし、本筋の対処 (`newly_committed` 差分のみ emit + UI 追記) は実運用で問題が顕在化してから行う。

### 5.6.2 Phase 6 の既知の制限: 暫定 (グレー) プレビューの一過性アーティファクト

`_emit_live_view` は確定列と暫定列を**別々に** `convert()` する。このため境界をまたぐ合成 (和文の濁点/半濁点が前カナと別パスになる) や、暫定先頭の語間スペースが、暫定が確定するまでの一瞬だけ不正に見えることがある (例: `カ`(黒) + `゛`(グレー) が一瞬表示され、濁点確定時に `ガ` に合成される)。**確定 (黒) テキストは常に正しく**、トークンが確定すれば自己修復する一過性の表示のみの問題。確定列+暫定列を 1 ストリームで変換して文字列境界で分割する方式は、合成による文字列長変化のため実装が脆く、現状は一過性の制限として許容する。

また、送信終了が再デコードスキップ直後に重なる極端なケースで、`commit_lag` 圏内の未デコードトークンが取りこぼされる理論的余地がある (無音中も暫定が残る間は再デコードを継続する設計のため発生確率は低い)。`stop()` の `finalize()` が大半を救済する。

### 5.7 WORD_BREAK トークンの実音声適応不足

#### 観察

合成データでは WORD_BREAK が正しく語間に挿入される (CER 14% → 2.5% 改善)。
しかし**実音声では過剰検出**: `コ ン ニ チ ハ` のように 1 単語が分割される。

#### 原因

- 学習データの語間 7 dot 無音は合成器が忠実に再現
- 実音声の語間は操作者によって 5-15 dot とバラつく
- 短い間でも WORD_BREAK を出してしまう

#### 対策

- 確信度閾値を WORD_BREAK だけ高くする (未実装)
- 学習データの語間分布を広げる
- 実音声 FT で実際の語間分布を学習

### 5.8 AGC ランプアップ初期不安定

#### 課題

AGC ゲインが初期値 1.0 から目標値 (例: 10x) に達するまで数秒かかる。その間の音声は適切に増幅されておらず、モデルが誤認識しやすい。

#### 対策案 (未実装)

- AGC 初期ゲインを履歴から学習
- 起動直後の数秒を decode 結果から除外
- 別の AGC アルゴリズム (look-ahead 有り)

### 5.9 Windows サウンドカードの可変サンプルレート

- デフォルトでは 44.1 kHz / 48 kHz など
- soxr で 8 kHz に正確リサンプル → 解決

### 5.10 BPF と AGC の相互作用

BPF を狭くする → 信号エネルギーが減る → AGC が過剰に増幅 → ノイズも増幅

#### 対策案 (未実装)

- AGC 目標ピークを BPF 帯域幅に応じて調整
- BPF 後の SN 比測定 → AGC ゲイン制御

## 9. 今後の作業

### 9.1 優先度: 高

1. **Phase 4 FT の実施** — ユーザーの実機録音 (現時点で 4 件あり) を蓄積して FT
2. ~~**設定マイグレーション**~~ — 実装済み (settings_version、v3 でレガシーキー撤去)
3. ~~**ホレ/ラタ 自動モード切替**~~ — **実装済み (2026-06-13)**。下記参照。

#### 自動モード切替 (実装済み)

モードコンボに「自動」を追加。`TokenConverter(mode="auto")` がトークン列を 1 回走査し、
ローカルな現在サブモードを `[ホレ]` (和文開始) で和文へ、`[ラタ]` (和文終了) で欧文へ
切替える。ラタは欧文 SN と同符号 (`・・・-・`) のため、**和文サブモード中のみ**和文終了
として扱い、欧文中は SN 表示・切替なし。初期は欧文。確定列は欧文起点で変換し、暫定列は
確定列末尾のサブモードを継ぐ (`initial_mode`/`final_mode`)。三層分離によりモデル再学習不要。

同時に、実用化したライブ連続モードへ一本化し、レガシー手動デコード経路 (手動バッファ蓄積・
オフライン一括 decode・無音検出自動チャンク・旧 StreamingDecoder) を UI・コードとも撤去。
デコード操作は単一トグル「デコード開始/停止」に集約。

**既知の制限 (自動モード):**
- 確信度が閾値付近の `[ホレ]` がコミット境界にあると、確定するまでの数フレーム、後続文字が
  欧文⇄和文で一時的に揺れることがある (暫定プレビューの一過性。確定後に解消)。
- モード変更・デコード再開始時は、旧テキストを即時クリアして新セッションで再構築する。

## 10. 教訓と知見

### 10.1 設計の正解

- **三層分離 (音→符号→文字)** が正解だった。和文数字対応がモデル再学習なしでできたのは大きい。
- **e-Gov 規則との照合テスト**が初期バグを多数検出。「規則と実装の二重管理」は冗長に見えて重要。

### 10.2 開発過程で学んだこと

- **scipy.signal.resample_poly はストリーミング不可** → soxr 必須
- **Qt クロススレッド呼出しは絶対 signal 経由** にする
- **AGC は時間がかかる** → 初期 5-10 秒は decode 結果当てにできない
- **実音声と合成音声には大きなギャップ**がある → FT が決定的
- **リモートデスクトップ音声経路は壊滅的** → アプリは音源に近い PC で動かす
- **エンドユーザーに対する UI は段階的** に明らかにすべき: 「開始 → レベル調整 → デコード録音開始 → デコード」が正解
- **無音検出の閾値は絶対値より相対値 (= UI で見える線)** が直感的

### 10.3 ユーザーフィードバックループの価値

実機テスト中のユーザー観察が決定打:
- 「scipy リサンプリングが per-block で歪む」発見
- 「先頭部分が失敗する」「無音検出が動かない」等の現場知見
- 「和文の方が認識いい」観察 → 短符号問題の特定
- 「リモートデスクトップで音が劣化」発見

→ 合成データだけで完結する開発は限界。実機ユーザー検証必須。
